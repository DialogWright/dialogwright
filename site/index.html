Voice and chat agents that understand people like an LLM, and act like code.

Callers say what they want in their own words, and are understood. What the line does is predictable: before anything is booked, sent or changed, a policy gate (your rules, checked in code) decides whether it may happen, and every decision is logged. Script every word, or let a model hold the conversation in agent mode. Either way, replies are fast.

GitHub repository Quick start

Open source, Apache-2.0. Pre-release. Try it on your laptop, no keys needed.

Two ways to build a line

Both understand callers in their own words, and both put every action through the same policy gate and the same audit log, where each entry is sealed with a hash of the one before, so a later edit shows. They differ in who chooses the words the caller hears.

What both share

  • The gate and the logEvery action checked against your policy, and every decision, allowed or refused, written to the audit log.
  • Phone and chatTelnyx and Twilio for calls, a web chat and its widget for sites, and texts.
  • The consoleA web page with every call and chat, turn by turn, and what was said and done.
  • Policy pagesWhat the gate allows, written out in plain English and as a table, generated from the policy for review.

How to choose

Choose agent mode when

  • the line should talk like a person at the counter: callers interrupt, wander, correct themselves and give things in any order,
  • the business accepts that it cannot choose every word, and that the line will sometimes be a little odd in ways a scripted one never is,
  • the business would rather fill in one file of its information and actions than design every step of the call.

Choose scripted when

  • every line must be the app's own words, such as a regulated disclosure,
  • callers must prove who they are, with a date of birth or a one-time code (agent mode cannot check that yet),
  • it needs answers from approved documents, more than one language, a keypad menu or call routing, which agent mode does not have yet.

Decision models are the heart of it

A decision model reads what the caller said and answers questions your app asks about it: yes or no, which of these options, how much. Each answer comes with a probability, and the model never writes text. DialogWright asks all of a turn's questions in one request, and your code acts on the answers against thresholds you set. Below, one turn in the front desk example.

Jev is the default, TypeSafe's decision model (jev-1.13). Any model that answers the same way (TypeSafe's System One API) can replace it, once measured on the app's own recorded calls, as Microsoft-Decision-1 has been.

Why it is cheap: it writes no text, only a few probabilities, so a turn pays almost only for reading.

Why you would use it

  • Callers talk naturally. They use their own words, and can give several answers at once.
  • What is done is predictable. Your code decides each step, and the policy gate checks every action. In a scripted line, every word is yours too.
  • Or a natural conversation, in agent mode. A model talks from a file of the business's information. Before anything is booked or sent, the line reads it back and waits for the caller to confirm.
  • Fast and cheap per turn. The decision model answers in about 90 to 150 ms at the median.
  • Every decision is logged. Allowed or refused, in a log where each entry seals the one before.
  • Tested before a call is taken. Recorded calls replay offline, and generated hostile calls try to talk the line into what it must not do.
  • Runs on your own machine, or on several servers for high availability. They share one database, and when a server stops, another takes its calls over.
  • Built for AI coding assistants: Claude Code builds the app.
  • Answers from a knowledge base. Answers come from passages and documents a person approved, searched on your own machine. Per topic, you choose whether they are said word for word, reworded for the question, or written from the documents (with the documents' own lines if a check fails). A follow-up question is read with the one before it.
  • On the web, too. The same app answers a web chat, with a branded page, formatted answers, answer buttons and where each answer comes from.
  • Generated wording only where you opt in. In the front desk example, the line repeats a message back with a model's short summary in a fixed sentence. If the summary fails a check, the caller hears their own words instead.

Describe your line in a paragraph. Claude Code builds the app.

DialogWright ships a Claude Code skill, create-app, in every project npm create dialogwright makes. Say what callers can ask for, who must verify, what must be confirmed and what goes to a person. Claude Code plans the app, scaffolds it, writes the YAML, the code, example caller phrases and scripted test calls, and keeps going until the checks, the type check and the tests pass. Then it gives you the command to record a real model's answers, and reviews what the recording changed.

The utility and front desk examples were each built this way, from one paragraph.

Quick start

Node 22.19 or later and pnpm. No keys: without a model, each app understands callers from its own labelled example phrases.

  1. Clone and install.

    git clone https://github.com/DialogWright/dialogwright.git
cd dialogwright
pnpm install

  2. Talk to the clinic in a text console.

    pnpm --filter @dialogwright/example-clinic cli --client heuristic

  3. Start an app of your own.

    pnpm create-app <name>

A real phone line needs a carrier account and a decision model's key (and, for generated wording, a key for the model that words it): run it on a machine you own.
