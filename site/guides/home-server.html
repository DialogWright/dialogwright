Guides / A machine you own

Run your own IVR on a machine you own

Your laptop to try it, then any machine that stays on: a Mac, a Linux mini PC, a spare desktop. Try it first with no accounts at all. A real phone line needs two keys, a carrier's and a decision model's, and a tunnel that can be had without signing up for anything.

Pre-release. DialogWright runs as a single process today, and its sessions live in that process's memory: restarting the server drops any call in progress. A tunnel can blip and a call reconnects; the server cannot restart and keep its calls. Phase 8 of the roadmap adds the production pieces.

A personal line (answering your own number, screening, taking a message, sending urgent calls to your mobile) is something you can build on it, not an example app yet. The steps are the same for any app; the utility example stands in for yours below. Every name, number, key and host name here is made up.

1. Try it with no accounts

Everything here runs on your laptop with no key and no sign-up. With no model attached, an app understands through its own labelled examples and a keyword fallback: enough to walk every path, not the real thing. You need Node 22.19 or later and pnpm (section 4). 

git clone https://github.com/DialogWright/dialogwright.git
cd dialogwright
pnpm install
pnpm --filter @dialogwright/widget build
pnpm configure --app utility --mode try
pnpm start --app utility

pnpm configure asks which app and how to try it (the flags above answer for the utility example, on this computer) and writes the app's settings to apps/utility/.env: the server on localhost, the web chat and its widget on, no model. pnpm start runs the app's server with that file. Then open http://localhost:3000/chat-demo (a fictional account page with the chat widget on it) and http://localhost:3000/dashboard (the operator console, showing the chat as it happens). Both exist only on this machine. The utility's README says what to try. Ctrl-C stops it.

The same server by hand, with its settings on the command line instead of in a file:

PUBLIC_HOST=localhost TWILIO_AUTH_TOKEN=unused HANDOFF_NUMBER=+15551234567 \
  CHAT=on CHAT_ALLOWED_ORIGINS=http://localhost:3000 CHAT_SIGNIN=mock WIDGET=on \
  pnpm --filter @dialogwright/example-utility serve

Or talk to the clinic example in a text console, with no server at all:

pnpm --filter @dialogwright/example-clinic cli --client heuristic

With one key you can hear the real model in the same console: pnpm --filter @dialogwright/example-clinic cli --client jev with TYPESAFE_API_KEY set (or another provider, section 3). To build your own app, run pnpm create-app myline and read Authoring an app.

Then a phone line, the same evening

With a carrier account and a number (Telnyx or Twilio), a decision model key (section 3) and cloudflared installed (brew install cloudflared on a Mac; section 6): 

pnpm configure --app utility --force
pnpm start --app utility

This time choose a phone line. pnpm configure asks for the carrier and its key, the model and its key, and the number a call goes to for a person. A key is read with the echo off (or taken from the environment variable of its own name, never from a flag) and written only to the app's .env, readable by you alone; the command prints its length, never the key, and sends it nowhere. It then checks the file (pnpm diagnose --offline) and says where to paste the webhook in the carrier's console. pnpm start opens a Cloudflare quick tunnel, which needs no account, starts the server with the tunnel's hostname, and prints the webhook URL (https://<words>.trycloudflare.com/voice/telnyx): paste it into your number (section 7) and call. While it runs, pnpm diagnose --app utility in another terminal checks it end to end (section 8).

The hostname changes every time pnpm start runs, so the webhook does too: fine for an evening, wrong for a line people rely on. The sections below make it permanent: a machine that stays on, the settings outside the repository, a named tunnel, and a service that starts it at boot.

2. The architecture

A caller dials your number. The carrier asks your server what to do (an HTTPS webhook), then opens a WebSocket to it and streams the call as text: the carrier recognises speech and speaks the lines, and DialogWright understands and decides. Both reach your machine through a tunnel, so nothing on your router is opened. On each turn the server asks the decision model a few short typed questions.

  • The carrier owns the number. DialogWright answers it on /voice/<carrier> (the webhook), /cr-action/<carrier> (the callback when the relay ends) and the WebSocket /conversation/<carrier>.
  • The tunnel gives the carrier an HTTPS address for a machine behind a home router.
  • The server is pnpm --filter <your app> serve: the phone line, the operator console and, if you turn it on, the web chat on /chat.
  • The decision model reads what the caller said and answers typed questions. It never writes what the caller hears.

3. Two keys, and what is optional

A phone line needs two accounts: a carrier, for the number, and a decision model, for the understanding (or a compatible model on your own machine, which needs neither an account nor a key). Everything else is optional or free of sign-up. The running cost is small: a few dollars a month for a number, and fractions of a cent per call for the model. The repository's live checks put a handful of test calls at "a few cents of call minutes and model requests", and each trace records the estimated cost of its turns' model requests (usage.costUsd), so your own numbers are in your own files.

The Telnyx adapter is built from Telnyx's documentation and checked against its documented frames, but a few of its details (the webhook's encoding, the handoff field, whether a callback is posted when the socket drops) are assumptions until a live call settles them: live check 2 is the call to make first. If anything there fails, Twilio is the fallback.

4. The machine

Your laptop is fine for trying a real call. For a line that stays up, use anything that stays on: a Mac, a Linux mini PC, a spare desktop. It needs little: one Node process and a tunnel.

Keep it on

  • macOS: in System Settings, Energy, turn on Prevent automatic sleeping when the display is off, Start up automatically after a power failure and Wake for network access. With FileVault on, a Mac that restarts after a power failure waits for a password before anything starts.
  • Linux: stop it suspending (sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target on a desktop install), and set the firmware to power on when power returns.
  • Both: let the clock set itself. Telnyx's signature is refused when the server's clock is more than five minutes off.

Node and pnpm

The repository requires Node 22.19 or later (CI runs Node 22 and 24) and pnpm 9 (it pins pnpm@9.12.0 in package.json, which corepack follows). Install Node 24 from nodejs.org, your package manager or Homebrew (brew install node@24), then: 

corepack enable pnpm
node --version     # v22.19 or later
which node pnpm    # note the folders: the service needs them on its PATH

Then clone and install as in section 1, and run pnpm --version once inside the repository: corepack fetches pnpm 9.12.0 then, so the service never has to. If you will put the chat widget on a site, build it (pnpm --filter @dialogwright/widget build, again after each update).

This guide calls your app myline (pnpm create-app myline makes apps/myline, package @dialogwright/example-myline). To follow along with a finished app, use @dialogwright/example-utility in its place. Keep what is yours apart from the repository: the settings, the logs and the call data. 

mkdir -p ~/ivr/logs ~/ivr/data/traces ~/ivr/data/audit
chmod 700 ~/ivr

5. Configuration

The server reads its environment and, when ENV_FILE (or --env-file <path>) names one, a settings file; a variable already in the environment wins over the file. pnpm configure writes one in the app's folder. For a line that stays up, keep it outside the repository instead, in ~/ivr/myline.env, readable by you alone, and name it: pnpm start --env-file ~/ivr/myline.env and pnpm diagnose --env-file ~/ivr/myline.env read it, and the service file (section 9) names it the same way. Write it by hand from the example below, or move the one pnpm configure wrote (mv apps/myline/.env ~/ivr/myline.env). The values below are made up. The variables, their defaults and their checks are the server's own (packages/dialogwright/src/server/config.ts): it refuses to start, naming the variable, when one is missing or malformed. 

chmod 600 ~/ivr/myline.env
PUBLIC_HOST
Your tunnel's hostname. The server builds every URL it gives the carrier from it, and checks Twilio's signature against https://<PUBLIC_HOST><path>, so it must be exactly the hostname the carrier calls.
VOICE_PROVIDERS and the carrier's secret
Each carrier listed needs its secret: TELNYX_PUBLIC_KEY (refused at startup unless it is a base64 Ed25519 key), TWILIO_AUTH_TOKEN.
SIGNATURE_CHECK=on
A webhook the carrier did not sign is refused. off exists only for posting webhooks by hand on a laptop.
JEV_CLIENT, JEV_PROVIDER and the key
Without JEV_CLIENT=jev the server runs on the stub. Once it is jev, the provider's key variable is required (for custom, JEV_BASE_URL and JEV_MODEL are).
CONSOLE_LOCAL_ONLY=on
The console (/dashboard) answers only a request made on this machine; through the tunnel it is a 404.
TRACE_DIR, AUDIT_DIR
Absolute paths keep the call data out of the repository, in one place to back up.
WIDGET_FILE
The default is the widget in your app's own node_modules, which a new app does not have (the utility does); name the built file instead.

The rest (RECONNECT_LIMIT, NO_INPUT_MS, SESSION_TTL_MS, the chat's limits and more) have defaults that suit one line; the options table and the commented .env.example list them.

6. The tunnel

A tunnel is an outbound connection from your machine to someone's edge; requests for its hostname come back down it, so your router needs no open port. Install cloudflared (brew install cloudflared on a Mac; on Linux, Cloudflare's package repository or a release binary from its downloads page).

To try it: a quick tunnel, no account

pnpm start does this for you when PUBLIC_HOST is unset (or with --tunnel quick): it starts cloudflared, reads the hostname it is given, starts the server with it, prints the webhook URL, and stops the tunnel only once the server has finished its calls. Without cloudflared it says how to install it. By hand, in one terminal: 

cloudflared tunnel --url http://localhost:3000

It prints a random https://<words>.trycloudflare.com address. Put that hostname (without https://) in PUBLIC_HOST, start the server in another terminal, and point the carrier at it (section 7): 

cd ~/dialogwright
set -a && source ~/ivr/myline.env && set +a
pnpm --filter @dialogwright/example-myline serve

The hostname changes every time cloudflared starts, so PUBLIC_HOST and the carrier's webhook change with it. That is fine for an evening of testing and wrong for a line people rely on. Cloudflare also gives a quick tunnel no uptime guarantee and caps it at 200 requests in flight.

Cloudflare's quick tunnel page does not mention WebSockets, which the call's relay needs. Named tunnels pass them; for a quick tunnel, a test call is the check (section 8).

To keep it: a named tunnel on your own domain

A named Cloudflare Tunnel keeps one hostname (ivr.example.com) for good. It needs a free Cloudflare account and a domain whose DNS is on Cloudflare. These are the steps for a locally managed tunnel, as Cloudflare's docs give them:

  1. Log in (it opens a browser; choose your domain) and create the tunnel. It prints the tunnel's id and writes its credentials to ~/.cloudflared/<id>.json.

    cloudflared tunnel login
cloudflared tunnel create myline

  2. Point your hostname at it (this adds the DNS record):

    cloudflared tunnel route dns myline ivr.example.com

  3. Write ~/.cloudflared/config.yml with your tunnel's id. The last rule, a catch-all, is required: anything not for your hostname is a 404 at Cloudflare.

    tunnel: 0b5e7c2a-5555-4f00-9d1e-123456789abc
credentials-file: /Users/alex/.cloudflared/0b5e7c2a-5555-4f00-9d1e-123456789abc.json

ingress:
  - hostname: ivr.example.com
    service: http://localhost:3000
  - service: http_status:404

  4. Check the rules and run it once in the foreground:

    cloudflared tunnel ingress validate
cloudflared tunnel run myline

  5. Run it as a service. cloudflared service install starts it at login from ~/.cloudflared/; sudo cloudflared service install starts it at boot and reads /etc/cloudflared/ (copy the config and the credentials file there, and fix credentials-file). On Linux, sudo cloudflared service install makes a systemd service.

    sudo cloudflared service install

When a tunnel drops a call's socket, the carrier calls /cr-action and the call reconnects, up to RECONNECT_LIMIT times (default 2), then goes to a person with an apology. That works because the server still holds the call; a restart of the server does not, and ends it. Whichever tunnel you use, the server tells a tunnelled request from one made on the machine by the headers a proxy adds and by the Host it names, so the console stays off the internet.

7. Pointing the carrier at it

Telnyx

  1. In the Mission Control Portal, get a number with voice.
  2. Go to Real-Time Communications, Voice, Programmable Voice, the TeXML Applications tab, and create an application.
  3. In Send a TeXML Webhook to the URL, enter https://ivr.example.com/voice/telnyx (your PUBLIC_HOST), with the Voice Method POST.
  4. Assign your number to the application, on its Numbers tab (or from Real-Time Communications, Numbers, Manage Numbers).
  5. Copy the public key from Account settings, Keys & Credentials, Public Key into TELNYX_PUBLIC_KEY, with VOICE_PROVIDERS=telnyx, and restart the server.
  6. Worth it on a home line: the application's Webhook Failover URL is asked when your server does not answer. Point it at a static TeXML document (a TeXML Bin) that dials your mobile, so a call still reaches you when the machine is off.

Portal labels move. These are the ones Telnyx's TeXML pages use as of this writing; if yours differ, the fields are the application's voice URL, its method and its failover URL.

Twilio

  1. In the Twilio Console, open Phone Numbers, Manage, Active numbers and choose your number.
  2. Under Voice Configuration, set A call comes in to Webhook, https://ivr.example.com/voice/twilio, HTTP POST.
  3. Optional: Primary handler fails takes a fallback URL, asked when your server errs or does not answer within 15 seconds. A TwiML Bin that dials your mobile does the same job as Telnyx's failover.
  4. Copy the account's auth token into TWILIO_AUTH_TOKEN, with VOICE_PROVIDERS=twilio (or twilio,telnyx), and restart the server.

The plain https://ivr.example.com/voice works for Twilio too: it is the path from before carriers were plug-ins.

8. Checking it works

  1. The startup line names what is in force, each secret by its length only (telnyx public key set (44 chars)), then listening on 3000; voice webhook https://ivr.example.com/voice/telnyx. The server answers on the machine and through the tunnel:

    curl -s http://localhost:3000/health
curl -s https://ivr.example.com/health

    Both print {"ok":true,"sessions":0,"retained":0}: the calls live now, and the ended ones still held for a minute. /health says the process is up; /ready says whether it takes new calls ({"ready":true}, or 503 while it drains before a stop).

  2. Or let pnpm diagnose check all of it, and more, one line each with its fix: the settings load, the hostname resolves and /health answers through the tunnel, the console is a 404 there, the carrier's secret has its shape, the model and its key variable, the handoff number is not a 555 number, the folders can be written with space to spare, and the clock is right (Telnyx refuses a webhook whose signature is more than five minutes off). It calls no carrier and no model.

    cd ~/dialogwright && pnpm diagnose --app myline --env-file ~/ivr/myline.env

  3. The console is not public. This prints 404:

    curl -s -o /dev/null -w '%{http_code}\n' https://ivr.example.com/dashboard

  4. Call your number. The server's output shows the webhook as the call arrives (/voice/telnyx ... from ...) and /cr-action/telnyx ... -> completed when it ends, with no signature rejected line.

  5. Watch calls in the console on the machine itself, http://localhost:3000/dashboard. From another computer, forward the port over SSH and open the same address there:

    ssh -L 3000:localhost:3000 alex@homebox.local

  6. Each call leaves two files in the traces folder: <call>.jsonl, its turns (what was heard, what the model answered, what the gate decided, how long each step took), and <call>.frames.jsonl, every frame in and out. The audit folder has one hash-chained file per UTC day; check the chains:

    ls -lt ~/ivr/data/traces | head
cd ~/dialogwright && pnpm audit:verify ~/ivr/data/audit

Then go deeper with the live checks: the Telnyx call that settles the adapter's assumptions, a reconnect, languages, a gateway for the model, and a real identity provider for the chat.

9. Keeping it running

Once the line works, hand it to the system's service manager: it starts the server at login or boot, restarts it when it exits, and keeps its output. pnpm service writes the service file for this machine, with the absolute paths of the repository, pnpm, node and the settings file, and prints the commands that install it; it runs none of them. The service runs pnpm --filter @dialogwright/example-myline serve from the repository with ENV_FILE naming ~/ivr/myline.env, so the server reads the same file pnpm start and pnpm diagnose read. Nothing from the file goes into the service file but its path.

A stop sends SIGTERM to pnpm, which passes it to the server and waits. The server drains: /ready answers 503, a new call is put through to HANDOFF_NUMBER, a new chat is told it is busy, and live calls go on until they end or DRAIN_MS passes (30 seconds by default); then it closes what is left and exits. The service gives a stop DRAIN_MS and ten seconds more before it kills anything. A second signal stops the server at once. A crash is logged with its stack and exits 1, and the service manager starts it again.

macOS: a launchd agent

cd ~/dialogwright
pnpm service launchd --app myline --env-file ~/ivr/myline.env --label com.example.myline

It writes ~/Library/LaunchAgents/com.example.myline.plist from this template, its values filled in:

and prints the commands that install, check and stop it:

mkdir -p ~/Library/Logs/com.example.myline
plutil -lint ~/Library/LaunchAgents/com.example.myline.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.example.myline.plist   # start now, and at every login
launchctl print gui/$(id -u)/com.example.myline | grep -E 'state|pid'             # running or not
tail -f ~/Library/Logs/com.example.myline/out.log ~/Library/Logs/com.example.myline/err.log   # its output
launchctl kickstart -k gui/$(id -u)/com.example.myline                            # restart: live calls get DRAIN_MS to finish
launchctl bootout gui/$(id -u)/com.example.myline                                 # stop, and keep it stopped

An agent runs while you are logged in: turn on automatic login, or run it at boot as a daemon (copy the file to /Library/LaunchDaemons/, owned by root, add <key>UserName</key><string>alex</string>, and use sudo launchctl bootstrap system ... and system/com.example.myline). With KeepAlive on, killing the process only restarts it: bootout stops it.

Linux: a systemd user unit

cd ~/dialogwright
pnpm service systemd --app myline --env-file ~/ivr/myline.env --label myline

It writes ~/.config/systemd/user/myline.service from this template:

and prints:

systemctl --user daemon-reload
systemctl --user enable --now myline   # start now, and at every login
loginctl enable-linger "$USER"         # and at boot, before anyone logs in
systemctl --user status myline         # running or not
journalctl --user -u myline -f         # its output
systemctl --user restart myline        # restart: live calls get DRAIN_MS to finish
systemctl --user disable --now myline  # stop, and keep it stopped

A system unit works the same way: copy the file to /etc/systemd/system/, add User=alex under [Service], make it WantedBy=multi-user.target, and use sudo systemctl without --user (and without the linger).

On either system, a wrong setting shows as a restart every ten seconds, with the variable named in the output (missing required environment variable TELNYX_PUBLIC_KEY (VOICE_PROVIDERS includes telnyx)): run pnpm diagnose --env-file ~/ivr/myline.env first.

10. Updating, backing up, watching, security

Updating

DialogWright is pre-release and its APIs change, so update on purpose, and note the commit you last ran well (git rev-parse --short HEAD) so you can go back. An update restarts the server: it stops taking new calls and gives live ones DRAIN_MS to finish, but a call still going after that is dropped (the server does not keep its calls across a restart yet), so check /health says "sessions":0 first. 

cd ~/dialogwright
git pull
pnpm install
pnpm check
pnpm --filter @dialogwright/example-myline test
pnpm --filter @dialogwright/widget build     # if you serve the widget
curl -s http://localhost:3000/health
systemctl --user restart myline              # or: launchctl kickstart -k gui/$(id -u)/com.example.myline

Update the operating system, Node and cloudflared on the same quiet occasions.

Backing up

What is yours and not in git: ~/ivr/myline.env (your keys: back it up only somewhere encrypted), the traces and audit folders, and ~/.cloudflared/ (a named tunnel's credentials). The audit files are append-only and chained: copy them, never edit them, since an edit breaks every later link.

What to watch

  • Disk. Unless you say otherwise, nothing deletes old traces: two files per call, kept until you remove them. TRACE_RETENTION_DAYS=30 deletes traces and frame logs last written more than 30 days ago, swept at startup and once an hour, and /health then reports disk (traceBytes, auditBytes) for a monitor. AUDIT_RETENTION_DAYS does the same for audit days, which ends the record for those days: keep them as long as you must keep the record. The traces are what pnpm kb:gaps reads to find the questions your knowledge base did not answer, so archive them before they go.
  • The output. Errors and restarts show there first.
  • Slow turns. Each trace record carries its timing (timing.askMs, timing.totalMs). A model request slower than JEV_TIMEOUT_MS plays the slow-turn line and keeps the question open.
  • The carrier's own logs (Telnyx's webhook debugging, Twilio's call logs) when a call never reached you.

Security

  • Keys only in the settings file, mode 600, outside the repository: never in the unit, the plist, a script you commit, or a message. The server prints a secret's length, never its value.
  • Signature checks on (SIGNATURE_CHECK=on).
  • The console local-only (CONSOLE_LOCAL_ONLY=on): it shows calls as they happen, with what callers said. Reach it from elsewhere over SSH, never by turning this off.
  • No port opened on the router. The tunnel connects out. Turn on the machine's firewall: the server needs no incoming connection from the network, only from cloudflared on the same machine.
  • The traces hold what callers said. Treat the data folder as personal data, kept on this machine and in encrypted backups.
  • Keep the machine updated.
  • Building a line for a small business (a law office's, say)? Its callers are the business's clients: ask what it must keep, for how long, and who may read it, before the first call.

11. What is coming

Phase 8 is a machine you own, run for months. Its first part is here: pnpm configure, pnpm start with a quick tunnel, settings files, readiness and a drain, retention, pnpm diagnose and service files. Next for one machine is a session store that outlives the process, so a restart no longer drops a call; then writes that are never done twice after a crash, carrier fallback documents, and console sign-in. Until the store, update when the line is quiet. When one machine is no longer enough, the same app folder is designed to run on many servers.
