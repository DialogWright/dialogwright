Guides / A machine you own

Run your own IVR on a machine you own

Try it on your laptop tonight with no accounts at all. Then, with two keys, a carrier's and a decision model's, answer a real phone call within the hour, through a tunnel that needs no sign-up. When it works, move the same setup to any machine that stays on: a Mac, a Linux mini PC, a spare desktop.

Pre-release. DialogWright runs as one process on one machine, and everything on this page is built: the commands, the service files, calls that survive a restart, and the console on your phone. Running on many servers is designed and not built yet (scaling out).

A personal line (answering your own number, screening, taking a message, sending urgent calls to your mobile) is something you can build on it, not an example app yet. The steps are the same for any app; the utility example stands in for yours below. Every name, number, key and host name here is made up.

1. Try it with no keys

Everything here runs on your laptop with no key and no sign-up. You need Node 22.19 or later and pnpm (section 7 says how to get them). With no model attached, an app understands through its own labelled examples and a keyword fallback: enough to walk every path, not the real thing. 

git clone https://github.com/DialogWright/dialogwright.git
cd dialogwright
pnpm install
pnpm --filter @dialogwright/widget build
pnpm configure --app utility --mode try
pnpm start --app utility

pnpm configure asks which app and how to run it (the flags above answer for the utility example, on this computer) and writes the app's settings to apps/utility/.env: the server on localhost, the web chat and its widget on, no model. pnpm start runs the app's server with that file. Then open http://localhost:3000/chat-demo (a fictional account page with the chat widget on it) and http://localhost:3000/dashboard (the operator console, showing the chat as it happens). Both answer only on this machine. The utility's README says what to try. Ctrl-C stops it.

Or talk to the clinic example in a text console, with no server at all: pnpm --filter @dialogwright/example-clinic cli --client heuristic. To build your own app, run pnpm create-app myline and read Authoring an app.

2. A phone line in an hour

A real call needs three things you do not have yet, and only two of them are accounts:

  1. A carrier and a number. Telnyx or Twilio: a number with voice, and the account's public key (Telnyx) or auth token (Twilio).
  2. A decision model key. TypeSafe's, or OpenRouter's or the Vercel AI Gateway's; or none, with a compatible model on your own machine (section 4).
  3. cloudflared, Cloudflare's tunnel client, so the carrier can reach your laptop. Its quick tunnel needs no account: brew install cloudflared on a Mac; on Linux, Cloudflare's package repository or a release from its downloads page.

  1. Configure a phone line. --force replaces the settings the try-out wrote.

    pnpm configure --app utility --force

    This time choose a phone line. It asks for the carrier and its key, the model and its key, and the number a call goes to when the caller wants a person (your mobile, say). A key is read with the echo off, or taken from the environment variable of its own name; a key is never a flag, which would stay in your shell's history. It is written only to the app's .env, readable by you alone, and the command prints its length, never the key, and sends it nowhere. It then checks the file (pnpm diagnose --offline).

  2. Start it with a quick tunnel.

    pnpm start --app utility --tunnel quick

    pnpm start starts cloudflared, waits for the https://<words>.trycloudflare.com hostname it is given, starts the server with it, and prints the webhook URL (https://<words>.trycloudflare.com/voice/telnyx) with the steps for your carrier's console. --tunnel quick is the default while PUBLIC_HOST is unset, as pnpm configure leaves it.

  3. Point your number at the webhook it printed (section 5 has each carrier's console steps).

  4. Check it end to end. pnpm start prints the line to run, with the tunnel's hostname, in another terminal:

    PUBLIC_HOST=<words>.trycloudflare.com pnpm diagnose --app utility

    One line per check, each with its fix (section 6).

  5. Call your number.

Ctrl-C stops it: the server finishes the calls under way first (a drain), and only then is the tunnel closed. The hostname changes every time pnpm start runs, so the webhook does too: fine for an evening, wrong for a line people rely on. Sections 7 to 9 make it permanent: a machine that stays on, the settings outside the repository, a named tunnel, a service that starts it at boot, and calls that survive a restart.

Cloudflare's quick tunnel page does not mention WebSockets, which the call's relay runs on. Named tunnels document them; for a quick tunnel, your first call is the check (live check 7). If it fails there, use a named tunnel (section 7) or ngrok.

3. How it fits together

A caller dials your number. The carrier asks your server what to do (an HTTPS webhook), then opens a WebSocket to it and streams the call as text: the carrier recognises speech and speaks the lines, and DialogWright understands and decides. Both reach your machine through a tunnel, so nothing on your router is opened. On each turn the server asks the decision model a few short typed questions.

  • The carrier owns the number. DialogWright answers it on /voice/<carrier> (the webhook), /cr-action/<carrier> (the callback when the relay ends) and the WebSocket /conversation/<carrier>.
  • The tunnel gives the carrier an HTTPS address for a machine behind a home router.
  • The server is pnpm --filter <your app> serve: the phone line, the operator console and, if you turn it on, the web chat on /chat.
  • The decision model reads what the caller said and answers typed questions. It never writes what the caller hears.

4. Two keys, and what is optional

pnpm configure asks for both keys and writes them where they go. A phone line needs two accounts: a carrier, for the number, and a decision model, for the understanding (or a compatible model on your own machine, which needs neither an account nor a key). Everything else is optional or free of sign-up. The running cost is small: a few dollars a month for a number, and fractions of a cent per call for the model. The repository's live checks put a handful of test calls at "a few cents of call minutes and model requests", and each trace records the estimated cost of its turns' model requests (usage.costUsd), so your own numbers are in your own files.

If anything there fails, Twilio is the fallback.

5. Pointing the carrier at it

pnpm start prints these steps with your webhook URL in them. With a quick tunnel the hostname is <words>.trycloudflare.com and changes every run; with a named tunnel it is yours for good. Below, ivr.example.com stands for either.

Telnyx

  1. In the Mission Control Portal, get a number with voice.
  2. Go to Real-Time Communications, Voice, Programmable Voice, the TeXML Applications tab, and create an application.
  3. In Send a TeXML Webhook to the URL, enter https://ivr.example.com/voice/telnyx (your PUBLIC_HOST), with the Voice Method POST.
  4. Assign your number to the application, on its Numbers tab (or from Real-Time Communications, Numbers, Manage Numbers).
  5. Copy the public key from Account settings, Keys & Credentials, Public Key into TELNYX_PUBLIC_KEY, with VOICE_PROVIDERS=telnyx, (pnpm configure does both).
  6. On a line people rely on: the application's fallback URL (Webhook Failover URL) is asked when your server does not answer. Point it at the document pnpm fallback writes (section 9), so a call still reaches you when the machine is off.

Portal labels move. These are the ones Telnyx's TeXML pages use as of this writing; if yours differ, the fields are the application's voice URL, its method and its failover URL.

Twilio

  1. In the Twilio Console, open Phone Numbers, Manage, Active numbers and choose your number.
  2. Under Voice Configuration, set A call comes in to Webhook, https://ivr.example.com/voice/twilio, HTTP POST.
  3. On a line people rely on: Primary handler fails takes a fallback URL, asked when your server errs or does not answer within 15 seconds. Point it at the document pnpm fallback writes (section 9).
  4. Copy the account's auth token into TWILIO_AUTH_TOKEN, with VOICE_PROVIDERS=twilio (or twilio,telnyx), (pnpm configure does both).

The plain https://ivr.example.com/voice works for Twilio too: it is the path from before carriers were plug-ins.

6. Checking it works

  1. The startup line names what is in force, each secret by its length only (telnyx public key set (44 chars)), then listening on 3000; voice webhook https://ivr.example.com/voice/telnyx. The server answers on the machine and through the tunnel:

    curl -s http://localhost:3000/health
curl -s https://ivr.example.com/health

    Both print {"ok":true,"sessions":0,"retained":0}: the calls live now, and the ended ones still held for a minute. /health says the process is up; /ready says whether it takes new calls ({"ready":true}, or 503 while it drains before a stop).

  2. Let pnpm diagnose check all of it, and more, one line each with its fix: the settings load, the hostname resolves and /health answers through the tunnel, the console is a 404 there, the carrier's secret has its shape, the model and its key variable, the handoff number is not a 555 number, the folders can be written with space to spare, the settings file is yours alone, and the clock is right against the carrier's (Telnyx refuses a webhook whose signature is more than five minutes off). It sends no key anywhere and calls no carrier or model API: its requests are to your own hostname, and one HEAD to the carrier's API host to read the time it answers with.

    PUBLIC_HOST=<words>.trycloudflare.com pnpm diagnose --app utility   # with a quick tunnel: the line pnpm start prints
ENV_FILE=~/ivr/myline.env pnpm diagnose --app myline                     # on a machine that stays on (section 7)

  3. Call your number. The server's output shows the webhook as the call arrives (/voice/telnyx ... from ...) and /cr-action/telnyx ... -> completed when it ends, with no signature rejected line.

  4. Watch calls in the console on the machine itself, http://localhost:3000/dashboard, or from your phone (section 10).

  5. Each call leaves two files in the traces folder: <call>.jsonl, its turns (what was heard, what the model answered, what the gate decided, how long each step took), and <call>.frames.jsonl, every frame in and out. The audit folder has one hash-chained file per UTC day; check the chains. Both folders are inside the app's folder until TRACE_DIR and AUDIT_DIR say otherwise (section 7):

    ls -lt apps/utility/traces | head
pnpm audit:verify apps/utility/audit

Then go deeper with the live checks: the Telnyx call that settles the adapter's assumptions, a restart mid-call, languages, a gateway for the model, a real identity provider for the chat, a quick tunnel, and the console from a phone.

7. A machine that stays on

Your laptop is fine for trying a real call. For a line that stays up, use anything that stays on: a Mac, a Linux mini PC, a spare desktop. It needs little: one Node process and a tunnel. The same commands run there; what changes is where the settings live, a tunnel whose hostname stays, and a service manager that keeps the server up (section 8).

Keep it on

  • macOS: in System Settings, Energy, turn on Prevent automatic sleeping when the display is off, Start up automatically after a power failure and Wake for network access. With FileVault on, a Mac that restarts after a power failure waits for a password before anything starts.
  • Linux: stop it suspending (sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target on a desktop install), and set the firmware to power on when power returns.
  • Both: let the clock set itself. Telnyx's signature is refused when the server's clock is more than five minutes off, and pnpm diagnose checks it.

Node and pnpm

The repository requires Node 22.19 or later (CI runs Node 22 and 24) and pnpm 9 (it pins pnpm@9.12.0 in package.json, which corepack follows). Install Node 24 from nodejs.org, your package manager or Homebrew (brew install node@24), then: 

corepack enable pnpm
node --version     # v22.19 or later
which node pnpm    # pnpm service puts these folders on the service's PATH

Then clone and install as in section 1, and run pnpm --version once inside the repository: corepack fetches pnpm 9.12.0 then, so the service never has to. If you will put the chat widget on a site, build it (pnpm --filter @dialogwright/widget build, again after each update).

The settings, outside the repository

This guide calls your app myline (pnpm create-app myline makes apps/myline); to follow along with a finished app, use utility in its place. Keep what is yours apart from the repository: the settings, the logs and the call data. Move the file pnpm configure wrote, and name it with ENV_FILE in front of each command from now on: 

mkdir -p ~/ivr/data/traces ~/ivr/data/audit
chmod 700 ~/ivr
mv apps/myline/.env ~/ivr/myline.env
chmod 600 ~/ivr/myline.env
ENV_FILE=~/ivr/myline.env pnpm diagnose --app myline

A variable already in the environment wins over the file. (--env-file <path> works too where pnpm passes it on, but some pnpm builds read a --env-file themselves, and fail on a relative path before the command starts, so ENV_FILE= is the form to use.) A tunnel whose hostname stays

A tunnel is an outbound connection from your machine to someone's edge; requests for its hostname come back down it, so your router needs no open port. The quick tunnel's hostname changes every run. For one that stays:

A named Cloudflare Tunnel keeps one hostname (ivr.example.com) for good. It needs a free Cloudflare account and a domain whose DNS is on Cloudflare. These are the steps for a locally managed tunnel, as Cloudflare's docs give them:

  1. Log in (it opens a browser; choose your domain) and create the tunnel. It prints the tunnel's id and writes its credentials to ~/.cloudflared/<id>.json.

    cloudflared tunnel login
cloudflared tunnel create myline

  2. Point your hostname at it (this adds the DNS record):

    cloudflared tunnel route dns myline ivr.example.com

  3. Write ~/.cloudflared/config.yml with your tunnel's id. The last rule, a catch-all, is required: anything not for your hostname is a 404 at Cloudflare.

    tunnel: 0b5e7c2a-5555-4f00-9d1e-123456789abc
credentials-file: /Users/alex/.cloudflared/0b5e7c2a-5555-4f00-9d1e-123456789abc.json

ingress:
  - hostname: ivr.example.com
    service: http://localhost:3000
  - service: http_status:404

  4. Check the rules and run it once in the foreground:

    cloudflared tunnel ingress validate
cloudflared tunnel run myline

  5. Run it as a service. cloudflared service install starts it at login from ~/.cloudflared/; sudo cloudflared service install starts it at boot and reads /etc/cloudflared/ (copy the config and the credentials file there, and fix credentials-file). On Linux, sudo cloudflared service install makes a systemd service.

    sudo cloudflared service install

When a tunnel drops a call's socket, the carrier calls /cr-action and the call reconnects, up to RECONNECT_LIMIT times (default 2), then goes to a person with an apology. That works because the server still holds the call. A restart of the server ends it, unless the call was saved (SESSION_STORE=file:) and the carrier's callback reaches the restarted server. Whichever tunnel you use, the server tells a tunnelled request from one made on the machine by the headers a proxy adds and by the Host it names, so the console stays off the internet.

With the named tunnel running as its own service and PUBLIC_HOST set to its hostname, point the carrier at https://ivr.example.com/voice/<carrier> once (section 5), and check it: 

ENV_FILE=~/ivr/myline.env pnpm start --app myline --tunnel named   # the server alone, to try it; Ctrl-C before section 8
ENV_FILE=~/ivr/myline.env pnpm diagnose --app myline               # in another terminal

8. Keeping it running

Hand the line to the system's service manager: it starts the server at login or boot, restarts it when it exits, and keeps its output. pnpm service writes the service file for this machine, with the absolute paths of the repository, pnpm, node and the settings file, and prints the commands that install it; it runs none of them. The service runs pnpm --filter <your app> serve from the repository with ENV_FILE naming ~/ivr/myline.env, so the server reads the same file pnpm start and pnpm diagnose read. Nothing from the file goes into the service file but its path, and it warns when others can read the file.

A stop sends SIGTERM to pnpm, which passes it to the server and waits. The server drains: /ready answers 503, a new call is put through to HANDOFF_NUMBER, a new chat is told it is busy, and live calls go on until they end or DRAIN_MS passes (30 seconds by default). What happens to a call still going then depends on where sessions are kept (section 9). The service gives a stop DRAIN_MS and ten seconds more before it kills anything. A second signal stops the server at once. A crash is logged with its stack and exits 1 after a short close, and the service manager starts it again.

macOS: a launchd agent

cd ~/dialogwright
ENV_FILE=~/ivr/myline.env pnpm service launchd --app myline --label com.example.myline

It writes ~/Library/LaunchAgents/com.example.myline.plist from this template, its values filled in:

and prints the commands that install, check and stop it:

mkdir -p ~/Library/Logs/com.example.myline
plutil -lint ~/Library/LaunchAgents/com.example.myline.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.example.myline.plist   # start now, and at every login
launchctl print gui/$(id -u)/com.example.myline | grep -E 'state|pid'             # running or not

launchctl kickstart -k gui/$(id -u)/com.example.myline                            # restart: live calls get DRAIN_MS to finish
launchctl bootout gui/$(id -u)/com.example.myline                                 # stop, and keep it stopped

An agent runs while you are logged in: turn on automatic login, or run it at boot as a daemon (copy the file to /Library/LaunchDaemons/, owned by root, add <key>UserName</key><string>alex</string>, and use sudo launchctl bootstrap system ... and system/com.example.myline). With KeepAlive on, killing the process only restarts it: bootout stops it.

Linux: a systemd user unit

cd ~/dialogwright
ENV_FILE=~/ivr/myline.env pnpm service systemd --app myline --label myline

It writes ~/.config/systemd/user/myline.service from this template:

and prints the commands below. A systemd user service runs only while you are logged in: systemd starts it at your first login and stops it when your last session ends, an ssh session too. For a line that starts at boot and stays up with no one logged in, turn on lingering for your user once, with loginctl enable-linger (some systems ask for sudo; loginctl show-user "$USER" --property=Linger says yes when it is on). 

systemctl --user daemon-reload
systemctl --user enable --now myline   # start now, and at every login
loginctl enable-linger "$USER"         # and at boot, with no one logged in (once)
systemctl --user status myline         # running or not
journalctl --user -u myline -f         # its output
systemctl --user restart myline        # restart: live calls get DRAIN_MS to finish
systemctl --user disable --now myline  # stop, and keep it stopped

A system unit works the same way: copy the file to /etc/systemd/system/, add User=alex under [Service], make it WantedBy=multi-user.target, and use sudo systemctl without --user (and without the linger).

On either system, a wrong setting shows as a restart every ten seconds, with the variable named in the output (missing required environment variable TELNYX_PUBLIC_KEY (VOICE_PROVIDERS includes telnyx)): run ENV_FILE=~/ivr/myline.env pnpm diagnose --app myline first.

9. Surviving a restart

A line that runs for months restarts: for an update, a reboot, now and then a crash. By default the server keeps calls in its memory, so a restart ends the calls under way (after the drain, the stopping server puts each one through to HANDOFF_NUMBER). With SESSION_STORE=file:<folder>, as in the settings above, it saves each call after every turn, and a restart no longer drops a caller.

What is saved
Each live call (what the caller has said so far, where they are in the form), each web chat, and the carrier's one-time relay tokens, kept only as hashes, in a folder only you can read (mode 700, each file 600, every save written whole and renamed into place). It holds what callers said, like the traces: keep it on this machine, on a disk that outlives a reboot (not /tmp; pnpm diagnose checks). One server per folder.
What the caller hears
When the carrier calls back for the call, the restarted server loads it, and the caller hears "Sorry, I lost you for a moment." (an app can say it its own way: the resumed line) and the question they were on, with what they had said still there. The trace and the audit chain go on in the same files. A call saved by a version whose session shape differs is not resumed: that caller is put through to a person.
A planned restart
An update or a launchctl kickstart -k / systemctl --user restart. A call still going after DRAIN_MS is handed over: the server closes its socket, answers the carrier's callback with "wait RESTART_PAUSE_S seconds, then connect again" (5 by default), stops listening and exits; the service starts the server again, and the carrier's connection, a few seconds later, reaches it. The caller hears a few seconds of silence, then the resumed line. Set RESTART_PAUSE_S a little above how long your server takes to stop and start (the log's listening on line says when it is back).
A crash, a reboot, a power cut
Nothing is handed over. The carrier calls back the moment the socket drops, usually before a server is listening again, and then turns to the number's fallback (below), which puts the caller through to you. A callback that comes after the restarted server is up resumes the call. A save is renamed into place whole, so a crash loses nothing; a power cut may lose the last few seconds, unless SESSION_FSYNC=on flushes every save to the disk (for a machine with no battery or UPS).
A write is never done twice
A call that resumes may run a write again (a report filed just before the crash, confirmed again after it). Each write carries a key that is the same for the same confirmed write, which your systems use to answer a repeat with what they did the first time (how a tool uses it).

When the server is down: the carrier's fallback

A carrier turns to a number's fallback when it cannot reach your server at all: a call that comes in while it is down, or a live call's callback that comes before a restarted server is listening. pnpm fallback writes the document: an apology and a dial to HANDOFF_NUMBER. Host the file anywhere that stays up when your machine does not (a static page on GitHub Pages or Cloudflare Pages, object storage) and paste its URL where the command says. Set it once per number: with it, a caller reaches a person whenever the server cannot answer; without it, they hear the carrier's own error. 

pnpm fallback --provider telnyx --number +15555550123 --out fallback.xml
# Telnyx: the TeXML application's fallback URL. Twilio (--provider twilio): the number's "Primary handler fails" URL.

That a carrier uses its fallback for a failed callback mid-call (and not only for a call that comes in), and takes the pause before it connects again, is read from the carriers' references and not yet shown on a live call: live check 3.

10. Looking at calls from your phone

The console shows each call as it happens, with what the caller said, so by default it answers only on the machine (http://localhost:3000/dashboard; from another computer, forward the port: ssh -L 3000:localhost:3000 alex@homebox.local). To watch from your phone through the tunnel, add CONSOLE_AUTH=token to the settings file and restart the server. The console then asks for a sign-in: a link that works once, for ten minutes. The server writes one when it starts, to a file only you can read (its log names the file, never the link); for a new one, on the machine: 

cd ~/dialogwright && ENV_FILE=~/ivr/myline.env pnpm console:link --app myline

It prints https://ivr.example.com/dashboard/login?code=.... Send it to your phone (a note to yourself, say), open it, and press Sign in (a link preview only fetches the page, so it never uses the link up). The phone stays signed in for twelve hours (CONSOLE_SESSION_HOURS), or until you press Sign out in the console's header, and the console fits the phone's screen. Each new link retires the one before it. A restart signs everyone out unless CONSOLE_SESSION_KEY is set (32 random bytes or more: openssl rand -hex 32); with it, a sign-out is kept on disk and still holds after a restart. Without a sign-in, https://ivr.example.com/dashboard shows only the sign-in page, and pnpm diagnose checks that it does.

Every sign-in, every refused attempt, the first look at the live feed and every replay of a stored call go into the audit, as console_access entries naming the session by a hash and never the link: the record of who looked at which call. Failed attempts are limited per address and in all. The address is the one your tunnel reports: with Cloudflare's tunnel, as here, CONSOLE_CLIENT_ADDRESS=cf-connecting-ip reads only Cloudflare's header (the default, auto, reads it first too); behind ngrok or another proxy, set x-forwarded-for. Your app's own pages that are local only (its chats) stay local only. Treat a sign-in link like a key: it opens every call for whoever uses it first.

11. Updating, the disk, backups, security

Updating

DialogWright is pre-release and its APIs change, so update on purpose, and note the commit you last ran well (git rev-parse --short HEAD) so you can go back. The restart drains and, with the file store, hands each call still going over to the restarted server (section 9); with the memory store, check /health says "sessions":0 first. 

cd ~/dialogwright
git pull
pnpm install
pnpm check
pnpm --filter @dialogwright/example-myline test
pnpm --filter @dialogwright/widget build     # if you serve the widget
ENV_FILE=~/ivr/myline.env pnpm diagnose --app myline
systemctl --user restart myline              # or: launchctl kickstart -k gui/$(id -u)/com.example.myline

Update the operating system, Node and cloudflared on the same quiet occasions.

Keeping the disk in check

Unless you say otherwise, nothing deletes old traces: two files per call, kept until you remove them. TRACE_RETENTION_DAYS=90 removes traces and frame logs last written more than 90 days ago, swept at startup and once an hour, never a live call's; /health then reports disk (traceBytes, auditBytes) for a monitor. AUDIT_RETENTION_DAYS does the same for audit days, which ends the record for those days (never today's): keep them as long as you must keep the record. The traces are what pnpm kb:gaps reads to find the questions your knowledge base did not answer, so archive them before they go. The sessions folder needs no sweep: it holds only the calls under way. Check the audit's hash chains with pnpm audit:verify ~/ivr/data/audit.

Backing up

What is yours and not in git: ~/ivr/myline.env (your keys: back it up only somewhere encrypted), the traces and audit folders, and ~/.cloudflared/ (a named tunnel's credentials). The sessions folder needs no backup. The audit files are append-only and chained: copy them, never edit them, since an edit breaks every later link.

What to watch

  • The output. Errors and restarts show there first.
  • Slow turns. Each trace record carries its timing (timing.askMs, timing.totalMs). A model request slower than JEV_TIMEOUT_MS plays the slow-turn line and keeps the question open.
  • The carrier's own logs (Telnyx's webhook debugging, Twilio's call logs) when a call never reached you.

Security

  • Keys only in the settings file, mode 600, outside the repository: never in the unit, the plist, a script you commit, or a message. The server and the commands print a secret's length, never its value.
  • Signature checks on (SIGNATURE_CHECK=on, the default).
  • The console local-only (CONSOLE_LOCAL_ONLY=on, the default): reach it from elsewhere with CONSOLE_AUTH=token's sign-in or over SSH, never by turning this off.
  • No port opened on the router. The tunnel connects out. Turn on the machine's firewall: the server needs no incoming connection from the network, only from cloudflared on the same machine.
  • The traces hold what callers said, and so does the sessions folder while a call is live. Treat the data folder as personal data, kept on this machine and in encrypted backups.
  • Keep the machine updated.
  • Building a line for a small business (a law office's, say)? Its callers are the business's clients: ask what it must keep, for how long, and who may read it, before the first call.

12. By hand, without the commands

The commands above only write files and run processes you could write and run yourself. When one does not fit (a machine where you would rather not run a wizard, a tunnel pnpm start does not know), these are the same steps by hand.

A settings file

Write it from this example (the values are made up), mode 600, and name it with ENV_FILE. The variables, their defaults and their checks are the server's own (packages/dialogwright/src/server/config.ts). 

chmod 600 ~/ivr/myline.env
PUBLIC_HOST
Your tunnel's hostname. The server builds every URL it gives the carrier from it, and checks Twilio's signature against https://<PUBLIC_HOST><path>, so it must be exactly the hostname the carrier calls.
VOICE_PROVIDERS and the carrier's secret
Each carrier listed needs its secret: TELNYX_PUBLIC_KEY (refused at startup unless it is a base64 Ed25519 key), TWILIO_AUTH_TOKEN.
SIGNATURE_CHECK=on
A webhook the carrier did not sign is refused. off exists only for posting webhooks by hand on a laptop.
JEV_CLIENT, JEV_PROVIDER and the key
Without JEV_CLIENT=jev the server runs on the stub. Once it is jev, the provider's key variable is required (for custom, JEV_BASE_URL and JEV_MODEL are).
WIDGET_FILE
The default is the widget in your app's own node_modules, which a new app does not have (the utility does); name the built file instead.

A quick tunnel, and the server

pnpm start --tunnel quick is these two, in two terminals: the tunnel, which prints a random https://<words>.trycloudflare.com address, and the server with that hostname (without https://) as its PUBLIC_HOST: 

cloudflared tunnel --url http://localhost:3000
cd ~/dialogwright
PUBLIC_HOST=<words>.trycloudflare.com ENV_FILE=~/ivr/myline.env pnpm --filter @dialogwright/example-myline serve

Stop the server first and the tunnel after it, so live calls keep their way in while they drain. Any other tunnel works the same way: it gives you a hostname for PUBLIC_HOST and forwards to the server's port.

Checking by hand

pnpm diagnose runs these and more; by hand, the server answers on the machine and through the tunnel, and the console is not public: 

curl -s http://localhost:3000/health
curl -s https://ivr.example.com/health
curl -s http://localhost:3000/ready
curl -s -o /dev/null -w '%{http_code}\n' https://ivr.example.com/dashboard   # 404, or 302 to the sign-in with CONSOLE_AUTH=token

13. What is coming

Everything on this page is built: one machine, run for months. When one machine is no longer enough (a deploy that must never drop a call, more calls than one machine answers), the same app folder is designed to run on many servers: the session stores this page uses sit behind interfaces with one contract suite, so a store many servers share is a drop-in, beside a shared audit, traces in object storage and a console with roles. That is Phase 8b, designed and not built yet.
