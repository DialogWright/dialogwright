Guides / Scaling out

Scaling out

The same app folder, the same policy and the same audit, on many servers behind a load balancer: for a business whose line must survive a deploy, a crashed instance and a busy Monday.

A design, not built yet. This is how DialogWright is designed to scale, for Phase 8 of the roadmap and later. Today it runs as one process, with its sessions in memory. Where this page names a setting or a command that does not exist yet, it says so.

One server is the right answer for most people. A single process answers a personal line or a small office's without strain; run it on a machine you own. Scale out when you need a deploy that never drops a call, or more than one machine's worth of calls.

1. What one process holds today

The design's principle is that the agent failing never means dead air: a turn that fails is asked again and then handed to a person; an instance that dies mid-call is replaced by another that resumes the call; a whole service that is down is answered by the carrier's fallback URL, static markup from somewhere independent that apologizes and dials the human queue. The single-process version of the middle one exists today: when a call's socket drops, the carrier calls /cr-action, and the same process reconnects the call with a fresh one-time token, up to RECONNECT_LIMIT times, then transfers it politely. What it cannot do is resume a call another process held.

Everything a call needs lives in the server's memory or on its disk, by design: laptop mode is first-class, and every production piece is to arrive as an interface whose default is the laptop implementation. The table in section 3 names each piece and where it is in the code.

2. The reference shape

  • Containers, one codebase in separate deploys by role. Voice and chat are public; the console is internal only.
  • A load balancer that carries WebSockets, with an idle timeout longer than the longest call, and no sticky sessions. Carrier webhooks are stateless HTTP.
  • Shared stores: sessions in Redis; the audit log in Postgres; traces in object storage; console events over Redis pub/sub. Each is to be chosen by configuration, one at a time (the design's example is SESSION_STORE=redis://..., a variable that does not exist yet).
  • A starter setup on a container platform with WebSockets: two instances, managed Redis and Postgres. Production on containers across availability zones. A second region later, as the carrier's fallback target.
  • For regulated data, services covered by the agreements your sector requires, encryption at rest, retention policies and in-region data.
  • Locally, the design has pnpm dev:stack bring up Redis, Postgres and an object-storage stand-in with docker compose, two instances behind a local load balancer, where the kill-an-instance test runs (planned).

3. What has to be shared

Each piece of state one process keeps today, and what it needs when there are many:

StateToday (in the code)Across instances
Call sessions, and each call's queue of turns A map in memory (SessionStore, server/sessions.ts): each call's session, its turn chain (tail, so turns run one at a time) and the turns in flight. Idle ones are evicted after SESSION_TTL_MS. The core already returns a new serializable session each turn. It is saved after every turn, keyed by call or chat id, with a time-to-live and a schema version (a resume onto an incompatible version hands off politely). One instance must own a call's turns at a time: a lock or lease per call id in the store.
One-time socket tokens A map in memory (CallTokens, server/tokens.ts): one per call, 10 minutes, tied to the call and to the carrier that minted it. Shared, with the same expiry, and still single-use: the instance that takes the socket must recognise a token another instance minted.
The reconnect counter A field of the call's entry (reconnects), checked against RECONNECT_LIMIT. Part of the shared session, incremented atomically, or two instances could each grant the last reconnect.
Chat sessions and resume tokens Maps in memory (server/chat/socket.ts); a fresh resume token with every ready. CHAT_MAX_SESSIONS counts this process's chats. Shared, so a resume reaches any instance (section 5). The limit becomes per instance, or moves to the store.
The audit chain One hash chain per UTC day file in AUDIT_DIR (audit/log.ts), continued from the file's last line when the process starts. Two processes appending to one day file would fork the chain. The design: Postgres, a hash chain per session, each session's final hash anchored into a daily chain.
Traces and frame logs Two JSONL files per call in TRACE_DIR. Object storage. A call that moves instance mid-call must continue one trace, not start a second.
Console events An in-process bus (DashboardBus). Redis pub/sub, so the console sees every instance's calls.
The knowledge base's index A committed file in the app folder (kb/.index), read at start. Read-only, so it ships in the image and every instance reads its own copy. pgvector is planned behind the same VectorIndex interface for production.

4. A call's WebSocket

A phone call touches the server in three steps, and with several instances each can land on a different one:

  1. The carrier posts the voice webhook (/voice/<carrier>). The instance that answers mints a one-time token and answers with a start document that names the socket's URL, with the token in its query.
  2. The carrier opens the WebSocket (/conversation/<carrier>?token=...). The token is checked at the upgrade; the call id arrives only afterwards, in the setup frame. The whole call then runs on this one socket, on whichever instance accepted it.
  3. If the socket drops (an instance dies, a deploy closes it, a network blip), the carrier posts the action callback (/cr-action/<carrier>) with the call id, and the answer is a new start document with a new token. The reconnected socket may land anywhere.

There are two ways to make that work:

The session in a shared store (the design's choice)
Any instance can take any step: it reads the token, the counter and the session from the store, and the call resumes ("Sorry, I lost you for a moment"). The load balancer needs no affinity. This is what Phase 8 builds.
Route by call id
Keep state in memory and have the load balancer send every step of a call to the instance that holds it. Today the socket's URL carries only the token, so a balancer cannot see the call id at the upgrade; it would need the call id, or a key derived from it, in the URL. And it saves nothing when the instance holding the call is the one that died, which is the case that matters.

A call is a long-lived socket. The load balancer's idle timeout must be longer than any call (the server ends a session it has held for SESSION_MAX_AGE_MS, two hours by default), and the carrier's own reconnect limit still applies.

5. Web chat across instances

A chat outlives its socket: the client reconnects with the resume token from the last ready and carries on, until CHAT_IDLE_MS of quiet ends it. Today the session is in the memory of the instance that started it, so a resume reaches only that instance. Across instances, the session and its resume token live in the shared store, a resume rotates the token there, and a resume that takes a chat over must close the old socket on whichever instance holds it (over the same pub/sub the console uses). The widget needs no change: it already reconnects and resumes with backoff.

6. Idempotent writes

When an instance dies after a tool started a write (booking an appointment, filing a report) but before the session recorded it, the call resumes elsewhere and the turn may run again. So every write tool gets a key derived from the session (the call id, the form, a hash of the confirmed values): a retry with the same key never acts twice. In-flight effects are recorded in the session and re-issued with the same key. The tool context is to provide timeouts, retries with those keys, a circuit breaker and caching, declared per tool. Your own systems must honour the key; the engine can only send it.

7. Readiness and drain

Today, on SIGTERM or SIGINT the server stops its sweeps, waits for turns already in flight (up to two seconds), closes every socket and exits (server/index.ts). /health answers {"ok":true,"sessions":N,"retained":M} whenever the process is up; there is no separate readiness.

The design for a rolling deploy: new instances report ready before they take traffic; old ones stop taking new calls and keep serving the ones they have; after a drain limit (about 15 minutes) they close the remaining sockets, and those calls reconnect to the new version from the shared session. The test that proves it is the kill-an-instance test: a deploy never drops a call.

8. The console behind single sign-on

On one machine the console is kept off the internet by CONSOLE_LOCAL_ONLY, or opened to its one owner through the tunnel by CONSOLE_AUTH=token's one-time sign-in link, with each sign-in and replay in the audit. Across instances it becomes its own role (--role console), internal only, behind single sign-on or a VPN, reading the shared stores. The design adds roles (viewer, supervisor, admin) to the sign-in, and the access log of who replayed which call goes to the shared audit store.

9. Secrets

The server takes every secret from its environment, and prints only each one's length. Give each role only the secrets it uses, from your platform's secrets manager, never baked into an image:

  • voice: the carriers' (TWILIO_AUTH_TOKEN, TELNYX_PUBLIC_KEY) and the model's (TYPESAFE_API_KEY, or the gateway's);
  • chat: the model's; its sign-in settings (CHAT_JWKS_URL, CHAT_ISSUER, CHAT_AUDIENCE) are configuration, not secrets;
  • both, if you use the handoff note: ANTHROPIC_API_KEY;
  • the stores' credentials, to the roles that reach them.

Rotate a key by rolling the instances, which the drain above makes safe.

10. Observability

The data to ship already exists, in two formats with stable fields:

Traces (one JSON record per turn, v: 2)
The session and turn, the event, the questions and the model's answers, the gate's rows and the decision, the actions, the slots, timing (retrieveMs, planMs, askMs, resolveMs, totalMs), usage (tokens and costUsd), the config hash and, on the first record, which model answered. They hold what callers said: ship them to storage you treat as personal data.
The audit (one JSON entry per decision)
seq, at, callId, channel, type (call_started, identity, gate, tool_result, handoff, call_ended, ...), a minimized detail, and prevHash and hash. Minimized by design: ids by their last four, never a date of birth or a code.

The design adds OpenTelemetry metrics and traces, logs that carry ids and never personal data, and alerts on fallback hits, handoffs for system failure, the reconnect rate and turn latency, plus a stable event stream derived from the audit for business reporting.

11. The decision model's limits

Every instance asks the same model account, so its rate limits are shared by all of them: size them against your busiest hour, with the provider. Each request has a budget, JEV_TIMEOUT_MS (1500 ms by default); the client retries once within it, so a caller waits up to twice that on a turn the model never answers, then hears the slow-turn line with the question still open. A turn that fails is asked again, then handed to a person. A per-instance cap on requests in flight, so that a surge queues rather than trips the provider's limit, belongs with Phase 8's resilient tools.

12. The roadmap

Phase 8, production: store interfaces with production implementations, resume across instances, idempotent writes, readiness and drain, a docker compose stack, a reference deployment and console access control, proved by the kill-an-instance test. Laptop mode stays first-class throughout: the same code runs in both modes, and contract tests keep the implementations honest.
