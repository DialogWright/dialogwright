Guides / Scaling out

Scaling out

The same app folder, the same policy and the same audit, on many servers behind a load balancer: for a business whose line must survive a deploy, a crashed instance and a busy Monday.

Part built, part designed. DialogWright runs as one process on one machine, and the seams many servers need are built into it: the session stores sit behind interfaces with one contract suite, a session is versioned and resumes on a restarted server, writes carry idempotency keys, the server says when it is ready and drains before it stops, and the console has a sign-in. Running on many servers on top of those seams is Phase 8b of the roadmap, designed and not built yet. Each section below says which is which, and where this page names a setting or a command that does not exist yet, it says so.

One server is the right answer for most people. A single process answers a personal line or a small office's without strain; run it on a machine you own. Scale out when you need a deploy that never drops a call, or more than one machine's worth of calls.

1. What one machine holds today

The design's principle is that the agent failing never means dead air: a turn that fails is asked again and then handed to a person; an instance that dies mid-call is replaced by another that resumes the call; a whole service that is down is answered by the carrier's fallback URL, static markup from somewhere independent that apologizes and dials the human queue. The one-machine version of the middle one exists today: when a call's socket drops, the carrier calls /cr-action, and the server reconnects the call with a fresh one-time token, up to RECONNECT_LIMIT times, then transfers it politely. With SESSION_STORE=file:<dir> the call is saved after every turn, so a restarted server on the same machine resumes it; a planned restart hands each call over to the server that starts next, and the carrier's fallback (pnpm fallback) catches a callback that finds no server. What it cannot do yet is resume a call on another machine: that needs a store they share.

Everything a call needs lives in the server's memory or on its disk, by design: laptop mode is first-class, and every production piece arrives as an interface whose default is the laptop implementation. The session stores already have theirs (CallStateStore, ChatStateStore and TokenStore, with memory and file implementations), and one contract suite, runStoreContract, that a shared store must pass unchanged. The table in section 3 names each piece and where it is in the code.

2. The reference shape

  • Containers, one codebase in separate deploys by role. Voice and chat are public; the console is internal only.
  • A load balancer that carries WebSockets, with an idle timeout longer than the longest call, and no sticky sessions. Carrier webhooks are stateless HTTP.
  • Shared stores: sessions in Redis; the audit log in Postgres; traces in object storage; console events over Redis pub/sub. Each is to be chosen by configuration, one at a time: SESSION_STORE exists and takes memory or file:<dir> today; a shared value such as redis://... is Phase 8b's.
  • A starter setup on a container platform with WebSockets: two instances, managed Redis and Postgres. Production on containers across availability zones. A second region later, as the carrier's fallback target.
  • For regulated data, services covered by the agreements your sector requires, encryption at rest, retention policies and in-region data.
  • Locally, the design has pnpm dev:stack bring up Redis, Postgres and an object-storage stand-in with docker compose, two instances behind a local load balancer, where the kill-an-instance test runs (planned, Phase 8b). Its one-machine version runs today: server/restart.e2e.test.ts kills the server mid-call and resumes the call on a new process.

3. What has to be shared

Each piece of state one machine keeps today, and what it needs when there are many:

StateToday (in the code)Across instances
Call sessions, and each call's queue of turns The live part in memory (SessionStore, server/sessions.ts): each call's socket, its turn chain (tail, so turns run one at a time) and the turns in flight. With SESSION_STORE=file: the session is saved after every turn (CallStateStore, server/stores/) with its SESSION_SCHEMA, and a restarted server loads it (a resume onto another schema hands off politely). The same CallStateStore, shared, passing the same contract suite, so any instance loads any call. One instance must own a call's turns at a time: a lock or lease per call id in the store.
One-time socket tokens A TokenStore (CallTokens in memory, or tokens.json with the file store), kept only as SHA-256: one per call, 10 minutes, tied to the call and to the carrier that minted it. Shared, with the same expiry, and still single-use: the instance that takes the socket must recognise a token another instance minted. The server calls its token store synchronously today; a networked one needs those calls awaited.
The reconnect counter A field of the call's entry (reconnects), saved with the call, checked against RECONNECT_LIMIT. Part of the shared session, incremented atomically, or two instances could each grant the last reconnect.
Chat sessions and resume tokens In memory (server/chat/socket.ts), and with the file store saved as a ChatStateStore record found by its resume token's hash; a fresh resume token with every ready. CHAT_MAX_SESSIONS counts this process's chats. Shared, so a resume reaches any instance (section 5). The limit becomes per instance, or moves to the store.
The audit chain One hash chain per UTC day file in AUDIT_DIR (audit/log.ts), continued from the file's last line when the process starts. Two processes appending to one day file would fork the chain. The design: Postgres, a hash chain per session, each session's final hash anchored into a daily chain.
Traces and frame logs Two JSONL files per call in TRACE_DIR. Object storage. A call that moves instance mid-call must continue one trace, not start a second.
Console events An in-process bus (DashboardBus). Redis pub/sub, so the console sees every instance's calls.
The knowledge base's index A committed file in the app folder (kb/.index), read at start. Read-only, so it ships in the image and every instance reads its own copy. pgvector behind the same VectorIndex interface is a candidate for production, beside the Postgres audit.

4. A call's WebSocket

A phone call touches the server in three steps, and with several instances each can land on a different one:

  1. The carrier posts the voice webhook (/voice/<carrier>). The instance that answers mints a one-time token and answers with a start document that names the socket's URL, with the token in its query.
  2. The carrier opens the WebSocket (/conversation/<carrier>?token=...). The token is checked at the upgrade; the call id arrives only afterwards, in the setup frame. The whole call then runs on this one socket, on whichever instance accepted it.
  3. If the socket drops (an instance dies, a deploy closes it, a network blip), the carrier posts the action callback (/cr-action/<carrier>) with the call id, and the answer is a new start document with a new token. The reconnected socket may land anywhere.

There are two ways to make that work:

The session in a shared store (the design's choice)
Any instance can take any step: it reads the token, the counter and the session from the store, and the call resumes ("Sorry, I lost you for a moment"). The load balancer needs no affinity. On one machine this is built: a restarted server loads the call from the file store. Across instances it needs Phase 8b's shared store.
Route by call id
Keep state in memory and have the load balancer send every step of a call to the instance that holds it. Today the socket's URL carries only the token, so a balancer cannot see the call id at the upgrade; it would need the call id, or a key derived from it, in the URL. And it saves nothing when the instance holding the call is the one that died, which is the case that matters.

A call is a long-lived socket. The load balancer's idle timeout must be longer than any call (the server ends a session it has held for SESSION_MAX_AGE_MS, two hours by default), and the carrier's own reconnect limit still applies.

5. Web chat across instances

A chat outlives its socket: the client reconnects with the resume token from the last ready and carries on, until CHAT_IDLE_MS of quiet ends it. Today the session lives on the machine that started it (and, with the file store, survives that server's restart), so a resume reaches only that machine. Across instances, the session and its resume token live in the shared store, a resume rotates the token there, and a resume that takes a chat over must close the old socket on whichever instance holds it (over the same pub/sub the console uses). The widget needs no change: it already reconnects and resumes with backoff.

6. Idempotent writes

When an instance dies after a tool started a write (booking an appointment, filing a report) but before the session recorded it, the call resumes elsewhere and the turn may run again. So every write tool gets a key derived from the session (the call id, the form, a hash of the confirmed values): a retry with the same key never acts twice. In-flight effects are recorded in the session and re-issued with the same key. Built: a tool that declares idempotent: true gets ctx.idempotencyKey, the same for the same confirmed write; a downstream service request always carries a key, recorded in the call before it is sent and sent again once, with the same key, by a server that resumes a call waiting on it. Still to come: timeouts, retries with those keys, a circuit breaker and caching, declared per tool. Your own systems must honour the key; the engine can only send it.

7. Readiness and drain

Built for one machine: /ready answers 503 once the server stops taking new calls, while /health stays liveness. On SIGTERM or SIGINT it drains for DRAIN_MS (30 seconds by default): a new call goes to the handoff number, a new chat is told it is busy, and live calls go on. With the file store, a call still live at the end is handed over: its carrier is told to wait RESTART_PAUSE_S seconds and connect again, and the stopping server refuses sockets until it exits, so the connection reaches the server that starts next.

The design for a rolling deploy: new instances report ready before they take traffic; old ones stop taking new calls and keep serving the ones they have; after a drain limit (about 15 minutes) they close the remaining sockets, and those calls reconnect to the new version from the shared session (Phase 8b). The test that proves it is the kill-an-instance test: a deploy never drops a call.

8. The console behind single sign-on

Built for one machine: the console is kept off the internet by CONSOLE_LOCAL_ONLY, or opened to its one owner through the tunnel by CONSOLE_AUTH=token's one-time sign-in link (an HMAC-signed session cookie, rate-limited sign-ins, a strict Content-Security-Policy), with each sign-in and replay in the audit. Across instances it becomes its own role (--role console), internal only, behind single sign-on or a VPN, reading the shared stores. The design adds roles (viewer, supervisor, admin) to the sign-in, and the access log of who replayed which call goes to the shared audit store.

9. Secrets

The server takes every secret from its environment, and prints only each one's length. Give each role only the secrets it uses, from your platform's secrets manager, never baked into an image:

  • voice: the carriers' (TWILIO_AUTH_TOKEN, TELNYX_PUBLIC_KEY) and the model's (TYPESAFE_API_KEY, or the gateway's);
  • chat: the model's; its sign-in settings (CHAT_JWKS_URL, CHAT_ISSUER, CHAT_AUDIENCE) are configuration, not secrets;
  • both, if you use the handoff note: ANTHROPIC_API_KEY;
  • the stores' credentials, to the roles that reach them.

Rotate a key by rolling the instances, which the drain above makes safe.

10. Observability

The data to ship already exists, in two formats with stable fields:

Traces (one JSON record per turn, v: 2)
The session and turn, the event, the questions and the model's answers, the gate's rows and the decision, the actions, the slots, timing (retrieveMs, planMs, askMs, resolveMs, totalMs), usage (tokens and costUsd), the config hash and, on the first record, which model answered. They hold what callers said: ship them to storage you treat as personal data.
The audit (one JSON entry per decision)
seq, at, callId, channel, type (call_started, identity, gate, tool_result, handoff, call_ended, ...), a minimized detail, and prevHash and hash. Minimized by design: ids by their last four, never a date of birth or a code.

The design adds OpenTelemetry metrics and traces, logs that carry ids and never personal data, and alerts on fallback hits, handoffs for system failure, the reconnect rate and turn latency, plus a stable event stream derived from the audit for business reporting.

11. The decision model's limits

Every instance asks the same model account, so its rate limits are shared by all of them: size them against your busiest hour, with the provider. Each request has a budget, JEV_TIMEOUT_MS (1500 ms by default); the client retries once within it, so a caller waits up to twice that on a turn the model never answers, then hears the slow-turn line with the question still open. A turn that fails is asked again, then handed to a person. A per-instance cap on requests in flight, so that a surge queues rather than trips the provider's limit, belongs with the resilient tools (design §11), not built yet.

12. The roadmap

Phase 8, local-first on a machine you own, is done: the store interfaces and their contract suite, a file store, resume after a restart, idempotent writes, readiness and drain, retention, service files, carrier fallback documents and console sign-in, proved by the kill-the-server test. Phase 8b, many servers, is planned: shared stores passing the same contract suite, the audit in Postgres, traces in object storage, console events over pub/sub, --role, a container image and a docker compose stack where the kill-an-instance test runs, and console roles with single sign-on. Laptop mode stays first-class throughout: the same code runs in every mode, and the contract suite keeps the implementations honest.
