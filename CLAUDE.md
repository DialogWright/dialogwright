# DialogWright: notes for AI coding assistants

DialogWright is a TypeScript framework for voice and chat agents that understand people and act safely: understanding is flexible (a decision model perceives through typed questions, so a caller talks naturally), while what is said and done is predictable (fixed lines, code that decides, a policy gate) and replies are fast. Read this before changing anything.

## The three roles

1. **The perceiver.** A fast decision model reads what the caller said and answers typed questions: yes or no, which of these options, what value was given. It returns judgments, not generated text.
2. **The core.** Deterministic code owns the dialog and the form-filling. It decides what happens next from the model's judgments and the current state.
3. **The gate.** Every action goes through a policy gate that checks identity level, scope, confirmation and attempt limits. Every decision, allowed or refused, is written to a hash-chained audit log.

Apps are defined against the `App` contract and plug into the engine. The engine knows nothing about any particular app.

An app is a folder: YAML for what is data (intents, forms, prompts, policy, identity, locales), TypeScript for what runs (slots, tools, form hooks, custom rules), joined by `defineApp`. To build or change one, read the authoring guide first, [docs/guide/](docs/guide/README.md), a chapter at a time: one file per section, and its README is the contents.

To start a new app, run `pnpm create-app <name>` (add `--identity` for one that verifies callers): it writes a small app under `apps/<name>` that passes `pnpm check`, its tests and its stub regression as created, with its own `CLAUDE.md`. To build an app from a description (a paragraph of what callers can do), follow the create-app skill, [.claude/skills/create-app/SKILL.md](.claude/skills/create-app/SKILL.md): a worksheet, the mapping onto slot types, policy and identity, the scaffold, the corpus and scenarios, and the checks until green. [docs/first-app.md](docs/first-app.md) walks a person through that with a paragraph to start from. Each app has its own `CLAUDE.md`: read it before changing that app.

## Layout

- `packages/dialogwright`: the engine. Its `testkit` is the engine's own test fixture, not a template for apps.
- `packages/dialogwright/schemas/*.schema.json`: the JSON Schemas of the app folder's YAML files. They are generated from the zod schemas in `packages/dialogwright/src/define/schema/`; never edit them by hand. Run `pnpm --filter dialogwright schemas` after changing a zod schema (a test fails when they are stale).
- `packages/dialogwright/src/slots/`: the slot library, one folder per slot type (options schema, questions, fill, display, tests, examples, README). `docs/slots/*.md` are generated from it; never edit them by hand.
- `packages/dialogwright/src/kb/`: the knowledge base in the engine (the `kb/` folder's reading and rules, resolution, approval and staleness, the knowledge record, the retrievers: keyword, dense, hybrid, the static embedder and its pinned model, the index, the bake-off, the optional ONNX adapter, speaking an answer, and the gaps in the traces, `kb/gaps.ts`: what `kb:gaps` ranks and the console's Insights and Knowledge pages count). An app's own `kb/` folder (kb.yaml, topics.yaml, passages, sources, locale, pending, rejected, approvals.jsonl, .index) is data: [section 12 of the guide](docs/guide/12-the-knowledge-base.md).
- `packages/kb-author`: `@dialogwright/kb-author`, the knowledge base's authoring tools (`pnpm kb:ingest`: documents and websites into `kb/sources`; `kb:draft`: drafts into `kb/pending`; `kb:review`: the local review page; `kb:refresh`: the sources read again; `kb:gaps`: what callers asked that the knowledge base did not answer, ranked from the traces). Authoring only: an app never imports it, and its dependencies stay out of the engine. Drafting calls a model with the author's own key, on their machine: never in CI or a test.
- `packages/create-dialogwright`: the thin package `npm create dialogwright@latest <name>` runs; it hands its arguments to the installed engine's `dialogwright create-app <name> --standalone`, which writes a project of its own from `packages/dialogwright/templates/` (`standalone/` replaces the files that name this repository) with the create-app skill copied in.
- `scripts/`: `build-package.mjs` (each package's `build`: the compiler into `dist/` from the entries `tsconfig.build.json` names, real specifiers made ones Node resolves by `build/specifiers.mjs`, the files git tracks under `src/` copied), `publish-guard.mjs` (each package's `prepack` and `prepublishOnly`: pnpm only, a fresh build, nothing git ignores) `adopt-test.mjs` (`pnpm adopt:test`) and `relink-guide.mjs` (moves a link to the guide's old page, `docs/authoring-an-app.md#<anchor>`, to its chapter; it finds nothing to move, and a test holds that). The packages' `package.json` files point at `src/` for this workspace; their `publishConfig` points a packed package at `dist/`. [RELEASING.md](RELEASING.md) is the maintainer's release.
- `packages/widget`: `@dialogwright/widget`, the web chat widget a site embeds (a script with no runtime dependencies that speaks only the chat wire, `src/channel/chat/protocol.ts`). It never imports the engine at run time; the engine's web chat, its carriers and every channel option are [section 13 of the guide](docs/guide/13-channels.md).
- `packages/dialogwright/src/render/`: generated wording (opt-in, [section 16 of the guide](docs/guide/16-generated-wording.md)): which lines an app generates (`config.ts`), the speech act a model is sent and the checks every generated line passes before anyone hears it (`checks.ts`), the turn's rendering after the core has decided (`turn.ts`), the OpenRouter and Anthropic adapters (`providers.ts`, by fetch, with the author's own key), the render cassette and the fake renderer the tests use.
- `packages/dialogwright/src/server/`: the server an app runs on (`pnpm --filter <app> serve`), and the root commands for running it on a machine you own (`setup.ts` is `pnpm configure`, `start.ts`, `doctor.ts` is `pnpm diagnose`, `serviceFile.ts`, `fallback.ts`, `console/linkCli.ts`; the service templates are in `packages/dialogwright/templates/service/`). `server/stores/` holds the session store interfaces (`types.ts`, with `CallLeases`: one owner per call) and their memory, file and Postgres implementations (`postgres.ts` over the thin SQL client in `sql.ts`; the engine's tests run it on PGlite through `pgliteSql.ts`, so nothing is installed), each held to `runStoreContract` (`dialogwright/testing`), and `notices.ts`, the notices between the servers on one Postgres (the console's events, a chat resumed elsewhere); `manyServers.e2e.test.ts` is the two-server test. With several servers the audit may be in Postgres (`audit/postgres.ts`, `AUDIT_STORE`: a chain per call anchored into each server's chain for the day) and the traces on S3-compatible storage (`trace/store.ts`, `TRACE_STORE`: segments per server, joined by one reader; signed by the engine's own SigV4, `trace/s3/sigv4.ts`; tests use `testing/fakeS3.ts`, never a real bucket). Every option is in [section 14 of the guide](docs/guide/14-running-it.md). `server/dashboard/` is the console: one page (`page.html`, its pure view logic in `view.js` with types in `view.d.ts`: Live, Calls, Insights, Knowledge, Health, a call's detail, by the address's fragment), its routes (`routes.ts`), the bus that keeps every call in progress (`bus.ts`), the Live list worked out from it (`live.ts`, the lists' types in `rows.ts`), the Calls page's reading of the traces (`calls.ts`), Insights' figures and the daily figures cache beside the traces (`figures.ts`, `figuresCache.ts`), and the Knowledge and Health pages' data (`knowledge.ts`, `health.ts`) ([14.9](docs/guide/14-running-it.md#149-looking-at-calls-from-your-phone)). Several apps on one server: `host.ts` (a host file's apps, each with its own environment, and the numbers that reach each; `loadHost`), `hostServe.ts` (`dialogwright serve --host <file>`, the server of a host file), with the file read by `define/host.ts` against `schemas/host.schema.json` ([14.15](docs/guide/14-running-it.md#1415-several-apps-on-one-server-hostyaml)).
- `apps/*`: example apps. `apps/clinic` is the one to learn from. Each is a folder (app.yaml, intents.yaml, forms.yaml, prompts.yaml, policy.yaml, optional identity.yaml, routes.yaml and locale/, and the generated POLICY.md, policy.matrix and APP-MAP.md) with its code in `src/app.ts`, and a `CLAUDE.md` of its own.
- `packages/dialogwright/templates/`: the files `pnpm create-app` copies (`app/`, and `app-identity/` for what `--identity` changes). Edit them as real files; a test scaffolds both and runs check, typecheck, the app's tests and its regression, and the three read-back commands, which must change nothing. Each variant ships its `policy.matrix`, `POLICY.md` and `APP-MAP.md` with `{{name}}` and `{{display}}` in their titles: after changing a template's policy, forms or tools, scaffold that variant into a scratch folder, run the three commands there, and copy the pages back with the name and display put back as tokens.
- `packages/dialogwright/src/define/fixture/`: a tiny app folder (a library, with a Spanish locale) that the engine's own tests build.
- `packages/dialogwright/src/testing/screened/`: a tiny app folder (a free visit booked after three checks) that the engine's tests of a form's `checks`, of a priority switch's correction (`correctsForm`) and of the values a handoff names as never confirmed (`handoff.data.unconfirmed`) build, with its corpus, scripted calls and read-back pages; `tsx src/testing/screened/regress.ts --scenario <id>` follows one call turn by turn.
- `packages/dialogwright/src/testing/callback/`: a tiny app folder (a callback set up: a name, a callback number and what it is about) that the engine's tests of a slot that offers the number the caller is calling from (a digits slot's `callerNumber`) build, with its corpus and scripted calls; `tsx src/testing/callback/regress.ts --scenario <id>` follows one call.
- `packages/dialogwright/src/testing/texting/`: a tiny app folder (a request opened, with an offer to text updates) that the engine's tests of the number the caller is calling from used by an app (app.yaml's `callerNumber: { use: hint }`, `callerOf`, the call-start lookup, the `callerNumber` rule, a text offer's `onNo` and `ifNone`, `App.callerOffer` and the `offer` audit row) build, with its corpus, scripted calls and read-back pages, and its variants (`variant.ts`: an offer that takes a yes or a no only, `answers: yes-no`, and consent to text for the whole call, app.yaml's `textConsent`); `tsx src/testing/texting/regress.ts --scenario <id>` follows one call.
- `packages/dialogwright/src/testing/proposals/`: a tiny app folder (a problem reported at an address, and the status of a request behind identity) that the engine's tests of a slot that proposes a value from the call-start lookup (a slot's `offer: facts`, `FactsConfig.offers`) build, with its corpus, scripted calls and read-back pages; `tsx src/testing/proposals/regress.ts --scenario <id>` follows one call.
- `packages/dialogwright/src/testing/recognized/`: a tiny app folder (a problem reported, and the status of a request behind identity) that the engine's tests of a caller-ID match as the identifier (identity.yaml's level 1 `callerId`, `FactsConfig.callerMatch`, the `identity_caller_match` question and audit row) build, with its corpus, scripted calls, read-back pages and its greeting and one-time code variants (`variant.ts`); `tsx src/testing/recognized/regress.ts --scenario <id>` follows one call.
- `packages/dialogwright/src/testing/routed/`: a tiny app folder (a problem reported, the status of a request behind identity, and a payment plan only a route reaches) that the engine's tests of routes (routes.yaml's `start`, `afterIdentity` and `afterForm`, each outcome, the `route` audit row), business hours (app.yaml's `hours`, a holiday and a named schedule, at a scripted call's `now`), the start hook (`onStart`, writing a fact), a call that fails soft (`ctx.callTool(call, { failSoft: true })`), a predicate in code (`{ named: vip }`), the language a call starts in by the number called (app.yaml's `voice.numbers`, `env.SPANISH_LINE: es`, a scripted call's `calledNumber` and `env`), the `locale` outcome (on the number called in `variant.ts`'s `SPANISH_BY_ROUTE`, and on a queue in the call data) and a transfer target on a named schedule's hours build, with its corpus, scripted calls, a Spanish locale and read-back pages; `tsx src/testing/routed/regress.ts --scenario <id>` follows one call.
- `packages/dialogwright/src/testing/host/`: a host file (`host.yaml`) over the callback and routed fixture apps, each with its own settings file (both name `MAIN_LINE`, each its own number), that the engine's tests of several apps on one server build: a number reaching each app, the default, settings kept apart, records per app, chat by path, the console across apps, and a call taken over on another server staying in its app (`server/host*.test.ts`).
- `packages/dialogwright/src/testing/message/`: a tiny app folder (a message taken for one of two people) that the engine's tests of generated wording build: its form's questions generated (`wording: generative`), its read-back a framed line whose summary is a span generated from the message (`generate`) the first time (`variant.ts`'s `WHOLE_LINE` keeps the read-back generated whole from it, `from:`, for the tests of that path), two prescribed lines, style.yaml, with its corpus, scripted calls, baseline, read-back pages and the adversarial suite on the fake renderer; `tsx src/testing/message/regress.ts --scenario <id>` follows one call.
- `packages/dialogwright/src/testing/adversarial/`: the adversarial suite every app inherits (`adversarialSuite`, `runAdversarialSuite` in `'dialogwright/testing'`): cases generated from an app (injections, relationships claimed and not proven, off-scope requests, codes said aloud or never sent, hostile replies from every tool and service), each held to properties over its run, never to lines. `regress` runs it for an app whose app.yaml says `testing: { adversarial: on }` (the scaffold's, the clinic's and the utility's); its own test runs it over the testkit and every fixture app ([section 15 of the guide](docs/guide/15-the-adversarial-suite.md)).
- `docs/guide/`: the authoring guide, one file per numbered section (`01-the-folder.md` to `15-the-adversarial-suite.md`) and `README.md`, its contents. A new section is a new numbered file, listed in the contents. Link to a chapter and its anchor (`docs/guide/14-running-it.md#1412-the-options`). `docs/authoring-an-app.md` is the single page the guide was, kept as a pointer for each heading it had (an `<a id>` with a link to the chapter), so an old link lands: add nothing else to it. The package ships the chapters, that page, the first-app page and the slot pages (`src/define/shipped.ts`, `scripts/shipDocs.ts`), and `src/docLinks.test.ts` checks every relative link and anchor of every Markdown page in the repository.
- `docs/README.md`: the docs index: everything in the repository, where its documentation is, and every command; keep it accurate when something is added. `docs/first-app.md`: the guided first app from a shipped, fictional paragraph (a test holds that its prompt carries the paragraph word for word). `README.md` is for an adopter: what it is, a try with no keys, building one's own, a real call, the status.
- `Dockerfile` and `.dockerignore` at the root: the image of one of `apps/*` (`--build-arg APP=<name>`), run from src/ with tsx's loader under tini as a non-root user, `/ready` its health check; a project of its own gets its own from `templates/standalone/` (`Dockerfile`, `dockerignore`). `deploy/compose/`: the two-server stack (Postgres, an S3-compatible store, two app servers, HAProxy) that `pnpm multi:test` (`scripts/multi-test.mjs`) builds and runs the takeover driver against; the driver, its in-process stack and its compose stack are `packages/dialogwright/src/testing/multi/` (internal, never exported), its settings `MULTI_SERVER_ENV`, which a test holds the compose file to ([section 14.14 of the guide](docs/guide/14-running-it.md#1414-many-servers-on-one-database)).
- `.claude/skills/create-app/`: the create-app skill (`SKILL.md`), its worksheet template, its options index (`options.md`: each option by the need it answers), its patterns and its corpus guide. A test checks its links and its vocabulary.
- `assets/brand`: logo and icons.

```sh
pnpm install
pnpm typecheck
pnpm test
pnpm verify        # typecheck and test together
pnpm check         # every app folder under apps/: YAML, schemas, cross-links to the code, prompts, corpus
pnpm create-app <name> [--identity] [--dir <path>] [--display <text>]   # a new app from the template, linked into the workspace
pnpm create-app <name> --standalone [--dialogwright <spec>]   # the same app as a project of its own, outside this repository, on the dialogwright package (npm create dialogwright does this)
pnpm -r build      # each package's dist/ (JavaScript, declarations, the files src/ reads) for a project that installs it; nothing in this workspace needs it
pnpm adopt:test    # build and pack the packages, make a project of its own outside the workspace from the packed create-dialogwright, run its check, typecheck, tests and stub regression (weekly in CI)
pnpm multi:test [--in-process] [--keep]   # build the image, start deploy/compose (Postgres, an S3 store, two app servers, HAProxy), kill and drain the server holding a call on Twilio and Telnyx, check the takeover, take the stack down (needs Docker; weekly in CI); --in-process: the same driver against two servers in one process
pnpm --filter dialogwright regress:testkit
pnpm --filter @dialogwright/example-clinic regress
pnpm --filter @dialogwright/example-clinic regress --scenario <id>   # one scripted call, turn by turn (also --corpus <id>; any app's regress)
pnpm --filter @dialogwright/example-clinic regress --adversarial <id>   # one case of the adversarial suite (any start of its id), turn by turn, with its properties' verdict

pnpm --filter dialogwright schemas   # regenerate the JSON Schemas after a schema change
pnpm policy:matrix [dir...]   # write policy.matrix, the reviewed golden of what the gate decides (deliberate; tests compare it, CI never writes it)
pnpm policy:card [dir...]     # write POLICY.md, the policy in plain English with its diagrams (the same)
pnpm app:diagram [dir...]     # write APP-MAP.md, the app's intents, forms, slots, actions and rules as Mermaid diagrams (the same)

pnpm --filter dialogwright slot-docs   # regenerate docs/slots/*.md after a slot type's options, README or examples change
pnpm kb:model                 # download the pinned embedding model (potion-base-8M) into ~/.cache/dialogwright/models, checking its SHA-256
pnpm kb:index [dir...]        # write a knowledge base's vector index (kb/.index/<embedder>.json) after its topics change; commit it
pnpm kb:bakeoff <dir> --paraphrases <file> [--sweep]   # compare the retrievers on paraphrases offline; pick kb.yaml's floor and cap here
pnpm kb:approve <id...> --by "<your name>" [--owner "<team>"] [--dir <app folder>]   # approve a passage or a draft after reading it against its source: a person does this at their terminal (it asks them to confirm), never an assistant or a tool
pnpm kb:status [dir...]       # the passages by state (fresh, stale, edited, never approved, drafts), each with its fix
pnpm kb:ingest <folder | file | url> --dir <app folder> [--depth N] [--include <glob>] [--dry-run]   # documents or a website into kb/sources/<doc>.yaml, by section with provenance (packages/kb-author)
pnpm kb:draft [app folder] [--source <doc>] [--topic-hint <text>] [--model <id>]   # drafts from the sources into kb/pending with Claude (ANTHROPIC_API_KEY, the author's; refuses in CI); each checked, never said
pnpm kb:review [app folder] [--port N] [--traces <path|glob>]   # the review page on 127.0.0.1 with a one-time token: approve, edit then approve, reject; accept or merge proposed topics; its Gaps tab ranks what callers asked that nothing answered
pnpm kb:refresh [app folder]             # read every source again from its provenance; lists passages withheld and sections nothing cites
pnpm kb:gaps [app folder] [--traces <path|glob>] [--since YYYY-MM-DD] [--out gaps.md] [--json]   # rank what callers asked that the knowledge base did not answer, from the traces, with the fix for each
pnpm --filter dialogwright test slots/<type>   # a slot type's tests, including the conformance kit
pnpm configure [--app <name>]   # asks, and writes <app>/.env (mode 600): a laptop with no keys, or a phone line; a key is read with the echo off or from its own environment variable, never a flag
[ENV_FILE=<path>[,<path>...]] pnpm start [--app <name>] [--tunnel quick|named|none]   # the app's server with its .env, or the file ENV_FILE names (not --env-file: some pnpm builds take that flag themselves); quick, the default with PUBLIC_HOST unset, opens a Cloudflare quick tunnel (no account)
# ENV_FILE may name several files, comma-separated: read in turn, a later one winning, the environment over all; one that names no file is refused
[ENV_FILE=<path>[,<path>...]] pnpm diagnose [--app <name>] [--offline]   # what is misconfigured, one line per check with its fix; sends no key and calls no carrier or model API
[ENV_FILE=<path>[,<path>...]] pnpm start --host <file>   # several apps on one server (host.yaml; or HOST_FILE, or host.yaml beside the apps): every app it lists, the number called picking each call's app, the server's settings from the .env beside it (also: pnpm diagnose --host, pnpm service ... --host, pnpm check host.yaml, pnpm serve --host, the server alone)
pnpm audit:verify <audit folder | postgres://...>   # each audit day file's hash chain, or the audit in Postgres (AUDIT_STORE: each call's chain and each day's anchors); exit 1 at the first break
ENV_FILE=<path>[,<path>...] pnpm service <launchd|systemd> --app <name> [--label <label>] [--out <file>]   # a service file with this machine's paths; prints the install commands, runs none
pnpm fallback --provider <twilio|telnyx> --number <E.164> [--message "..."] --out <file>   # the document a carrier plays when it cannot reach the server; host it elsewhere, paste its URL where it says
[ENV_FILE=<path>[,<path>...]] pnpm console:link [--app <name>]   # with CONSOLE_AUTH=token: a new one-time sign-in link for the console (the one before it stops working), printed on the server's machine
```

`pnpm check` prints one line per problem, `file:line:column  path  message  ->  fix`, and exits 1 when there is any. Act on the fix text.

## Rules

- Never put policy in tool code. Tools do work; the gate decides whether they may run.
- A line is generated only where the app explicitly asks for it (prompts.yaml's `mode: generative`, a form's `wording: generative`); every other line is said word for word. What is regulated is the app designer's call, never the framework's: mark such a line `prescribed: true` and it is never generated (`pnpm check` refuses `mode: generative` on it). The policy card lists every generated and every prescribed line, so a reviewer sees which lines a model words. To summarize what a caller said, frame it: the line fixed, saying whose words follow, and only the summary a generated span (`generate`), given nothing but its goal and the caller's words, held to them alone, and filled with the exact words whenever it fails; a line generated whole from what the caller said is the app's choice, and `pnpm check` warns of it. Checks hold every generated line to the shape of what it was given (every value word for word; no figure and no capitalized word it was not given, a figure from the caller's words only in an acknowledgement; the word budget; one question only where the fixed text asks, and a decision question kept word for word; no negation added or dropped; no other value of an item's slot in its place), collected content is screened again before a line is worded from it, and the decision model's drift check judges what the shape checks cannot (a line that does more than its goal, or states the caller's words as the agent's own): a judgement, not a guarantee. The fixed text is said whenever a check fails, the model is slow or errs, or the turn's words were flagged. A model is sent a line's values as its fixed text would say them (a value recorded by its last four among them, which the policy card lists), never an identity factor, a value the records hide whole (but for the one named exception, a `text` slot's `redact: length-summarized`: its words are sent whole to the render model only for a framed line's span that summarizes them, never a line generated whole from them, and to the decision model's checks of that span; in such an app no other line is sent the caller's words, and every caller's words are masked by their length in the trace, the console and the frame log; the policy card lists it, and `pnpm check` refuses it on an identity factor and on a slot no framed span summarizes), the transcript or anything else a tool returned, and never called in a test or in CI (tests use the fake renderer; recording with a real model is the maintainer's step).
- The engine never imports an app.
- An app imports only from `'dialogwright'` (src/index.ts), the supported API, and from its three other entries: `'dialogwright/testing'` (its tests: the shadow harness, the slot conformance kit, the gate-event goldens, the gate grid and the shadow gate, with their reference, the legacy `evaluateCall`, and the one id map from its ids to the rules' names; the adversarial suite; and a carrier adapter of one's own: the voice conformance kit with the voice provider types, `VoiceProvider` and `DialTarget`, and `dialVerb`, the `<Dial>` the built-in carriers write), `'dialogwright/slot-kit'` (the helpers a slot type is written with) and `'dialogwright/policy'` (the gate, `compiledPolicyOf`, the named rules the lifecycle runs, and `passed`; policy.yaml and identity.yaml for an app that is not a folder: `definePolicy`, `defineIdentity`; the compilers; and the types its tables and rules are written in). The `dialogwright/<dir>/<file>` subpaths are internals; when an app needs one, export it from the root instead.
- No real personal data anywhere: use the 555 phone range and invented names.
- Run `pnpm check`, `pnpm verify` (the type check and the tests) and both regressions (the testkit's and the clinic's) before committing. `pnpm check` is the one that catches an app folder and its code disagreeing.
- Every YAML file of an app starts with `# yaml-language-server: $schema=<relative path>/packages/dialogwright/schemas/<kind>.schema.json`, so an editor completes and checks it. Keep the line when you add a file.
- Rules are recorded by name (`identity`, `scope`, `confirmed`, `role`, `attempts`, `fields`, `dateInRange`, `limit`, `oneOf`, `noneOf`, `callerNumber`; a custom rule by its own id; `unlisted` for an action the policy does not list; `subject` for an identity tool refused to a party who is not one of the app's subjects, which the gate does for every app) in decisions, gate events, the trace, the console and the audit. Ask a decision whether a rule passed with `passed(decision, 'role')` (`'dialogwright/policy'`), never by an id string. The legacy ids `R0` to `R7` live only in the tables' `rulesFor` (and the legacy evaluator, the shadow gate's reference, whose ids the shadow maps to the names in one place: `nameOfLegacyId` in testing/gateGrid.ts) and in audit files written before 2026-10-03; an app's own rule may take none of them.
- Policy changes land as a set. After you change policy.yaml or identity.yaml, run `pnpm policy:matrix`, `pnpm policy:card` and `pnpm app:diagram` for the app, read each diff as a change in what the agent may do, and commit them with the policy; the golden tests fail when one is stale. Never write them to make a test pass without understanding the diff, and never from CI. The three tests an app keeps beside its policy are `policyInvariants`, `expectPolicyMatrix` (with `runRuleExamples`) and `expectPolicyCard`, from `'dialogwright/testing'`. Write `say:` for every action. `.github/CODEOWNERS` makes a change to these files need compliance's review: do not widen it away.
- A rule of an app's own is written with `defineRule` (from `'dialogwright/policy'`), with a description and at least one example the gate allows and one it refuses; its `compared` line goes to the audit as it is, so it holds only what may be recorded. The built-in rules are `identity`, `scope`, `role`, `confirmed`, `attempts`, `fields`, `dateInRange`, `limit`, `oneOf`, `noneOf` and `callerNumber`; add one only through "Adding a built-in policy rule" in CONTRIBUTING.md.
- Every tool lists the `params` its calls carry, and `policy.yaml` declares under `audit` how each that is not a slot with a redact setting is recorded (`last4`, `mask`, `length`, `secret` or `keep`). A tool whose result a party acting for subjects may not see in full declares its `fields`, and `redact` names them. Bounds of `dateInRange` and `limit` come only from the app's lookups (`code.lookups`), never from the session, and every param a reference reads is held to the caller's own records by a `scope` rule earlier in the action, unless the rule says `unscoped: true` (its lookup is about no one's record).
- A form's `hooks:` list in forms.yaml must name exactly the hooks the code writes for it, and every tool has an action in policy.yaml. Policy lives in policy.yaml and the gate, never in a tool.
- Most slots are configuration: an app names a library type in `slots.yaml` (see `docs/slots/README.md`). Write a slot in code only when no type fits. When you add or change a slot type, follow "Adding a slot type" in CONTRIBUTING.md: run its conformance kit (`pnpm --filter dialogwright test slots/<type>`), regenerate the schemas (`pnpm --filter dialogwright schemas`) and the pages (`pnpm --filter dialogwright slot-docs`), and commit the results; tests fail when they are stale. Edit a type's `README.md`, never the generated page.
- Keep `packages/dialogwright` free of any one industry's vocabulary: its code, comments, tests and fixtures use neutral words (caller, subject, record, request, appointment, loan). Words that belong to one app's domain stay in that app. The same goes for names, dates of birth and numbers: invented, 555 range.
- A knowledge base's answers are fixed text, said word for word. A model never writes or rewrites one: it may only choose which topic a caller asked about (the `topic` slot), and a drafting tool may only propose a passage into `kb/pending`, which is never read at run time.
- Approvals are by people only. Never run `pnpm kb:approve` (or the review page) to make a check pass, never pass it `--yes`, never write an `approval` or a hash by hand (`pnpm check` refuses an approval with no line in the log), and never edit `kb/approvals.jsonl` (it is only appended to). A passage that is stale or edited is withheld until a person has read it against its source and approved it again.
- Never commit a model key. `kb:draft` reads `ANTHROPIC_API_KEY` from the environment or a git-ignored `.env`; it refuses in CI, and no test, fixture or script makes a real drafting call (tests use a fake drafter). Never put a key in a file, a log or a message.
- Retrieval floors, caps and the retriever change the request the model gets, so they are chosen offline on paraphrase sets (`pnpm kb:bakeoff --sweep`), never by re-recording a cassette. After a change to a topic's title, keywords or example questions in an app with an embedder, run `pnpm kb:index` and commit the index.
- A tool that writes declares `idempotent: true` and passes `ctx.idempotencyKey` to the system it writes to, so a write repeated after a restart is not done twice. What goes into an idempotency key (`core/idempotency.ts`) is a promise kept across versions; a change to the shape of a saved session bumps `SESSION_SCHEMA` (`core/session.ts`), so a call saved before it goes to a person rather than resume wrongly.
- A new session store implements `server/stores/types.ts` and passes `runStoreContract` unchanged, its `lease: ...` checks included (CONTRIBUTING.md, "Adding a session store"). The Postgres store's tests run on PGlite (a devDependency), never a database a test has to reach; `pg` is an optional dependency loaded only when `SESSION_STORE` names Postgres, and a connection string is never logged with its password (`maskConnectionString`). Every server option has a default that keeps the behaviour from before it (two exceptions, each the maintainer's decision: `RESUMED_AFTER_MS` defaults to 1500, so on one machine a planned restart its caller hardly notices, under 1.5 s of silence, gets no apology; `RESUMED_AFTER_MS=0` restores the old line; and, decided 2026-10-13, `END_PLAYBACK_FACTOR` defaults to 2, so a call ending on a line waits up to twice its estimate (plus `END_PLAYBACK_MARGIN_MS`) for the carrier's report that it has played, where before it waited the estimate alone and cut a slow voice's goodbye; `END_PLAYBACK_FACTOR=1` restores the old wait), and is documented in section 14.12 of the guide ([docs/guide/14-running-it.md](docs/guide/14-running-it.md#1412-the-options)) and each `.env.example`.
- Never regenerate a regression baseline or snapshot to make a test pass. A changed output is a finding to explain, not noise to overwrite.
- A case the adversarial suite fails is a finding: fix the app (its policy, a hook, a tool's `check` of its reply) or the engine, never by loosening a property, changing a case, or turning the suite off. A tool whose reply a line says, or a call is made from, declares `check` (written with `replyShape`), in the field's closed form where it has one (`oneOf`, `digits`, `code`, `isoDate`, `amount`; `text()` only for what is truly free text): a check bounds a shape, it does not detect instructions. A downstream system's reply is untrusted, and a turn whose reply fails its check ends with a person (`result-unchecked`); read a call's verdict before its value.
- Every root command is a subcommand of the one command line, `packages/dialogwright/src/define/cli.ts` (`dialogwright <command>`; `npx dialogwright <command>` in a project of its own): a new one goes there, and its root script runs that entry. Code a runtime path reads (a file beside a module, a JSON import, a template) must work from the build in `dist/` as from `src/`; after a change to a package's manifest, its build, the scaffold's templates or a command line, run `pnpm adopt:test`. Nothing is published from here: publishing is the maintainer's step (RELEASING.md).
