# 14. Running it

[Contents](README.md) · Previous: [13. Channels](13-channels.md) · Next: [15. The adversarial suite](15-the-adversarial-suite.md)

An app's server is `pnpm --filter <app> serve`, configured by its environment. On a machine you own, a few commands at the repository root do the rest, in the order a developer meets them below: try it with no keys, configure a phone line, start it with a tunnel that needs no account, point the carrier at it, diagnose it, then move it to a machine that stays on. Each command prints what it does, and none sends a key anywhere.

```sh
pnpm configure [--app <name>]                # asks, and writes <app>/.env (mode 600): a laptop with no keys, a laptop with a model's key, or a phone line
pnpm start [--app <name>] [--tunnel quick|named|none]   # the server with that file; quick opens a tunnel that needs no account
pnpm start --host <file>                     # several apps on one server: every app host.yaml lists, the number called choosing each call's app (14.15)
pnpm diagnose [--app <name> | --host <file>] [--offline]   # what is misconfigured, one line per check with its fix
ENV_FILE=<path> pnpm service <launchd|systemd> --app <name>   # a service file that keeps it running; prints the install commands, runs none
pnpm fallback --provider <twilio|telnyx> --number <E.164> --out fallback.xml   # what the carrier plays when it cannot reach the server
pnpm console:link [--app <name>]             # with CONSOLE_AUTH=token: a new one-time sign-in link for the console, on the server's machine
pnpm audit:verify <audit folder | postgres://...>   # each audit day's hash chain (or, in Postgres, each call's and each day's), exit 1 at the first break
pnpm multi:test [--in-process]               # two servers in containers behind a balancer, one killed and one drained mid-call (needs Docker; 14.14)
```

In a project of its own ([where to start](11-walkthroughs.md#where-to-start)), each is the package's command, run in the project's folder with no `--app` (the project is its one app): `npx dialogwright configure`, `npx dialogwright start`, `npx dialogwright diagnose`, `ENV_FILE=<path> npx dialogwright service <launchd|systemd> --app <name>`, `npx dialogwright fallback ...`, `npx dialogwright console:link` and `npx dialogwright audit:verify <audit folder | postgres://...>` (the project's package.json has each as a script too, so `npm start` is `npx dialogwright start`). `start` runs the project's own `serve` script with npm, where this repository runs `pnpm --filter <app> serve`; `service` writes a file that runs it with pnpm, so it needs pnpm on the machine. The rest of this section names them as this repository does.

The website's guide, [running your own IVR on a machine you own](https://dialogwright.com/guides/home-server.html), tells the same story step by step with the carriers' consoles, the tunnels and the service managers; this section is the reference, and [14.12](#1412-the-options) lists every option with its default.

### 14.1 Try it with no keys

```sh
pnpm configure --app utility --mode try
pnpm start --app utility
```

`pnpm configure` asks which app and how to try it: on this computer with no keys, on this computer with a decision model's key, or as a phone line (the flags above answer both). Trying it writes `apps/utility/.env` with the server on `localhost`, the web chat on (and its widget, once it is built with `pnpm --filter @dialogwright/widget build`), and no model (`JEV_CLIENT=heuristic`: the app understands by its own labelled examples and keywords, enough to walk every path). `pnpm start` runs the server with that file and no tunnel, since `PUBLIC_HOST` is `localhost`. Open `http://localhost:3000/dashboard`, the console, to watch each call and chat, and, for an app with a chat page (the utility's is `/chat-demo`), the page with the widget on it. Both answer only on this machine. With no server at all, `pnpm --filter <app> cli --client heuristic` is a text console.

**With a decision model, and no phone line yet.** `pnpm configure --app <name> --mode model` (the third choice when it asks) writes the same laptop settings with the model in place of the examples: it asks for the model (TypeSafe, OpenRouter, the Vercel AI Gateway or a compatible endpoint; not none) and its key, as a phone line does, and no carrier. It is what recording an app needs: the regression reads the folder's `.env` itself, so `pnpm --filter <app> regress --client record --threshold JEV_TIMEOUT_MS=15000`, which it prints, records the app against the model, and `--client recorded` replays it offline. `pnpm start` then serves the web chat and the console on `localhost` with the model understanding them. A phone line added later (`--force`, choosing a phone line) keeps the model's key from the file it replaces when the same provider is chosen, and asks for the carrier's.

### 14.2 A phone line: configure

A phone line needs two keys: a carrier's (Telnyx or Twilio, with a number) and a decision model's (TypeSafe, OpenRouter or the Vercel AI Gateway; or none, with a compatible model on your own machine, `JEV_PROVIDER=custom`). Nothing else needs an account.

```sh
pnpm configure --app <name> --force         # --force replaces the .env the try-out wrote
```

It asks, in order: the app; this computer (with no keys or with a model) or a phone line; the carrier and its secret (`TELNYX_PUBLIC_KEY` or `TWILIO_AUTH_TOKEN`); the model and its key; the number a call goes to for a person (`HANDOFF_NUMBER`); and each number the app's YAML names by its variable (`env.<NAME>`): a transfer target app.yaml's `transfer` names (an E.164 number or a `sip:` URI) and a number callers dial (a `called` condition's, a `voice.numbers` key's: E.164), each checked as the server will check it. A number is no key: it is echoed and written as given, taken from `--number <NAME>=<value>` or the environment variable of its name when either gives it; on this computer, Enter takes a 555 number of its own, which goes nowhere, so a fresh laptop's `.env` starts (the server refuses to start with a variable the YAML names unset). The YAML's other variables (`startParameters`) are written commented out, with a line saying the server needs them. A key is read with the echo off (the line editor keeps no history), or taken from the environment variable of its own name when that is set; a key is never a flag, since a flag stays in the shell's history. It is printed by its length only and written only to `<app>/.env`, mode 600, git-ignored. `pnpm configure` refuses to replace a `.env` without `--force` (before it asks anything; with it, a model's key the old file holds is kept when the same provider is chosen, and said so by its length), checks the file it wrote with `pnpm diagnose --offline`, and prints what to run next and where the webhook goes in the carrier's console. Every question is a flag for a script: `--mode try|model|phone`, `--carrier telnyx|twilio`, `--model typesafe|openrouter|vercel|custom|none` (with `--base-url` and `--model-id` for `custom`), `--handoff`, `--number <NAME>=<value>` (once for each number the YAML names), `--public-host`, `--port` and `--non-interactive`, which answers from the flags and the environment and asks nothing (on this computer a number it is not given is a 555 number; for a phone line each is needed).

The commands are `pnpm configure`, not `pnpm setup`, and `pnpm diagnose`, not `pnpm doctor`: those two names are pnpm's own commands, which win over a script of the same name.

### 14.3 Start it with a quick tunnel

```sh
pnpm start --app <name> --tunnel quick
```

The carrier reaches the server over HTTPS and a WebSocket, so a laptop behind a home router needs a tunnel. `quick`, the default when `PUBLIC_HOST` is unset, starts `cloudflared tunnel --url http://localhost:<PORT>` (Cloudflare's quick tunnel, which needs no account; `cloudflared` must be installed, and without it `pnpm start` says how), reads the `*.trycloudflare.com` hostname it is given (within 30 seconds), starts the server with that `PUBLIC_HOST`, and prints the webhook URL and the carrier's steps. The hostname changes every run, so the webhook does too: fine for an evening, wrong for a line people rely on. `named` runs the server alone for a named tunnel that runs as its own service, with `PUBLIC_HOST` its hostname; `none`, the default when `PUBLIC_HOST` is set, runs the server alone.

A stop (Ctrl-C, SIGTERM, or the terminal closing) is passed to the server once, and `cloudflared` is stopped only after the server has drained, so live calls keep their way in while they finish ([14.6](#146-an-always-on-machine)). If `cloudflared` stops on its own, the server is stopped too, since no carrier can reach it.

### 14.4 Point the carrier at it

`pnpm start` prints the webhook, `https://<PUBLIC_HOST>/voice/<carrier>`, and where it goes: for Telnyx, a TeXML application's voice URL (method POST) with the number assigned to it; for Twilio, the number's "A call comes in" webhook (HTTP POST). Then call the number. [13.2](13-channels.md#132-serving-voice-twilio-telnyx-or-both) has the paths each carrier answers on, and the website's guide the console steps for each.

### 14.5 Diagnose

```sh
PUBLIC_HOST=<the tunnel's hostname> pnpm diagnose --app <name>   # pnpm start prints this line
```

`pnpm diagnose` reads the settings the server would and checks, one line each with `ok`, `warn`, `fail` or `skip` and a fix: the settings file is its owner's alone; the config loads (with the server's own messages); `PUBLIC_HOST` resolves and `/health` answers through it within five seconds; the console is a 404 there (or, with `CONSOLE_AUTH=token`, sends a browser with no cookie to the sign-in page, and its data answers 401); each carrier's secret has its shape and signatures are checked; which model, from where, and its key variable set; `HANDOFF_NUMBER` is not a 555 number; each environment variable the app's app.yaml and routes.yaml name (`env.<NAME>`, read from the YAML alone: `startParameters`, `transfer`, a `called` condition, a `voice.numbers` key) is set, by its length and never its value, and fits a custom parameter, or, for a transfer target, holds an E.164 number or a `sip:` URI and is not a 555 number, or, for a `called` condition and a `voice.numbers` key, holds an E.164 number (and no number is listed under `voice.numbers` in two languages); for an app that names its languages, what the carriers listed are sent of them (`languages`: a locale spoken as a tag with no region fails where the server answers on Twilio, which refused one as a `<Language>` code on a live call, and a bare transcription tag, or either on Telnyx alone, warns; a language other than English heard by a recognizer that hears English only fails on Twilio where that is certain, its own or the server's `TWILIO_SPEECH_MODEL` for the default locale, and warns where it names none and another language's may be kept: [13.3](13-channels.md#133-languages-on-the-phone)); the trace and audit folders can be written, with a gigabyte free; the clock is within a minute of the carrier's API host's (Telnyx refuses a webhook signed more than five minutes off); with `SESSION_STORE=file:`, its folder ([14.7](#147-surviving-a-restart)); and with several servers, the shared database, the audit's and the trace store's bucket ([14.14](#1414-many-servers-on-one-database)). It exits 1 only on a `fail`. It calls no carrier or model API and sends no key: its requests are DNS, a few GETs to the server's own address, and one `HEAD` with no key and no body to the carrier's API host (or else the model provider's) for its `Date`. `--offline` makes no request at all; it is what `pnpm configure` runs.

### 14.6 An always-on machine

For a line people rely on, the same setup moves to a machine that stays on (any Mac or Linux machine), with the settings outside the repository, a named tunnel whose hostname stays, and the service manager keeping the server up.

**The settings file.** The server reads its environment and, when `ENV_FILE` names one, a settings file (Node's own parser); a variable already in the environment wins over the file, and a file that does not exist stops the start. `pnpm start` sets it to `<app>/.env`. A file kept elsewhere (the right place on a machine that stays up, mode 600) is named with `ENV_FILE=<path>` in front of the command: `ENV_FILE=~/ivr/myline.env pnpm start --app myline`, and the same for `pnpm diagnose`, `pnpm service` and `pnpm console:link`. `ENV_FILE` may name more than one file, separated by commas: `ENV_FILE=apps/myline/.env,~/keys/render.env pnpm start --app myline` reads each in turn, a later file's variable replacing an earlier one's, and the environment still winning over them all, so an app's settings and a key kept in a file of its own are read together with no shell `source`. A relative path is from where the command was run, and a leading `~/` is the home folder (a shell expands only the first). A comma, not a colon (a colon is in a Windows path); a path with a comma in it cannot be named. `pnpm start` hands the server the same list, `pnpm diagnose` checks each file is its owner's alone, and `pnpm service` writes the list into the service file. The regression run, the text harness and the cassette trim read `ENV_FILE` the same way ([11](11-walkthroughs.md#after-a-recorded-run)). `--env-file <path>` works too where pnpm passes it on, but some pnpm builds read a `--env-file` themselves, and fail on a relative path before the command starts, so `ENV_FILE=` is the form to use.

**The service.** `ENV_FILE=<path> pnpm service <launchd|systemd> --app <name> [--label <label>] [--out <file>] [--force]` writes a launchd agent or a systemd user unit from `packages/dialogwright/templates/service/`, with this machine's absolute paths (the repository, pnpm, node's folder, the settings file): it runs the app's server with `ENV_FILE`, starts it at login (and at boot, with a launchd daemon or systemd's lingering, which it explains), restarts it when it exits, and gives a stop `DRAIN_UNREADY_MS`, `DRAIN_MS` and ten seconds more before anything is killed. It prints the commands that install, check and stop it, and runs none of them. It warns when the settings file can be read by others. Nothing from the file goes into the service file but its path.

**Ready, and a drain.** `GET /ready` answers 200 `{"ready":true}` while the server takes new calls, and 503 `{"ready":false,"draining":true}` once it stops (with `DRAIN_UNREADY_MS` set, 503 `{"ready":false,"stopping":true}` first, for that long, while new calls are still answered as usual, so a load balancer has seen it go before the drain sends any new call to a person). `GET /health` stays 200 while the process runs: it counts live calls (`sessions`), and adds `chat` with the chat on, `draining` while it drains, and `disk` when a retention is set ([14.10](#1410-keeping-the-disk-in-check)). A stopping server (SIGTERM from the service manager, or Ctrl-C) first drains: a new call is put through to `HANDOFF_NUMBER`, a new chat is told `busy`, and live calls and chats go on until they end or `DRAIN_MS` passes (30 seconds by default). Then the calls still live are closed as going away (WebSocket 1001), and the carrier calls back for each: with the memory store the server, about to close, puts that caller through to `HANDOFF_NUMBER` (it waits up to three seconds for those callbacks); with `SESSION_STORE=file:` it hands each call over to the server that starts next instead ([14.7](#147-surviving-a-restart)). A second signal stops it at once (exit 130 or 143).

**A crash** (an uncaught exception, or a promise rejected with nothing to catch it) is logged with its stack and its causes' stacks (never the settings); then the server closes as far as it can in three seconds (turns under way finish; a new call goes to `HANDOFF_NUMBER`) and exits 1, for the service manager to start it again. That is Node's own rule for an unhandled rejection, kept on purpose rather than made an option: a server in a state nothing planned for should start again, not go on answering calls. Code that means to carry on after a failed promise catches it where it happens.

### 14.7 Surviving a restart

With the default memory store a restart (an update, a reboot, a crash) ends the calls under way. With `SESSION_STORE=file:<dir>` it does not. With `SESSION_STORE=postgres://...` neither does a server that dies or drains while others run beside it ([14.14](#1414-many-servers-on-one-database)). In either, after a planned restart or a drain the `resumed` line is said only past `RESUMED_AFTER_MS` of silence (default 1500), and after a crash always (14.14).

**What is saved.** The server saves each call after every turn, before the turn's frames go out (its session with `SESSION_SCHEMA` beside it, its reconnect count, its audit entries, and a service request it is waiting on with its key), each chat with its resume token's hash, and the live relay tokens as hashes, in a folder of its own (mode 700, each file 600, every write a temporary file renamed over the last). `pnpm diagnose` checks the folder is writable, kept across a reboot (not a temporary filesystem), and its owner's alone. One server uses a folder: two servers on one folder would sweep each other's calls. The folder holds what callers said, as traces do: keep it on this machine, never in the repository (`sessions/` is git-ignored).

**What the caller hears.** When a carrier calls back for a call this server does not hold (`/cr-action/<carrier>`, its relay having lost the socket), or opens a socket for one, the server loads it, and the caller hears the `resumed` line ("Sorry, I lost you for a moment." unless prompts.yaml says otherwise) and then the question they were last asked, with every value they gave still on the form; the reconnect counts toward `RECONNECT_LIMIT`. A web chat resumes the same way with its resume token, and the client sees `ready` for the same session. The trace, the frame log and the day's audit chain go on in the same files, and `pnpm audit:verify` passes across the restart. What is not resumed: a call saved under another `SESSION_SCHEMA`, or for an app this server does not run (the caller is put through to the app's transfer `default`, `HANDOFF_NUMBER` for an app without `transfer`, and the log says why); one saved for another carrier; one past `SESSION_TTL_MS` idle or `SESSION_MAX_AGE_MS` old; and one whose carrier never calls back (forgotten once past its time, with a `call_ended` in the audit).

**A planned restart** (SIGTERM from a service manager, Ctrl-C, `pnpm start` stopped for an update) hands each call still live after `DRAIN_MS` over to the restarted server. The server closes the call's socket as going away; the carrier calls back at once, and this server, still listening, answers with a document that pauses `RESTART_PAUSE_S` seconds (a `<Pause>` before the `<Connect>`, which Twilio's TwiML and Telnyx's TeXML both take) and then connects again, with a relay token saved where the restarted server finds it. Once every call has called back (or three seconds have passed) the server stops listening and exits, and while it is still there it turns every socket away (503), so the carrier's lands on the restarted server. A carrier that connects too early meets that 503, calls back, and is told to wait again (each time counts toward `RECONNECT_LIMIT`, so the loop ends with a person). What the caller hears: silence for `RESTART_PAUSE_S` seconds, then the `resumed` line and the question they were on. Set `RESTART_PAUSE_S` a little above how long the server takes to stop and start (the log's `listening on` line says when it is back); a restart slower than the pause fails the carrier's connect, and its callback, finding no server, goes to the fallback ([14.8](#148-when-the-server-is-down-the-carriers-fallback)). `RESTART_PAUSE_S=0` skips the handover: the server stops listening first, and every callback goes to the fallback unless the restarted server is already up. A voice provider of your own that leaves out the pause (`StartDocumentOptions.pauseS`) connects at once and meets the 503 until its reconnects run out.

**The same address before and after.** Both a planned restart and a crash bring a call back only to the hostname the carrier already has. A named tunnel keeps it. `pnpm start --tunnel quick` stops its tunnel with the server, and the next quick tunnel gets a new `*.trycloudflare.com` hostname, so a call cannot come back to it: to try a restart on a laptop, run the quick tunnel in a window of its own (`cloudflared tunnel --url http://localhost:3000`), set `PUBLIC_HOST` to its hostname, and restart only the server (`pnpm start --app <app> --tunnel none`).

**A crash** (or a kill, a reboot, a power cut) hands nothing over: the server stops listening at once, and a carrier calls back the moment the socket drops, so its callback usually finds no server and fails. The carrier then uses the number's fallback ([14.8](#148-when-the-server-is-down-the-carriers-fallback)), and the caller is put through to `HANDOFF_NUMBER`; a callback that comes after the restarted server is up resumes the call. A call waiting on a service's answer when its server went away keeps the request, and the restarted server sends it again once, with the same key ([14.13](#1413-writes-that-are-never-done-twice)).

**The disk.** A save is renamed into place whole, so a process that stops or crashes loses nothing. It is not flushed to the disk unless `SESSION_FSYNC=on`, so a power cut may lose the last few seconds of saves (a call whose save is lost resumes a turn or two back, or not at all); `on` flushes each save and its folder, at the disk's latency on every turn, for a machine with no battery or UPS. A save that fails (a full disk) is logged and the call goes on; it only cannot be resumed from that turn.

### 14.8 When the server is down: the carrier's fallback

A carrier turns to a number's fallback document when it cannot reach the server at all: a call that comes in while it is down, and a callback for a live call that comes before a restarted server is listening. `pnpm fallback --provider <twilio|telnyx> --number <HANDOFF_NUMBER> [--message "..."] --out fallback.xml [--force]` writes one: the carrier's own apology (or your `--message`, escaped) and a dial to the number. It reads no setting and sends nothing. Host the file at an https URL somewhere that stays up when this machine does not (GitHub Pages, Cloudflare Pages, object storage), and paste the URL where the command says: Twilio's number's "Primary handler fails", Telnyx's TeXML application's fallback URL. Write it again when `HANDOFF_NUMBER` changes. Without one, a caller whose callback finds no server hears the carrier's own error. Whether a carrier uses it for a failed callback mid-call, and not only for a call that comes in, is [live check 3](../live-checks.md#3-reconnect-after-the-relay-socket-fails-and-a-restart-mid-call).

### 14.9 Looking at calls from your phone

The console shows calls as they happen, with what callers said, so by default (`CONSOLE_AUTH=local`) it answers only a request made on this machine, and is a 404 through the tunnel (`CONSOLE_LOCAL_ONLY`, on by default). Another computer can reach it over SSH (`ssh -L 3000:localhost:3000 <the machine>`). `CONSOLE_AUTH=token` serves it through the tunnel too, for its one owner, behind a sign-in (refused with `DASHBOARD=off`):

1. When the server starts it makes a one-time sign-in link, `https://<PUBLIC_HOST>/dashboard/login?code=<64 hex digits>` (on a laptop, `http://localhost:<port>/...`), valid for ten minutes and used once, and writes it to `CONSOLE_LINK_FILE` (mode 600, in a folder of mode 700; a folder another account owns or others may write in is refused). The log names the file and a short hash of the code, never the code.
2. On the server's machine, `pnpm console:link` prints a new link (the one before it stops working). It reads the link file, refuses one that others can read or another account owns, and posts the key in it to the server's `/dashboard/link`, which answers only a request made directly on this machine that carries that key and no `Origin`; through the tunnel there is no such path. The key is what proves the caller is the owner: other accounts on the same machine can reach its localhost ports, but not read the file. Send yourself the link however you like.
3. Opening the link shows a page with a Sign in button, so a link preview, which only fetches the page, never uses the code up. Pressing it sets the session cookie, signed with HMAC-SHA256 (`CONSOLE_SESSION_KEY`, or a key made at start), HttpOnly, Secure, SameSite=Strict, on `/dashboard` only, for `CONSOLE_SESSION_HOURS`; on a laptop (`PUBLIC_HOST=localhost`) a plain http request on the machine gets it without Secure. The console's header then has Sign out, which ends that session at once, closing a live feed it has open. With `CONSOLE_SESSION_KEY` set, sign-outs are kept beside the link file (`signed-out.json`, mode 600: a SHA-256 of each session's id with its expiry, never the id or the cookie), so a signed-out cookie stays refused after a restart. A cookie whose expiry is further off than `CONSOLE_SESSION_HOURS` allows (the hours were lowered since) is refused too; to sign every browser out at once, change `CONSOLE_SESSION_KEY`.

**The console's pages.** The console opens on **Live**, what is happening now; its menu leads to **Calls**, **Insights**, **Knowledge** and **Health**. On a host the app filter sits beside the menu (`/dashboard?app=<id>` shows one app's calls alone, on every page); with one app there is no app column and no filter.

- **Live** is a strip of four numbers: the calls in progress, the calls waiting for a person or being transferred, today's containment (of today's calls that ended, the share the agent handled to the end with no handoff; a hang-up or an error is not counted as handled, and Insights shows them apart) and today's cost (the decision model's, from the traces, and the carrier's beside it when its rate is set, below, with the minutes on a carrier with no rate counted and not priced). Today starts at the viewer's midnight. Under it, the calls in progress on every server and in every app, one row each: the app, the caller as masked (`…0110`), the channel and carrier, the task and the step (the form and the slot or confirmation being asked, in the app's console labels), the time ticking, and a status: on track, second try (the slot asked is past its first attempt), frustrated (the frustration gate fired on the call), transferring (a handoff is under way) or with a person (handed off; the server does not see the person's leg of the call, so the row stays two minutes and then leaves the list). Alerts come first, then the longest-running. A call is in progress until it ends: a turn that finishes after the caller hung up (one under way when the hangup came) is marked as late in the call's detail and does not bring the call back, only a reconnect does; and a call with no end recorded that has had no word for half an hour is taken for ended ("no end recorded"), as a server that stopped with calls on it, or a peer server that died, never says. A click (or Enter) opens the call's detail, the view the console has always had, live, with Back to the list; **Follow the newest call** is that view following each call as it starts, as the console used to open.
- **Alerts.** A call that turns frustrated, or starts waiting for a person, is marked in the list, and the calls in alert are counted in the tab's title (`(2) Live · ...`) and beside Live in the menu, on every page. **Sound** (off by default, remembered in this browser) adds a short chime, made by the page itself, when a call enters an alert; an alert is a change, so the calls already in alert when a page opens make no sound.
- **Calls** are the calls that happened, from the traces (`TRACE_DIR`, each app's folder on a host, or the trace store), newest first by their last write, 25 to a page. Filter by the caller's last four digits, a date range (the viewer's days), the app, a task and how the call ended: handled, to a person (with the reason), hung up (with where: the task and step, or the greeting) or an error (including a call with no end recorded that has written nothing for half an hour). A click opens the call's replay as before, with Back to the list as it was.

- **Insights** is how the line is doing, for a range (today, yesterday, the last 7, 30 or 90 days, or dates of your own, at most 92 days) and an app or all of them: the calls, by the hour for a range of two days or less and by the day beyond, with the most in progress at once (every app's calls together, to the minute: the most calls in progress in any one minute, so two calls in the same minute count as two even if one ended as the other began; a call already going when the range began is not counted); containment as Live counts it, with hang-ups and errors apart; the calls that went to a person by the handoff's reason, and the calls hung up by the last question the caller heard (the task and step in the app's console labels, or the greeting); where callers struggle, per question asked (a slot by its label, what the caller wants, a confirmation, the one-time code): re-asks (a slot asked again after an answer that did not fill it), silences (counted on the question asked before them) and slots that ran out of attempts; each task started against finished, with the time a finished one took; call length (the average, and how many in each band); minutes on voice calls; the decision model's cost, exact from the traces, and the carrier's when its rate is set (`CARRIER_RATE_PER_MIN_TWILIO`, `CARRIER_RATE_PER_MIN_TELNYX`, in dollars a minute; with neither set no carrier cost is shown at all), with the cost per call and per handled call; safety: the injection screen's hits, the gate's step-ups, and its refusals by the rule that refused; the calls routed on business hours: those a route rule reading the hours (routes.yaml) sent somewhere, by the point, whether the rule asked for open or closed, and what followed; and, for an app with a knowledge base, the questions it did not answer, counted by `kb:gaps`' own rules, with that command to see the callers' words. The carrier's cost is an estimate of the automated part of the inbound call only: the time with a person after a transfer, and the transfer's own dialed leg, are not in it (the server does not see them). Each voice call's length is rounded up to the minute, as carriers bill, and priced at the rate of the carrier it came in on (which the server logs as each call starts; a call recorded before that names none, and its minutes are counted, not priced); the carrier's invoice is the bill. Each chart is drawn by the page itself as inline SVG, every mark with its number on hover, and each has a table view (As a table) for a screen reader or a closer look; the ranges are your days, and the figures are kept by the server's hours (UTC), so in a time zone whose offset is not whole hours a range starts half an hour off.
- **Generated wording**, for an app that generates lines ([16](16-generated-wording.md)): a call's detail shows under each agent line each line the app generates, said generated with the fixed line it stands for beside it, or said fixed and why (the share's fixed group, a situation the line is not generated in, the screen, or a check that failed); a framed line's span is shown by its name, with its exact content beside it. Insights adds a card comparing the calls served generated with those served fixed (`RENDER_SHARE`): containment, re-asks a call, the share with a frustrated caller, call length and the models' cost a call; each generated line's fallback rate and latency; and what the lines cost, in the cost beside the decision model's. Counts, durations and dollars only, as every figure: never a line's words.
- **Knowledge** is each app's knowledge base at a glance, read only: its passages by state as `pnpm kb:status` counts them (approved and fresh; stale because the source changed, or edited after approval, both withheld; never approved; approved outside `kb:approve`), as this server loaded them (a passage approved since it started is said once it starts again); the drafts waiting in `kb/pending`, counted when the server knows the app's folder (a host's apps, or the folder the server runs in); and the unanswered questions of the last 7, 30 or 90 days by their nearest topic, the most asked first, with how many. Only counts and topics: the callers' words, ranked with the fix for each, are `pnpm kb:gaps` at the terminal. Approving stays a person's, at their terminal (`pnpm kb:approve`) or on the local review page (`pnpm kb:review`).
- **Health** is whether the line is healthy: the servers heard from in the last two minutes (with `SESSION_STORE=postgres` every server says it is up every 30 seconds, with its calls and chats, through the notices; on one machine, this one) with their calls and today's reconnects and fallback dials (a fallback dial is a call the server put through to a person itself: stopping or draining, a store it could not read or reach, a session it cannot read, a token it could not save, a call past its reconnects; never a handoff the dialog decided; each server counts its own, by `TIMEZONE`'s day); `/health`'s numbers (sessions, those ended and kept a while, chats, draining, the trace and audit folders' sizes, the free space and its warning, trace writes failed); the decision model's latency over the last hour (the median and the 95th percentile of every ask, from the console's bus, so every server's with a shared store); and the audit verified on demand: **Verify the audit now** walks every hash chain as `pnpm audit:verify` does (the day files, or the database with `AUDIT_STORE`), without holding up a call, one verification at a time (a second asked while one runs gets its answer), and the page keeps the last result.

**The daily figures.** Insights and the Knowledge page's unanswered questions are worked out from the traces a day (UTC) at a time and kept beside them: on one machine a small JSON file per day in the trace folder (`<TRACE_DIR>/.figures/<day>.json`, each app's folder on a host), on the trace store an object beside the day folders (`<prefix>.figures/<day>.json`, so no day folder's listing grows with them). A day's file holds counts, durations and dollars by the hour, and how many calls were in progress in each minute (for the most at once), keyed by what the app is made of (a form, a slot, a rule, a handoff reason, a topic, a carrier, a route) and, for where a caller hung up, the form and what was asked by their ids, said in the app's current labels when shown; never a value a caller gave or a word they said, and no call's own time (its fingerprint of the traces is a count and a hash, the time a call in progress settles is rounded up to the hour, and an unanswered question's latest is its hour). Each number is checked as a file is read, and a file that does not read is worked out again. With it are the version of the figures, the fingerprint of the traces it came from (how many, their bytes, their newest write) and, while a call of the day has no end recorded, when it will be taken for ended (half an hour after its last word). A day is open while its traces can still change (on one machine until a day after its end, the longest a call lasts; on the store until the day before yesterday; each with an hour's margin for a late write) or a call of it is still in progress: an open day is taken from memory for a minute while no call ends, then its traces are listed again (names, sizes and times only) and its figures worked out again when they changed or a call it held in progress is now taken for ended. Then the day is closed, and final: a trace written for it later is not counted, and its file is its record, never listed or worked out again, and it outlives the traces (a trace retention, `TRACE_MAX_GB` or a store's lifecycle rule removing them changes nothing it shows) under a retention of its own, `FIGURES_RETENTION_DAYS` (unset: kept; the figures hold no caller's data). A day older than it is neither read nor worked out (Insights names those days), so a figures retention shorter than `TRACE_RETENTION_DAYS` never has a day worked out again only to be swept; the server warns at start when it is shorter. A newer server worked out with another version of the figures works a closed day out again while its traces are there; once they are gone, it shows the day from its older figures where it can read them, and says which days those are (their peak at once is each app's own, added) and which it could not read. A day is worked out once at a time for the same traces (a second asker waits for the first), reading a few traces at a time with the server's calls let run between; a range's calls are sorted into their days in one pass, and only the days still open are listed again; a figures file that cannot be written is worked out again next time, and its day is not closed. One Insights read and one Knowledge read run at a time per session (a second is refused with 429, and the page waits its turn); naming an app the host does not run is refused (400). In memory each day kept is its sums, its calls by the hour and its counts by the minute (2,880 small integers, about 6 KB: a quarter of one app is under 1 MB; 2,000 app-days at most), and a quarter's range is added up a few days at a time with the server's calls let run between; the figures by the hour, which a range starting or ending inside a day needs, are kept for 64 days and otherwise read back from the day's file.

How the Calls page reads the traces: the list of calls comes from names alone, so a date range narrows them before any call is read: a file is a candidate only if it was last written from the range's start to a day after its end (a call is never longer), and on the store only the day folders in the range, a day either side, are listed. A call's summary is read from its trace and frame log, redacted as a replay is, for the calls on the page shown, or, for a filter a name cannot answer (the last four, a task, the ending), for the calls newest first until the page is filled. Each summary is kept in memory for the server's run (the 20,000 used most lately), so a call is read once; one request reads at most 1,000 calls, and a page that stopped there says so: searching again goes on from where it stopped, as what it read is kept. The traces are read without holding up the server's calls (a few at a time, letting a turn run between), one search at a time per session (a second while the first runs is refused with 429, and the page waits its turn), and today's figures are worked out again only when a call has ended or a minute has passed. Nothing is written for it.

Every row holds only what the console already shows: the number by its last four, the app's labels for what was asked, never a value a caller gave. The Live list is worked out on the server from the events the console already carries, so a viewer of the list never receives a call's whole history; a call's detail receives that call's events alone (`/dashboard/events?call=<id>`). Opening the list or a call's detail counts as opening the live feed in the access log (its first open in a session); a call's detail is recorded under that call too, the first time a session opens it (`live`, as a replay is `replay`); a search by a caller's last four is recorded with its date range (`calls_search`); and a replay from the Calls page is recorded as every replay is. Insights, Knowledge and Health are recorded the first time a session reads each (`insights`, `knowledge`, `health`): they show counts, not calls, so a page's later reads (another range, a refresh) are not; every verification of the audit asked for is recorded (`audit_verify`).

Each console tab keeps two event streams open (the Live list's, and a call's detail's while it is shown). A browser opens at most six connections to one server over HTTP/1.1, so on a plain connection (a laptop, an SSH tunnel) three console tabs are the most at once; through a tunnel that speaks HTTP/2 (Cloudflare's) there is no such limit.

The console fits a phone's width: up to 820 pixels wide the lists become cards, a call's columns stack, the pages of figures put their cards in one column (a wide table scrolls inside its card, never the page), and the header (the menu and Sign out included), the call's bar and the replay bar wrap.

**What protects it.** Without a session, `/dashboard` sends the browser to the sign-in page, which shows nothing of the app or of any call, and everything else under `/dashboard` (the live feed and the Live list's, the traces, a replay, the Calls page's list, today's figures, Insights, Knowledge, Health and the audit's verification) answers 401. Codes are kept only as SHA-256 and compared in constant time; a used, expired, replaced or unknown code is refused the same way. A sign-in or sign-out form from another site's page is refused (by its `Origin`, and by `Sec-Fetch-Site`, which a browser sends whatever the page's policy). Failed sign-ins are limited: ten in a quarter of an hour from one address, and a hundred through the tunnel as a whole, after which an attempt is refused (429) without being looked at; a request made on the machine itself is held only to its own address's limit, so the owner can always sign in. The address is read as `CONSOLE_CLIENT_ADDRESS` says. `auto` takes `cf-connecting-ip`, which Cloudflare's edge sets whatever the client sent, else the last `x-forwarded-for` entry, the one the proxy in front added, else the socket's. That is right for Cloudflare's tunnels; behind another tunnel a client could send a `cf-connecting-ip` of its own and choose the address it is counted under (the limit for everyone still holds), so name the header your tunnel sets: `cf-connecting-ip` for Cloudflare, `x-forwarded-for` for ngrok or another proxy that appends the address it saw, and `remote` when nothing sits in front of the server. Every answer under `/dashboard` carries a Content-Security-Policy (nothing from anywhere else, the page's own script and style only by a nonce, no framing), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. The app's own local-only pages (its chats) stay local only either way. `pnpm diagnose` checks, through the tunnel, that `/dashboard` sends to the sign-in page and its data answers 401.

**The access log.** With `CONSOLE_AUTH=token`, the audit records who looked, as `console_access` entries on channel `console`: each link made (`link_made`, at start or by `console:link`), each mint refused (`link_refused`), each sign-in (`sign_in`) and refusal (`sign_in_refused`, with why: `used`, `expired`, `replaced`, `unknown`, `malformed`, or `rate_limited` once per lock), each sign-out, the live feed's first open in a session (`live`), the first open of each call's own detail in a session (`live`, under that call's id), every search of the Calls page by a caller's last four (`calls_search`, with the last four and the date range), the first read of Insights, Knowledge and Health in a session (`insights`, `knowledge`, `health`), every verification of the audit asked from Health (`audit_verify`), and every replay of a stored call (`replay`, under that call's id, so a call's audit shows who watched or replayed it). An entry names the session by a short hash of its id and a code by a short hash, never the cookie or the code, with the address and whether it came through the tunnel or from the machine. The entry is written before the answer, so an access the audit could not record is not served. One owner, no roles: roles and many users are for later (design §8).

### 14.10 Keeping the disk in check

The retention policy. A server writes two files per call (its trace and its frame log), one audit file per UTC day, and, under a service manager, its own log. Unset, nothing is removed, as before these options: every trace and audit day is kept, and the log is wherever the service manager puts it. `pnpm configure` writes a policy into a new settings file, each line a setting to change:

```sh
TRACE_RETENTION_DAYS=30    # traces and frame logs last written more than 30 days ago go
TRACE_MAX_GB=5             # and past 5 GB, the calls written least recently go first
DISK_WARN_FREE_GB=2        # /health and the log warn when less than this is free
LOG_MAX_MB=10              # the server's own log, where LOG_FILE names one, rolled at 10 MB
LOG_KEEP=5                 # keeping 5 rolled files beside it
# AUDIT_RETENTION_DAYS=    # the audit is a record: set only how long it must be kept
```

- **Traces, by time and by size.** `TRACE_RETENTION_DAYS` removes a call's trace and frame log once last written more than that many days ago; `TRACE_MAX_GB` then removes the calls written least recently, each whole, until the traces are under it. Never a live call's files. Both are swept at startup and once an hour; the log says `retention: removed N trace files, M audit days` (and how many of them went for the size bound). On the trace store ([14.14](#1414-many-servers-on-one-database)) the same: whole day folders past the days, then the calls written least recently past the size; the bucket's own lifecycle rule (expire objects under the prefix after N days) is the store's native way, and needs no server. The traces are what `pnpm kb:gaps` reads to find the questions a knowledge base did not answer, so archive them first if it should still read them.
- **The audit, by time only, never by size.** `AUDIT_RETENTION_DAYS` removes audit day files older than that (never today's); with the audit in Postgres, a call's chain whole once its newest entry is past the days, and the days' anchors. Deleting an audit day ends its record, so the server warns at startup when it is set: keep it as long as the record must be kept. No size bound removes the audit: watch the free space instead.
- **The free space.** `DISK_WARN_FREE_GB` (in gigabytes; a fraction such as `0.5` works) adds `freeBytes` and `low` to `/health`'s `disk`, from the disks the trace and audit folders are on, and says `WARNING: ... free` in the log once an hour while it is low. With any retention or this set, `/health` reports `disk` (`traceBytes`, `auditBytes`, measured at most once a minute) for a monitor; it measures the local folders only.
- **The server's own log.** `LOG_FILE` makes the server append everything it prints (stdout and stderr) to that file, which it rolls past `LOG_MAX_MB` (default 10) to `<file>.1`, `<file>.2` and so on, keeping `LOG_KEEP` (default 5); a relative path is from where the server runs. What it prints goes where it always went too. `pnpm service` sets `LOG_FILE` for launchd on a Mac, whose own output files would only grow ([14.6](#146-an-always-on-machine)); launchd's `err.log` beside it then holds only what fails before the server reads its settings (pnpm not found, say), and is not rolled; systemd keeps the journal, which it rotates itself. One process writes a `LOG_FILE` (a second is refused, naming the first): give each server its own.
- **A trace that cannot be written never fails a turn.** A full disk, or a trace folder removed or not writable, is logged (at most once a minute, with how many since) and counted on `/health` as `traces` (`failures`), and the call goes on; a turn whose audit cannot be written still fails, as the audit is the record. This is a change in behaviour on one machine (before, a trace write that failed failed the turn, and the caller heard "please say that again"); with a disk that works, every line is written as before.

`pnpm audit:verify <audit folder>` checks each day file's hash chain and exits 1 at the first break. `pnpm diagnose` says the policy in one line. The sessions folder needs no sweep or backup: it holds only the calls under way.

### 14.11 Updating and restarting

Update on purpose (the project is pre-release, and its APIs change), and note the commit you last ran well so you can go back: `git pull`, `pnpm install`, `pnpm check`, the app's tests, the widget's build if you serve it, then restart through the service manager (`systemctl --user restart <unit>`, `launchctl kickstart -k gui/$(id -u)/<label>`). The restart drains as in [14.6](#146-an-always-on-machine): with the file store a call still live after `DRAIN_MS` is handed over and resumed ([14.7](#147-surviving-a-restart)); with the memory store it is put through to `HANDOFF_NUMBER`, so check `/health` says `"sessions":0` first. A version whose `SESSION_SCHEMA` differs from the one that saved a call puts that caller through to a person rather than resume them.

### 14.12 The options

Every option here has a default that keeps the behaviour a deployment had before it existed: nothing is saved, nothing is swept, the console stays on the machine. Two options are exceptions, each the maintainer's decision: `RESUMED_AFTER_MS` (below), and `END_PLAYBACK_FACTOR` (below, decided 2026-10-13), whose default of 2 lets a call ending on a line wait up to twice its estimate (plus `END_PLAYBACK_MARGIN_MS`) for the carrier's report that it has played, where before it waited the estimate alone and cut a slow voice's goodbye on a live call (`END_PLAYBACK_FACTOR=1` restores the old wait). One behaviour changed too, also the maintainer's decision: a trace that cannot be written is logged and counted and never fails a turn ([14.10](#1410-keeping-the-disk-in-check)). The server checks each at startup and refuses to start, naming the variable, when one is malformed. Each app's `.env.example` lists them, commented, with their defaults.

### 14.13 Writes that are never done twice

A call resumed after a crash may run a write again: the turn that filed a report ran, the server went away before it saved the call, and the restarted server resumes at the summary, where the caller says yes again. A tool that writes declares `idempotent: true`, and its `run` is given `ctx.idempotencyKey`: the first 32 hex characters of the SHA-256 of the JSON array `["tool", call id, form, confirmed, tool]`, where confirmed is the hash of the values the caller confirmed at the summary (or, for a call with nothing confirmed, of the call's params as canonical JSON). The same confirmed write on the same call has the same key however often it runs; any value changed makes another. Pass it to the system the tool writes to, which keeps the keys it has seen and answers a repeat with what it did the first time. An illustration, shaped like the engine's own test app's `createReport` (`testing/testkit/domain/tools.ts`):

```ts
createReport: {
  params: ['accountId', 'missingNote', 'expectedDate'],
  idempotent: true,
  run(call, sys, { idempotencyKey }) {
    const r = (sys as Systems).createReport(call.params, idempotencyKey); // a key seen before: the report it filed
    return { value: { number: r.number }, summary: `report ${r.number}`, ref: r.number };
  },
},
```

A request to a downstream service (`code.services`) always gets a key, in `resolve`'s options (`opts.idempotencyKey`, over `["service", call id, turn, service, params]`, the turn being the one that left the request), which a service sends on as an `Idempotency-Key` header where its system takes one. The turn that leaves a request records it, with its key, in the call before the turn is saved and before the request is sent; a call waiting on the answer when its server went away keeps it, and the restarted server sends it again, once, with that same key, after the `resumed` line. Nothing changes for a tool without `idempotent`. The engine only makes and passes the key: a system that ignores it may still do a repeated write twice. What goes into each key is a promise kept across versions: a key made another way would make a retry look new.

### 14.14 Many servers on one database

One machine is the right answer for most lines. A business that wants a deploy, or a server that dies, not to end its calls, or whose calls outgrow one machine, runs several servers on one Postgres: `SESSION_STORE=postgres://<user>:<password>@<host>:5432/<database>` (or `postgresql://`) on each. A call then goes on on whichever server the carrier reaches. When the server running it dies, the carrier's reconnect, counted in the database, lets another take it over at once; when that server drains for a deploy, it gives its calls up as their sockets close, and another takes each at once. The caller hears the question they were on, with every value they gave still on the form, and the `resumed` line before it when the silence was long enough to notice (`RESUMED_AFTER_MS`, below).

**Setting it up.** Any Postgres you run or rent. The server connects with the `pg` package, an optional dependency of the engine that a normal install has (`pnpm add pg` in a project installed without it; the server says so if it is missing). Point every server at the same database, each with its own `SERVER_ID`, behind one balancer that sends a carrier's webhooks and sockets to any server whose `/ready` answers 200, with WebSockets allowed and an idle timeout longer than your longest call, and no sticky sessions (a carrier's webhooks are stateless). Every server has the balancer's hostname as its `PUBLIC_HOST`.

**The tables, and the user.** The first server to start against an empty database makes the tables (`dw_schema` with each part's version, then `dw_calls`, `dw_call_leases`, `dw_chats`, `dw_tokens`, `dw_notices` and `dw_sweeps`, and with `AUDIT_STORE` naming it, `dw_audit_entries`, `dw_audit_anchors` and `dw_audit_roster`), so its user needs to create tables in the schema that first time. Every start after reads their versions first and runs no DDL; tables an owner made are taken as they are, even without their version row. So the servers may use a user with only these rights (make the tables once with an owner, or start one server once with a user that may create):

| Table | Rights the servers' user needs |
|---|---|
| `dw_schema` | `SELECT` (and `INSERT`, only if an owner made the tables without their version rows) |
| `dw_calls`, `dw_call_leases`, `dw_chats`, `dw_tokens` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| `dw_notices` | `SELECT`, `INSERT`, `DELETE`, and `USAGE` on the sequence `dw_notices_id_seq` |
| `dw_sweeps` | `SELECT`, `INSERT`, `UPDATE` (which server runs the trace store's hourly sweep) |
| `dw_audit_entries`, `dw_audit_anchors`, `dw_audit_roster` (`AUDIT_STORE`) | `SELECT`, `INSERT`, and `DELETE` for `AUDIT_RETENTION_DAYS` |

Each server opens at most 12 connections to `SESSION_STORE`'s database (one held for `LISTEN`, the rest for the stores' questions, and the audit's when `AUDIT_STORE` names the same database), and 5 more to `AUDIT_STORE`'s when it names another: set the database's `max_connections` above servers times 12 (plus 5 each) and what else uses it. A database whose tables are at another version is refused at startup, with what to do; nothing is migrated without your asking. `pnpm diagnose` checks that the database answers, the tables' version, that the server can take a test lease and give it up and write a notice (in a transaction undone), and says how far the database's clock is from this machine's; neither it nor the server ever prints the password.

**One owner per call.** One server runs a call's turns at a time, under a lease on the call in `dw_call_leases`, timed by the database's clock (so the servers' own clocks are never compared):

- The server a carrier's socket reaches takes the call's lease and reads the call in one transaction. It takes it when no one holds it, when its holder gave it up, when its holder's lease has lapsed (`CALL_LEASE_MS` without a renewal), or when a reconnect has been counted for the call since its holder took it: the carrier only reconnects a call when it has given up the socket it had, so its holder is no longer running it, alive or not (a crash, or a socket the carrier abandoned without closing). A holder that saw the socket close while a turn ran marks its lease closing, and then the claimer waits for it to finish the turn and give the call up. Otherwise it waits, backing off, until a deadline of one and a half holds, and then puts the caller through to a person, never at a silent line.
- The holder renews every lease it has every third of `CALL_LEASE_MS`, in one statement for all its calls, and saves and removes the call only while it holds the lease: a save or a removal the database refuses means another server has the call, and this one lets it go, closing the socket it had. A turn that was still running there when the call moved ends nothing and revokes no token: it acts only on its own records: its trace and audit day files, or, with the audit and traces shared, its own trace segments and its audit entries, chained in order after the other server's.
- When the call's socket closes, its holder gives it up once the turn running has saved (waiting up to a quarter of a hold less than a claimer waits, and never for a service's answer: the request is saved with its key, and whoever takes the call sends it again). A drain and a stop give up every call they hold, marked as given up by a stop.
- The carrier's callback, on any server, counts the reconnect in the database in one statement, so two callbacks never count one and `RECONNECT_LIMIT` holds across servers.
- A transfer whose `end` is held for its line to play (`END_AFTER_PLAYBACK`) is saved with the call until the `end` is sent; if the socket closes first, whichever server the carrier's callback reaches takes it from the database, in one statement, and puts the caller through, once. (So does a server restarted on the file store.) A callback saying the caller hung up in the hold drops it, and the sweep removes one no callback took after two minutes.
- A write repeated after a takeover carries the same key ([14.13](#1413-writes-that-are-never-done-twice)): a service request the dead server had sent is sent again once, with its key, and an idempotent tool's write, run by a server that died before it saved, is run again by the next with the key it had.
- Every question to the database has a deadline (`SESSION_STORE_TIMEOUT_MS`, default 2000, on the driver and on the server's side), and the connection is kept alive, so a database that stops answering fails fast: a socket's setup it cannot answer ends toward a person, and a callback answers with the handoff number within a few times that, never a carrier's webhook timeout.
- `RELAY_PING_MS` (off by default) pings each relay socket and closes one that has not answered the last ping, so a socket the carrier abandoned without closing it is let go even before the carrier calls back. WebSocket endpoints answer pings by the protocol (RFC 6455); turn it on once a test call on your carrier shows it does.

**What the caller hears.** The `resumed` line ("Sorry, I lost you for a moment.") is said by what the server that resumes a call knows of the caller's silence:

- A reconnect to the server that has the call, or to one it handed the call to as its socket closed (a clean hand-off), never hears it, as on one machine.
- A call its server let go cleanly as it stopped (a drain, a close; on one machine, a planned restart) hears it only when the silence was longer than `RESUMED_AFTER_MS` (default 1500): the time from the carrier's callback asking to reconnect to the setup of the socket that resumes the call. Twilio calls back as the relay session ends; that Telnyx does the same is an assumption of its adapter (`server/voice/telnyx.ts`, its assumption 1) for a live check to confirm. A quick drain hand-off passes unnoticed; a planned restart's pause (`RESTART_PAUSE_S`, default 5) is past the threshold, so its caller hears the line as before, and a pause set under it lets a quick restart pass unnoticed.
- A call whose server never let it go (a crash, a lapsed lease, a socket the carrier abandoned) always hears it, however quick the takeover: its caller's silence began before anything measured it.

`RESUMED_AFTER_MS=0` says the line wherever it was said before the option.

A turn still running when its socket closes is finished where it runs: the server marks the call's lease closing, finishes and saves the turn, and gives the call up, and the server the carrier reconnects to waits for that (up to its deadline) rather than take the call on the reconnect, so no turn runs twice and the caller hears where the turn got to. A turn that ends the call while no socket is there to hear it (a transfer or a goodbye) keeps its lines and its `end` with the call, and the server the carrier's next socket reaches says them and sends the `end`, once: the carrier's callback then puts the caller through where the turn decided, or hangs up after the goodbye. The same on one machine with the file store. A turn that takes longer than the wait is let go by its server, and acts on nothing the call shares from then on.

`CALL_LEASE_MS` (default 5000) is now the wait for the rare takeover no reconnect announces (a server that stopped renewing while its socket stayed up); a crash takes as long as the carrier's reconnect. Chats are kept in the database too, so a chat resumes on any server with its resume token.

**A deploy.** Stop one server at a time. Set `DRAIN_UNREADY_MS` to at least the time the balancer takes to see a 503: the stopping server says 503 that long while still answering new calls, then drains. Its `/ready` says 503 while it drains, so the balancer sends new calls and every callback elsewhere; after `DRAIN_MS` it closes its live calls' sockets, gives them up, and their carriers' callbacks reach the other servers. With several servers, `RESTART_PAUSE_S=0` hands each call straight on; keep `DRAIN_MS` longer than the balancer takes to see the 503. With the default pause, a callback that still reaches the stopping server is told to wait and connect again, and its socket then reaches another.

**The audit, the traces and the console.** Two servers appending to one day file would fork its chain, and two servers writing one trace file cannot, so with several servers these move off the machine too. Each is its own setting; unset, each is as on one machine.

- **The audit in Postgres:** `AUDIT_STORE=postgres://<user>:<password>@<host>:5432/<database>`, the same database as `SESSION_STORE` or another. Each call has a hash chain of its own (the same entries, the same redaction and the same hash as a day file's line, `seq` being the entry's place in its call's chain), and each time a call's chain grows its newest hash is anchored into the writing server's own chain for the day (`<day>/<server>`), so no server waits on another's anchors. Each day also has a roster: a server enters its chain for the day in it when it opens it, its head every ten minutes as it writes, and its head as it stops, so a server's whole chain for a day cut away is found. A call's entries are chained in one transaction under a lock on the call, so the servers that run it in turn, and a turn that outlived its server's hold on the call, are put one after the other and never fork it; nothing a turn did goes unrecorded. Every lock wait is bounded (`lock_timeout`, `SESSION_STORE_TIMEOUT_MS`). The console's access log (`console_access`, [14.9](#149-looking-at-calls-from-your-phone)) goes there too, chained per day. The first server to start makes the tables (`dw_audit_entries`, `dw_audit_anchors`, `dw_audit_roster`, with their version, 2, in `dw_schema`); later starts only read and insert. `pnpm audit:verify postgres://...` (or with `AUDIT_STORE` set) walks every call's chain, every server's anchors for every day and every day's roster, checks each anchor names an entry that is there as anchored, each call's newest entry is anchored, each roster entry names an anchor that is there and every server's anchors for a day are in its roster, says the database with its password masked, and exits 1, saying every break. What the audit cannot show by itself, as a day file cannot its own last lines, is the newest few minutes cut away together: a server's anchors and entries written since it last entered its head in the roster (at most ten minutes, or since its stop), with the roster's own newest entries. An app's own pages append through `AppRouteDeps.audit`, whose `append` answers at once with day files and with a promise with `AUDIT_STORE`: take either with `whenChained` (from `dialogwright`).
- **Traces on S3-compatible storage:** `TRACE_STORE=s3://<bucket>/<prefix>` with `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` and, for a store reached by path (MinIO), `S3_FORCE_PATH_STYLE=on`. Each server writes its own segments of a call under the day the call started and its id (`<prefix><yyyy-mm-dd>/<call>/`; a call that crosses midnight stays under the day it started), named by the turn they start at and the reconnect that moved the call there, so a call that moved reads on in order without comparing the servers' clocks. A chat is the same, its restores (saved with the chat) in place of the reconnects. Two exceptions: frame lines a server writes after the reconnect was counted, within the same turn as the next server's, are ordered by server rather than by time; and a record a server writes after it let the call go (a turn that outlived its hold) is kept in a segment of its own, marked `outlivedHold`, shown on the console as a late turn, and passed over by `kb:gaps` and the turn counts, since the server that took the call ran that turn too. The console lists the newest days only; the console's list and replay, `--replay s3://<bucket>/<prefix>/<call>` in the text harness, and `kb:gaps --traces s3://<bucket>/<prefix>` and `kb:review`'s Gaps tab (both read `TRACE_STORE` when no `--traces` is given) all read them through one reader, so they agree. Requests are signed with AWS Signature Version 4 by the engine's own code (no SDK), with a deadline of ten seconds each. A turn's record is written at once and frame-log lines within a second; a write that fails never stops the call: it is logged (once a minute at most, never a key), counted on `/health` as `traces` (`failures`, and `dropped` past four megabytes waiting for one call or 64 for the server), and tried again under the same name, so a write whose answer was lost is never written twice; a stopping server writes what is waiting, for up to five seconds. A listing longer than a thousand pages is refused rather than read in part. Retention ([14.10](#1410-keeping-the-disk-in-check)) removes whole day folders, and `TRACE_MAX_GB` one day folder at a time from the oldest; with servers sharing a database, one of them runs the store's sweep each hour (`dw_sweeps`); a day folder of more than a thousand listing pages (a million objects on S3) is refused; the bucket's lifecycle rule (expire objects under the prefix after N days) does the same without a server. A server that dies loses at most its last second of frame lines.
- **The console across servers:** with `SESSION_STORE=postgres://...`, each server's console events go to the others through the database (a row in `dw_notices` and a `NOTIFY` of its id, as a console event can be larger than `NOTIFY`'s 8000 bytes), redacted exactly as on one machine, so one console follows every server's calls, as one machine's follows its own: its Live list has the calls in progress on every server, from when the console's server started. A server that starts (or restarts, or joins) while calls are in progress lists each of them once it next hears of it, by the reconnect a moved or resumed call makes; a call that stays where it was shows up at its next turn only if this server saw it start, else at its next reconnect or not at all (a chat resumed after a restart is not listed until it ends). A call whose server died with it leaves the list after half an hour with no word ([14.9](#149-looking-at-calls-from-your-phone)). A chat resumed on another server closes its old socket on the first, as a resume on one server does. A server lets a chat go only for an announcement later than its own restore of it. Each server also reads the notices every 30 seconds, so one whose `NOTIFY` was lost is still read. Every 30 seconds, and as it starts listening, each server also says it is up (a notice with its name, its calls and chats, and today's reconnects and fallback dials, numbers only), and answers a server it hears from for the first time with its own, so every console's Health page lists the servers on the database ([14.9](#149-looking-at-calls-from-your-phone)). The notices' rows, the console's events as redacted as on the console itself (the callers' words among them), stay in the database for ten minutes, by its clock, and are then swept; they are never a record.

`pnpm diagnose` checks each: that the audit's database answers, its tables' version, and that an entry can be written (in a transaction undone, so a check never writes to the audit); and that the bucket takes a small test object under the prefix, lists it, gives it back and deletes it; never a password or a key.

**In containers.** The repository's `Dockerfile` builds the image of one of its apps (`APP`, default `clinic`): Node 22 pinned by version and digest, the workspace installed from the lockfile (`pnpm fetch`, then an offline, frozen install), and the app's server run from `src/` with tsx's loader, as `pnpm serve` runs it. A project of its own gets a `Dockerfile` and a `.dockerignore` from `npm create dialogwright` too (`npm ci` from its lockfile, the folder checked with `npx dialogwright check` as it builds). Both images run as the non-root `node` user, under tini, so a `docker stop` (SIGTERM) reaches the server and its drain runs, and both check `/ready` as their health check (503 while draining). No key and no settings file is in either: each `.dockerignore` is an allowlist (everything left out, then the manifests, the lockfile and the app's folders let back in, and within them dotfiles, env files under any name, keys, certificates, logs and records left out again), so a settings file or a local tool's settings never reach the image even when only your own global gitignore hides them; a file with an ordinary name inside an app's folders still does, so keep such files elsewhere. Every setting is given at run time, by `-e`, an env file, or the platform's secrets. Docker kills a container 10 seconds after `docker stop` unless told otherwise: give the drain its time with `--stop-timeout` (`DRAIN_UNREADY_MS` and `DRAIN_MS`, 30 seconds by default, and about 15 more), as below.

```sh
docker build --build-arg APP=clinic -t dialogwright-clinic .
docker run --rm --stop-timeout 45 -p 3000:3000 -v dialogwright-data:/data -e PUBLIC_HOST=<your hostname> -e TWILIO_AUTH_TOKEN=<token> -e HANDOFF_NUMBER=+1555... dialogwright-clinic
```

A container keeps a server's own records under `/data` (`TRACE_DIR=/data/traces`, `AUDIT_DIR=/data/audit`, the console's sign-in link file beside them, and `SESSION_STORE=file:/data/sessions` if you choose the file store): mount a volume there for one container, or give it the shared stores above for several. An app with a knowledge base whose embedder needs the model's weights (the utility's) finds them under `/home/node/.cache/dialogwright/models`, or where `DIALOGWRIGHT_MODEL_DIR` says: mount the cache `pnpm kb:model` fills, or retrieval falls back to keywords with a warning. `NODE_ENV` is left unset, as on any machine, so that warning does not stop the server: set `DIALOGWRIGHT_REQUIRE_EMBEDDER=1` for an app with an embedder, and a server whose model is missing refuses to start rather than answer with keywords alone.

**Two servers in compose, and the test.** `deploy/compose/docker-compose.yml` is the stack in small: Postgres, an S3-compatible store (RustFS; MinIO's own images are no longer published for anonymous pulls, and any store that speaks S3 with Signature Version 4 does) and its bucket, two servers of the app (`app-a`, `app-b`, each its own `SERVER_ID`) sharing `SESSION_STORE`, `AUDIT_STORE` and `TRACE_STORE`, and HAProxy in front (`deploy/compose/haproxy.cfg`). Every image is pinned by version and digest, each with builds for amd64 and arm64. `pnpm multi:test` builds the image, starts the stack with secrets it makes for that run (the database's password, the store's keys, the carriers'; none is written anywhere), and runs the takeover driver against it from the machine running Docker: on Twilio and on Telnyx, a call placed through the balancer whose server is killed (`docker compose kill`, SIGKILL) and one whose server is stopped (`docker compose stop`, SIGTERM: the drain, then exit 0), each taken over by the other server. The call is the clinic's cancellation, its server going once the summary has been read back: the server that goes has run the lookup, and the one that takes the call over runs the write. The server goes between turns (the driver waits for the reply and for the turn to be saved and traced); a server that dies in the middle of a turn is the in-process test's (a request sent again with its key, an idempotent write run again by the next server), since the clinic's systems live in each container and a write repeated there could not be seen. Each is held to what the in-process test holds: the caller hears the question they were on (with the resumed line after a crash), every turn is in the joined trace once across both servers' segments, no tool runs twice, the whole audit verifies with the call's newest entry anchored, the other server's console followed the call, and nothing of the call is left in the tables. A drain is also asked for a new call directly, past the balancer: while `/ready` says it is stopping (`DRAIN_UNREADY_MS`, 2000 in the stack, past HAProxy's detection of a check every 500 ms) it answers the call as usual, and once it drains it puts the caller through to the handoff number. It then writes the stack's logs to `deploy/compose/logs/` and takes the stack down with its volumes and network, passed or not (`--keep` leaves it up); the image stays, for the next run, and the untagged images a rebuild leaves (Docker's legacy builder leaves one per layer) are removed, never another's. Without Docker it stops at once and says so; `pnpm multi:test --in-process` runs the same driver, call and checks against two servers in one process, on PGlite and a fake S3 store. The driver (`packages/dialogwright/src/testing/multi`) is also in the normal suite, against two in-process servers of the testkit. A GitHub Actions workflow (`multi.yml`) runs `pnpm multi:test` weekly and by hand, never on a push, keeping the logs when it fails or is cancelled; it has not run yet (it runs once the branch is pushed). The stack is a test stack, not a deployment: its console is served past the loopback rule with no sign-in (`CONSOLE_LOCAL_ONLY=off`) for the driver to read it, its signature checks are off (the driver is the carrier), and its ports are published on `127.0.0.1` only.

**In production.** The same image, two or more of it, behind a balancer:

- **The database and the store:** a managed Postgres (the connections above: servers times 12, plus 5 each for a separate audit database) and a managed S3-compatible bucket (AWS S3, Cloudflare R2), each with credentials for the servers alone; a bucket lifecycle rule can expire the traces.
- **The balancer:** health-check each server on `/ready` (every half second to a few seconds) and send nothing new to one answering 503; carry WebSockets, with an idle timeout longer than your longest call (the stack's HAProxy has `timeout tunnel 2h`); no sticky sessions and no hashing on the caller (the server a call's socket reaches takes it); and send a request that could not reach a server to another (HAProxy's `retries` and `option redispatch`). Terminate TLS there for `PUBLIC_HOST`.
- **Before the drain:** `DRAIN_UNREADY_MS` at least the time the balancer takes to see a 503 (its check interval times the failures it needs), so a new call it still sends meanwhile is answered rather than put through to a person; or the platform's own deregistration delay (a target group's, say) or a `preStop` sleep that takes the server out of the balancer before the SIGTERM.
- **The drain:** `RESTART_PAUSE_S=0`, so each drained call goes straight to another server, and `DRAIN_MS` as long as calls should be let finish where they are (the stack runs 4000; a deployment whose calls should mostly finish where they are uses minutes, about 15 for long calls).
- **The grace period:** the platform's time between its SIGTERM and its kill longer than `DRAIN_UNREADY_MS` plus `DRAIN_MS` plus about 15 seconds. Common defaults are lower: Docker's `docker stop` 10 seconds (`--stop-timeout`, or compose's `stop_grace_period`; the stack's is 30 seconds), Kubernetes' `terminationGracePeriodSeconds` 30, Fly's `kill_timeout` 5 seconds; set them above the drain, or a server is killed mid-drain and its calls are taken over as after a crash.
- **An app with an embedder:** `DIALOGWRIGHT_REQUIRE_EMBEDDER=1`, with the model's cache mounted (above), so a server without the model refuses to start.
- **The console:** `CONSOLE_AUTH=token` on the servers, or the console kept to an internal network; never `CONSOLE_LOCAL_ONLY=off` with no sign-in, as the test stack has it.

**What holds, and what does not yet.** What the tests show, in one process with two servers on one PGlite and one in-process S3 store behind a balancer (`server/manyServers.e2e.test.ts`): a call survives its server crashing, draining, a half-open socket, a database that stops answering (to a person), a held transfer, and a turn that outlives its server's hold, on Twilio and on Telnyx; and across a crash and a drain, the call has one trace, joined from both servers' segments with no turn dropped or repeated (a late turn of a server that let the call go is kept, marked), one audit chain that verifies and is anchored in the day's chain, a console on the other server that followed it, and a chat resumed on the other server closes its socket on the first. The signing is held to AWS's published test vectors, and the trace store to a fake that checks every signature; AWS S3 and R2 themselves are for a live check. And under Docker (`pnpm multi:test`, run on an arm64 Mac with Colima; the weekly workflow on GitHub's amd64 runners has not run yet): servers in separate containers on a real Postgres with parallel connections and a real S3-compatible store, behind HAProxy, through a crash (SIGKILL) and a drain (SIGTERM) on each carrier, each between turns, with the same checks. Not shown by any test: a real carrier's reconnect timing (a live check) and a hosted platform's balancer. An app's own pages (`AppRouteDeps.traceDir`) still write traces to `TRACE_DIR`.

### 14.15 Several apps on one server: host.yaml

One deployment (one server, or many under [14.14](#1414-many-servers-on-one-database)) can run several apps, each reached by the numbers callers dial: a clinic's two lines and a utility's outage line on one machine, say, all from one owner's carrier accounts. A host file, `host.yaml` beside the apps, lists the apps and points each number at one; a call to any other number, or to none, reaches the default. Each app stays a folder of its own, with its own policy, prompts, tests, traces and audit. A server with no host file runs its one app exactly as before.

```yaml
# yaml-language-server: $schema=packages/dialogwright/schemas/host.schema.json
apps:                                     # each known by the id its own app.yaml gives it
  - apps/utility                          # a folder, from host.yaml's folder
  - { folder: apps/clinic, env: clinic.env }   # with its own settings file named (default: its .env)
  - { folder: apps/repairs, services: { scheduler: env.SCHEDULER_URL } }   # its services' URLs, by variable
  - { package: "@acme/repairs-line" }     # an app installed as a package
numbers:                                  # the number called -> the app's id; several numbers may name one app
  - { number: env.POWER_LINE, app: utility }
  - { number: env.CLINIC_LINE, app: clinic }
  - { number: env.CLINIC_LINE_ES, app: clinic }
default: utility                          # any other number, or none; default: the first app listed
```

**Each app runs as its own.** A call or chat in an app runs that app's tools against its own systems (`App.systems`, made once per app for the process, so a record one call makes is there for the next), its gate reads its own lookups, its traces and the console mask by its own slots, and with `JEV_CLIENT=heuristic` or `stub` its own client answers (the stub from its own fixtures' corpus, the heuristics alone where it has none). With `jev` and the cassettes the one model client is shared: a model knows no app.

**How a call finds its app.** The number called, as each carrier delivers it (Twilio's `To`, Telnyx's), is matched as a `called` condition matches it ([13.13](13-channels.md#1313-the-number-the-caller-is-calling-from)): a ten-digit national number matches its `+1` form, and a SIP address (`sip:+15551234567@pbx.example.com:5060`) by its user part. A number that matches digit for digit wins over a ten-digit match; when two listed numbers end in the same ten digits (a `+1` number and another country's), a call delivered as those ten digits alone reaches the first listed, and the server says so as it starts. The answer webhook picks the app and answers in it (its languages, its `startParameters`, its hints), and its start document names the app as the custom parameter `dialogwright_app` (an app's own `startParameters` may not take that name), so the setup starts the call in the same app on whichever server the socket reaches; a setup without it (a start document written before it) reads its own number called. A reconnect, a callback and a call another server takes over keep the app the call was saved in. The numbers live in the server's settings, never in YAML; the server refuses to start, with the fix, when one is unset or not E.164, or when two variables hold one number (a call to it could reach either app). An app's own `voice.numbers` (the number to the language) and its `called` routes still work inside the app: a host picks the app first, then the app's routes see the same number. Calls never move between apps: a call starts and finishes in its app, and a transfer goes to a person as each app's `transfer` says.

**Settings in two layers.** The server's settings file (the `.env` beside `host.yaml`, or the one `ENV_FILE` names) holds what every app shares: the carrier's secrets, the model and its key, `PUBLIC_HOST`, `PORT`, the stores, retention, the console's and the chat's settings, and the numbers `host.yaml` names. Each app's own `.env` (or the file its entry's `env:` names) is read only for the variables its own YAML names (`env.<NAME>`: its transfer targets, `startParameters`, `called` numbers, `voice.numbers`), its services' variables (host.yaml's `services`), and four server settings an app may give its own value: `HANDOFF_NUMBER`, `CHAT_AUDIENCE`, `CHAT_ISSUER` and `CHAT_JWKS_URL`. It is read only for that app, so `env.MAIN_LINE` in two apps can be two numbers; a variable an app names and its own file does not set is read from the server's settings, and never from another app's file. Precedence: for those variables an app's own file wins, over the process's environment too; the server's settings follow their own rule, a variable already in the environment winning over the server's file. The rest of an app's `.env` is not read by the server under a host: the server names what is there as it starts (names only), and `pnpm diagnose --host` does too: one of the server's own settings left there (a carrier's secret, a model's key, `PUBLIC_HOST`, a store's URL: any name the server's settings readers read) is a warning, since there it does nothing; any other name is the app's code's, said as information. The app's code reads its own settings with `ctx.env(name)` at call time (on every hook's, tool's and predicate's context, [chapter 4](04-what-stays-in-typescript-and-why.md#settings-ctxenv-never-processenv)): the whole of its own file, over the server's settings, the variables its YAML names and the rest. `process.env` is the server's: an app's code that reads it sees the server's settings only, and a constant read from it at a module's top level is read once, at import. Read a setting through `ctx.env`, inside the hook, the tool or the predicate. Replaying such a call in the text harness (`--replay`) reads the settings from the shell (with a model client, from the file `ENV_FILE` names): point `ENV_FILE` at the app's own settings file, or export what its code reads, so the replay's code reads what the call's did. `pnpm configure` still writes one app's `.env`, with the server's settings in it, as for an app alone; for a host, write the server's settings once in the `.env` beside `host.yaml` (copy them from one app's) and keep only each app's own variables in its `.env`, then add the app to `host.yaml`'s `apps` by hand: one line, and `pnpm check` checks it.

**Where a handoff goes.** An app with `transfer` targets puts its callers through to its own ([13.15](13-channels.md#1315-where-a-handoff-goes-and-what-goes-with-it-transfer)). One without goes to `HANDOFF_NUMBER`: its own, set in its own settings file, else the server's. With several apps, an app with neither its own targets nor its own `HANDOFF_NUMBER` hands off to the server's number, which may be another business's desk: the server warns of it as it starts, and `pnpm diagnose --host` does too. A drained or stopping server puts a new call through to its app's number in the same way.

**Downstream services.** An app's services (`App.services`) are reached at the URLs `host.yaml` names for it, `services: { <name>: env.<NAME> }`, each variable read from the app's own settings file (else the server's), so two apps' services of one name each have their own. A service with no URL is answered with no result, as when a launcher starts none; the server warns of each as it starts (a service run in the process, which needs no URL, may pass the warning by), and `pnpm diagnose --host` checks each URL `host.yaml` names. A launcher's own `ServerOverrides.serviceUrls` are the default app's alone under a host.

**Records per app.** Each app's traces are in `TRACE_DIR/<app id>/`, its audit day files in `AUDIT_DIR/<app id>/` (one hash chain per app per day, each entry naming its app in `app`, hashed with it), and the server's own audit (the console's sign-ins and replays, [14.9](#149-looking-at-calls-from-your-phone)) in `AUDIT_DIR/_server/`. With `AUDIT_STORE`, the audit is a chain per call as always, each entry naming its app; with `TRACE_STORE`, each app's traces are under the prefix `<prefix><app id>/`. Recorded clips (`CLIPS=on`) are in `AUDIO_DIR/<app id>/`, served at `/audio/<app id>/`. Retention is the server's, the same for every app: `TRACE_RETENTION_DAYS` and `AUDIT_RETENTION_DAYS` for each folder, and `TRACE_MAX_GB` bounding each app's traces, so one busy app never removes another's. `pnpm audit:verify AUDIT_DIR` walks every app's folder and the server's, and `pnpm kb:gaps --traces TRACE_DIR/<app id>` reads one app's traces. Plan the disk for the apps together: `TRACE_MAX_GB` and `CHAT_MAX_SESSIONS` count per app, so with N apps the traces may take N times `TRACE_MAX_GB`, and N times `CHAT_MAX_SESSIONS` chats may be open.

**Moving one app to a host.** A server that ran one app kept its records in `TRACE_DIR` and `AUDIT_DIR` themselves. Under a host they stay where they are: the console does not list them and retention does not sweep them, though `pnpm audit:verify AUDIT_DIR` still walks their day files. To keep them with the app, stop the server and move them into the app's folder: `mkdir -p TRACE_DIR/<app id> AUDIT_DIR/<app id>`, then move `TRACE_DIR/*.jsonl` into the first and `AUDIT_DIR/*.jsonl` into the second (each day file is its own chain, so a moved file verifies as it did). Entries written before the host name no app.

**Web chat.** With `CHAT=on`, each app's chat is at `/chat/<app id>`, and the default app's at `/chat` too, as on a server of one; the widget names its app with `data-app` (or `mount({ app })`, [13.7](13-channels.md#137-the-widget)). `CHAT_ALLOWED_ORIGINS`, the sign-in method and `CHAT_MAX_SESSIONS` are the server's settings (the session cap counted per app); a chat is resumed only at its own app's path. With `CHAT_SIGNIN=jwt`, each app may take tokens from an identity provider of its own: `CHAT_AUDIENCE`, `CHAT_ISSUER` and `CHAT_JWKS_URL` (its keys, https) in its own settings file, each else the server's, so an app whose portal signs in with another provider has its tokens checked against that provider's keys at its own `/chat/<app id>` alone. Each JWKS URL's keys are fetched and cached once, whichever apps share it. Two apps sharing one audience would take each other's portals' tokens, so the server warns of it as it starts, and `pnpm diagnose --host` does too; diagnose also checks each app's own `CHAT_JWKS_URL` (an https URL) and warns of one given without its own `CHAT_ISSUER`.

**The console.** One console shows every app's calls: the Live list and the Calls page have an app column and an app filter, each replay row starts with its app's name, the app filter in the header (`/dashboard?app=<id>`) shows one app's calls alone, on every page, and each call is shown in its own app's words, a call's detail with its app's name, mark and link buttons in the header ([14.9](#149-looking-at-calls-from-your-phone)). A replay is read from its own app's records (`/dashboard/traces/<call>?app=<id>`, as its row says), and with `CONSOLE_AUTH=token` its access entry names the app. The live feed's `call_started` event names the call's app as `app`.

**The commands.**

```sh
pnpm check host.yaml                          # its problems (an app folder missing, an app listed twice, an unknown app id, a number listed twice, a default that is no app), then each app's own check
pnpm start --host host.yaml                   # (or HOST_FILE, or host.yaml beside the apps) every app in one server, with the .env beside it; --app still runs one app
pnpm diagnose --host host.yaml                # the server's checks, the numbers, and each app's own variables as the server will read them
ENV_FILE=<path> pnpm service <launchd|systemd> --host host.yaml   # a service that runs the host's server
pnpm serve --host host.yaml                   # the server alone (dialogwright serve), what start and the service run
```

A bare `pnpm check` checks the `host.yaml` beside the apps too, and `pnpm check <file>` reads a file as a host file by its name (`host.yaml`, or the one `HOST_FILE` names) or its shape (a top-level `apps` list). The server of a host is `node <the engine's bin> serve --host <file>` (`bin/dialogwright.mjs`), run in the host file's folder, so a relative `TRACE_DIR` or `AUDIT_DIR` is beside it; `pnpm serve` alone reads the `.env` beside `host.yaml` when neither `ENV_FILE` nor `--env-file` names a settings file, as `pnpm start --host` does.

**What a host does not run.** Each app's code is imported from its folder (`app.ts` or `src/app.ts`, as `pnpm check` reads it), not its own launcher (`src/serve.ts`): what an app's launcher starts beside the server (a service it runs itself, its own pages such as the utility's chat demo) does not run under a host. A service running elsewhere is reached through `host.yaml`'s `services` (above). A deployment that needs a launcher's work writes a launcher of its own, with `loadHost` and `serverMain` from `dialogwright`: it starts what it runs, sets the variables `host.yaml`'s `services` names to their URLs, and then loads the host, so each app reaches its own. Its own pages (`ServerOverrides.routes`) are the default app's: its client, tools, audit, traces and services.

```ts
import { loadHost, serverMain } from 'dialogwright';

process.env.REPAIRS_SCHEDULER_URL = await startScheduler();   // the launcher's own service, named in host.yaml's services
await serverMain(async () => ({ overrides: { apps: await loadHost('host.yaml', process.env) } }));
```

**Many servers.** Each server behind the balancer runs the same `host.yaml` with the same settings; a call taken over by another server stays in its app ([14.14](#1414-many-servers-on-one-database)).
