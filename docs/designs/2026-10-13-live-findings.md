## A. Carriers

1. **A withheld number on Telnyx (privacy).** A call made with the caller's number withheld (`*67`) reached the server with the real number in `From`, and the privacy markers beside it (a caller ID of `anonymous`, a SIP From of `anonymous@anonymous.invalid`). The engine took the number as given and offered it back. The Telnyx adapter treats any of those markers as a withheld number: nothing kept, nothing offered, no call-start lookup, exactly as a call with no number. The markers arrive with the answer webhook and are carried into the call the way the app's id is. A captured webhook (its number replaced by one in the 555 range) pins it. Not an option: a number the caller withheld is withheld.
2. **Telnyx's voice on the relay element.** For an app with more than one language, the voice was written only on each language's element; Telnyx then said nothing at all, from the first line (three calls in three). The start language's voice goes on the relay element as well, for Telnyx; each language's element keeps its own, so a switch still changes the voice. Twilio is unchanged (it speaks either way). A test pins the document.
3. **Ending after the last line has played.** A call that ends with a line was hung up while Telnyx was still saying it: the wait for playback ended at the line's estimated length plus a margin, and Telnyx's own word that it had finished came later. With the carrier's playback events, the call ends on them; the estimate becomes an outer limit, generous enough that a slow voice is not cut (its margin an option, the default chosen from the calls).
4. **Barge-in per carrier.** `BARGE_IN` is the server's; a carrier may need its own (Telnyx's support advised turning barge-in off while a fault of theirs is open, while Twilio keeps it). `BARGE_IN_TWILIO` and `BARGE_IN_TELNYX` override it for their carrier; unset, `BARGE_IN` applies as before.

## B. Understanding

5. **A digits value read digit by digit.** A number the agent says back (a callback number, its last four) was read as a number ("nine thousand one hundred ten"). A digits slot's value, and its last four, are spoken digit by digit on voice by default, rewritten only on the voice wire as the app's `spokenDigits` rules are (the session, the trace and the console keep the readable form). The slot type takes an option to read it as a number instead.
6. **A number said with a pause.** With barge-in off, a caller who said a digit, paused, then said the rest was answered after the first digit and sent to the keypad. When a digits slot with a known length has heard fewer digits than that, the engine waits a little for the rest (the next words joined to the first), before asking again; the wait is an option on the slot, with a default. (The same calls had a carrier hear eight digits as nine: the engine refused the value and asked again, which is right.)
7. **A bare name.** A caller who answered the name question with only a name ("Jordan Avery") was asked again, the model unsure the words were a name given; the same words a turn later were taken. Right after the name question, a short answer the model found a confident name in is taken as given. The threshold is the slot type's, with a default.

## C. Languages

8. **A language tag a carrier rejects.** Twilio refuses a language element whose code has no region (`es` rather than `es-US`) and the call ends with an error. `pnpm check` warns of such a tag in an app's voice settings, and `pnpm diagnose` refuses it for a server with Twilio.
9. **A recognizer per language.** The server's speech model (an English-only one) was applied to the Spanish language too; the carrier failed to connect it, and the engine's reconnect recovered the call. A language may name its own recognizer (its provider and model), and `pnpm check` warns when a language falls to a default the carrier documents as English-only.
10. **Intent labels per language.** A Spanish line named the caller's request with its English label ("le puedo ayudar a report a problem"). An intent's label may be given per locale, in the locale's files; check warns when a locale lacks one a line of that locale uses.

## D. Small

11. **An ending's own goodbye.** A route that ends the call with its own line that says goodbye was followed by the app's goodbye line, so the caller heard goodbye twice. An ending outcome takes `goodbye: false` to end on its own line alone; unset, the goodbye follows as before. The routed fixture's closing route uses it.
12. **An app's code reading its own settings.** An app on a host file has its own settings file, which the server reads for the app's routes and transfer targets, but the app's code reading `process.env` saw only the server's. The contexts an app's code is given (its hooks, its tools, its start hook and its predicates) carry `env(name)`, its own settings over the server's, the same lookup an `env.` value in YAML uses; the guide says that `process.env` is the server's.
13. **Routes are first-match.** A Spanish call was greeted in English: the outage rule above the language rule matched first. The guide's routes chapter and the create-app skill say plainly that the first rule that holds is taken, with that example and the fix (order, or a rule that does both).

## As built: B

Built on the branch `live-understanding` in four commits (the later three after review); no regression baseline, snapshot or cassette changed (the clinic's and the utility's stub and recorded runs print the same as before, the testkit's regression too).

5. **A digits value read digit by digit.** `SlotSpec.sayAs: 'digits'`, set by a `digits` slot unless its new option `sayAs` is `number` (default `digits`). The voice server spells the values out in `sendFrames`, after the app's `spokenDigits` rules and before the respellings (`channel/sayDigits.ts`): the session, the trace, the console, a chat and every baseline keep the readable form; the frame log masks it as before (the scrubber already finds digits however spaced). How the engine knows the value's span: by the value itself, not the line's shape. The values a turn can say of each such slot (its value and display, a pending read-back's or offer's, the last four of the caller's number at its offer or the consent question, and the decision's variables named for the slot or `last4`) are looked for whole in each text frame: never with a digit beside them, nor a digit across a `.`, `,`, `:`, `/` or `-` (dates, times, amounts), and a value of fewer than five digits (a year, a day, a last four) only where the decision's own variables name it (or a repeat of the offer still asked), never because the session holds it, so "born April 12, 1980" stays a date. A summary, a model-worded line (values kept word for word), a repeat and an app's own line all say a longer value with nothing to mark. A repeat of the last line (no variables) says a short value the session holds too, its read-back's or the offer's. A grouped display is spelled by group with a comma between ("5 5 5 2, 0 4 1 7"), the shape a `groups` rule gives; a value an app's rule already spelled out is left as it spelled it.
6. **A number said with a pause.** What was seen: after a nine-digit miss (the carrier heard eight digits as nine, refused and asked again, which is right and unchanged), "Five." came as a final prompt and got the keypad line; the caller spoke over it 235 ms later, and Telnyx, with the barge-in off, does not transcribe while a line it may not interrupt is playing, so the rest was lost. As built: the voice server holds the **words**, before any turn runs (`server/adapter.ts holdWords`). When the slot just asked has `waitForRestMs` (new option, default 1500, 0 to 5000, 0 off) and the final prompt's words are, read without the model, only the start of its value (new spec hook `SlotSpec.startOfValue(text, locale)`; a digits slot with a `length`: 1 to `length` - 1 digits by `spokenToDigits`), and no turn is queued or running, the words wait. A final prompt in the wait is joined and runs no turn of its own, and the wait starts again while the words joined are still a start (up to ten prompts, so eight digits in four parts are joined whole); the caller heard speaking (Telnyx) stops the clock until they stop, a partial prompt (Twilio) starts it again; nothing more, or speech with no prompt after it, runs the words alone. A digit keyed for a slot that takes keys drops them (a `#`, a `*`, or a key for a slot that takes none leaves the hold as it is, so a stray key loses no words; after re-review: run first, their re-ask was said and the keys keyed over it refused as keyed ahead, losing the first digit, and on the last attempt sending a keying caller to a person); the keys answer the question already asked. The socket closing or a reconnect drops them too (a reconnect said its question again and then the re-ask). The hold is in memory: a restart during it loses the words and the caller is asked again; a `{ wordsHolding }` line marks each hold's start, so replay runs no turn on a hold the log never saw end. One turn runs on the words as held, so nothing is said over the caller, nothing is undone, no silence turn runs over the hold, and the last attempt is held like any other. The frame log's `{ wordsHeld: { slot, ms, fragments, end } }` (with `dropped`, the words digits masked, where none runs) comes before the turn, and replay joins the prompts it counts as logged, whatever the app's settings are then; the turn's trace record names the prompts it joined (`joined: { fragments, waitedFor }`), and the console's join note says the hold. The first commit held the turn's reply instead, after the turn ran; review found it ran a silence turn (and counted a failure) for a re-ask never said when speech came with no prompt after it, and could not hold the last attempt, whose turn had already handed off; it is gone, and the model-read reply hold (`INCOMPLETE_WAIT_MS`) is as it was. The default: 1500 ms, longer than `INCOMPLETE_WAIT_MS`'s 1000, since words of fewer digits than the number are certainly no whole answer, so a wait costs only a miss taken a little later, and a reader pauses longer than a speaker finishing a sentence. Not on a chat; not for a mask-only slot (no least length is known), nor for a number as long as the slot's or longer.
7. **A bare name.** A `name` slot's new option `bareAnswer: { words, given, span }` (defaults 4, `NAME_BARE_GIVEN` and `NAME_BARE_SPAN`, two new engine thresholds at 0.2 and 0.7, sweepable, with `NAME_BARE_GIVEN <= SLOT_DETECT` a sweep constraint; `words: 0` off): on the slot just asked, an answer of at most `words` words whose chosen span was offered and reaches `span` is taken as stated, though the yes-or-no is under `SLOT_DETECT`, as long as it reaches `given`: an unsure yes-or-no is overruled, a confident no never is. The live call (0.41, the span 0.74) fills under the defaults. The questions are unchanged, so no cassette key moved; a threshold name that is not the engine's is declared (`SlotSpec.thresholds`), so a misspelt one is found when the app is defined.

Doubts left for the maintainer: the live checks for 5 to 7 on each carrier (the next sitting); whether 1500 ms is right for callers reading a card (the option is there); whether `NAME_BARE_SPAN` 0.7 holds on a line whose callers often answer with someone else's name (`words: 0` turns it off); a final prompt that arrives while an earlier turn is still running is not held (its question may be about to move), so a caller who says the first digit within a turn's latency is taken as before.

## As built: D

Built on the branch `live-small`. Where the plan left a choice open, the choice and why:

11. **An ending's own goodbye.** `goodbye: false` is taken wherever a call can end on a line of the app's: a route's `then: end` (routes.yaml, the `else` written out too), a check's (forms.yaml `checks[].on`), a slot's `onMaxAttempts` written out (slots.yaml), and a completion in code (`{ kind: 'end', promptId, vars, acks, goodbye: false }`). It rides the decision (`CompleteDecision.goodbye`), and the renderer leaves the goodbye out after the line (`prompts/render.ts closesWithGoodbye`, which already did so for a completion that is the goodbye); unset, or `goodbye: true` (the default written out, kept as absent), the goodbye follows as before. `then: end` already requires `say`, so `goodbye: false` always has a line to end on; on any other `then` it is refused (the schema for a folder, `validateApp` and the routes' checks for an app in code): nothing ends there, so there is no goodbye to leave out. `pnpm check` warns, never refuses, of the live case itself: an ending whose line ends as the goodbye line does (its last sentence, word for word, punctuation aside, in any locale) while the goodbye still follows it. The app map writes such an ending `end, no goodbye`. The routed fixture's closing route uses it, and its APP-MAP.md says so (regenerated with `pnpm app:diagram`; POLICY.md and policy.matrix are unchanged). While there, the same doubled goodbye on a chat was fixed: "no, that's all" on a chat ends on `goodbye_chat` ("Thanks for chatting ... Goodbye."), which the renderer followed with the voice's `goodbye`; `goodbye_chat` is now itself the goodbye, as `goodbye` is. **The baselines do not change**: a scripted call's baseline records the decision (its kind, prompt and acks), not the words said, so the routed fixture's `closed-evening` and `closed-holiday` still match; their words lose the second "Goodbye." (`regress --scenario closed-evening` shows it), and the engine's tests pin the words.

12. **An app's code reading its own settings.** `env(name)` is on every context an app's code is given at call time: `AppContext` (so every form hook, `complete`, the start hook, `callerOffer`, `onServiceResult`, `onSummaryRead`, `principalEntry`), a tool's run context (now the named type `ToolContext`) and a predicate's (`PredicateContext`). It reads the turn's settings (`TurnContext.settings`, a lookup, never a record, so no setting is carried into the trace, the audit or the console; a test holds a setting's value out of both): `RunOptions.settings` where given, else `RunOptions.env`. The server gives each app its environment: on a server of one, the one the YAML's `env.` values are read from (the process's, or a test's `overrides.env`); under a host, the app's own settings file, the whole of it, over the server's settings (`appEnvironment`'s `settings`, `HostApp.settings`), the same precedence the YAML's variables take. A scripted call's `env` serves the code too, so a run is the same wherever it runs, and a seeded corpus call has no settings. Not given to the gate: a rule of the app's own (`defineRule`) and its lookups do not read settings, so what the agent may do stays in policy.yaml and the policy matrix holds on any server; not given to a slot's code either (understanding reads the caller's words, not the deployment). What an app's own file sets beyond what its YAML names is still named at start as not read by the server, now with "the app's code reads them with ctx.env", and `pnpm diagnose --host` says the same. The routed fixture's vip predicate reads `VIP_NUMBERS` with `env` (its baseline unchanged: no scripted call sets it), and the host fixture's routed.env sets it; tests run it on a server of one, under the host file (the server's settings and `process.env` lack it), in a scripted call, and through `RunOptions.settings`.

13. **Routes are first-match.** The guide's routes.yaml section and the create-app skill (patterns.md's routes pattern, options.md by need) say that the first rule that holds is taken and the rest are not looked at, with the live call and both fixes: order the rules, or a rule that does both above them (`when: [{ fact: outage, is: true }, { called: env.SPANISH_LINE }]`, `say: outage_notice`, `then: locale`: the switch comes first, so the notice is said in Spanish). The routed fixture now has that rule, above the outage rule (the start rules after it are numbered one more: the outage rule is rule 4, the language rule 5). `pnpm check` warns of the one case that is almost never meant: a rule that says a line and goes on (`then: continue` with a `say`) above a `locale` rule both could hold for; not where both read the number called (a call dials one number), not where a rule above already does both, and not for a `continue` with no line (an exception written on purpose). Rules that end or hand off above a `locale` rule are not warned of: one line in the default language may be meant, and the guide says so.

### Review fixes (D)

A review of the first build found these, fixed on the same branch:

14. **`goodbye: false` with a request queued.** Every `then: end` but a `start` route's goes on to a queued request instead of ending (the line said, then the request bridged into), `goodbye: false` or not, so a line that says goodbye itself is then heard mid-call. Kept as it is (a request the caller asked for is not dropped), and said wherever `goodbye: false` is documented: the line must read right both ways, and only at `start` can no request be queued. `pnpm check` now puts "take the goodbye out of the line" first in its fix for an ending other than `start`'s, and warns of `goodbye: false` on a line that ends as the goodbye does wherever a request may be queued (afterIdentity, afterForm, a check, a slot's `onMaxAttempts`). An ending that says the goodbye line itself (`goodbye`, `goodbye_chat`) is never warned of, and a line is compared with the chat's goodbye as well as the voice's.
15. **The lost-switch warning, narrowed and widened.** It was silenced whenever both rules read the number called, which missed the live call's own shape (`[{ fact: outage }, { called: env.SPANISH_LINE }]` with a line and `continue`, above `{ called: env.SPANISH_LINE }` with `locale`). It is now silenced only where the two cannot both hold (`core/routes.ts exclusive`): `called` conditions with no variable in common, one fact, call data key or slot tested for values that exclude each other (`is` against another `is`, an `in` without it or a `notIn` with it; two `in` lists with nothing in common; `present` true against false), or the same hours open and closed. Values are compared by their spelling, as call data is.
16. **A chat's goodbye on every ending.** An ending other than "no, that's all" on a chat was followed by the voice's `goodbye`. The core now names the goodbye with the decision (`CompleteDecision.goodbyeId: 'goodbye_chat'` on a chat, absent on voice, as `goodbye()` picks its line), and the renderer says it. No baseline changed (a baseline records the decision's kind, prompt and acks).
17. **An app's own settings are not a fault; a server setting left there is.** The start log and `pnpm diagnose --host` named what an app's own file sets beyond its YAML as a warning; now that is an informational line (`diagnose` says `ok`): "also sets X, not named by its YAML: available to its code through ctx.env". A name that is one of the server's own settings (a carrier's secret, a model's key, `PUBLIC_HOST`, a store's URL) keeps its warning, since in an app's file under a host it does nothing ("sets TWILIO_AUTH_TOKEN, the server's own setting ... here it does nothing", with the fix to move or delete it). The server's settings are not a list kept by hand: `server/serverSettings.ts` runs the server's readers (`loadConfig`, the decision model's and the renderer's provider settings) over environments that turn each part of the server on, recording every name they ask for, so a setting added to a reader is known at once (a test holds the carriers', the model keys', the stores' and the chat's names among them, and an app's own, such as `VIP_NUMBERS`, not). Names only, never a value.
18. **The text harness and the shell.** `--scenarios` in the text harness ran a scripted call with no `env` on the shell's environment; it now gives such a call none, so "a scripted call reads its own env, never the shell's" holds there as in `regress` (no test or baseline changed; a test runs it with `VIP_NUMBERS` in the shell). The corpus, the prompt and `--replay` still read the shell's environment (with a model client, the settings file `ENV_FILE` names): chapters 4 and 14.15 say to point `ENV_FILE` at the app's own settings file when replaying a call of an app on a host.
19. **Upgrade note (no CHANGELOG yet, and RELEASING.md has no notes section, so it is here).** `env(name)` is a required member of the exported `AppContext`, `ToolContext` (a tool's run context, now a named type) and `PredicateContext`. Code the engine calls is unaffected (the engine builds every context), but an adopter's test or code that builds one of these contexts by hand stops type-checking until it adds `env: (name) => undefined` (or a lookup of its own), or casts as the templates' tests do (`{} as never`). Kept required, so an app's code never has to ask whether `env` is there.

## As built: A. Carriers

1. **A withheld number on Telnyx.** Telnyx's provider reads the answer webhook's marks of a withheld number (`server/voice/telnyx.ts` withheldMarked): any one, in any case, of a caller ID that is a withheld word (`CallerId` anonymous, restricted, private...), an anonymous SIP From (`FromSipUri` whose user is such a word or whose host is `anonymous.invalid`), a `From` that is itself one of those, or a SIP Privacy header that hides the caller (`Privacy` or `SipHeader_Privacy` with `id`, `user` or `header`; RFC 3323, not yet seen on a live call). Such a webhook is read with `withheld: true` (`CallbackParams.withheld`), no `from`, and every copy of the number out of its fields (`From`, `Caller`, the caller's name, and any field whose digits hold the number's last seven), so neither the server's log nor the frame log has it; the marks stay. The start document carries a parameter of the engine's own, `dialogwright_withheld=true` (`WITHHELD_PARAMETER`, which `startParameters` may not name, by check and the schema), and the adapter takes the number out of the setup that comes back before anything reads it (`server/voice/registry.ts` setupWithCallerWithheld: its `from`, its `callerName`, and the provider's `callerParameters`, Telnyx's `telnyx_call_from`). The session's start then has no `callerNumber`: nothing kept, offered or looked up; the trace, the frame log, the console and the log hold no copy, and the console shows the caller as `withheld`. A reconnect stays withheld wherever it lands: the call remembers it (`CallEntry.callerWithheld`, set by a setup that carries the parameter) and is saved with it (`StoredCall.callerWithheld`, every store), so the server that answers the callback (this one, a restarted one on `SESSION_STORE=file`, another on `postgres`, which loads the call to answer) marks the reconnect's document, and the server the socket reaches takes the number out of the new setup, whether or not the callback carries the marks or the setup the parameter. On a server holding such a call, the callback's frame-log line leaves out every copy of the number (`withoutCopiesOf`), not even its last four. **SESSION_SCHEMA is unchanged:** the flag is outside the session, optional, and a call saved before it reads as not withheld, which is how every call was read then (a setup that carries the parameter still marks it); the store contract checks the flag round-trips. Not an option. The captured webhook (its number +15555550142) is a fixture (`__fixtures__/telnyx/webhooks.json`), read by the conformance kit and `telnyx.test.ts`; `voice/withheld.e2e.test.ts` runs the texting fixture (which keeps the number and looks the caller up by it) from the webhook to the call and its reconnect.
2. **Telnyx's voice on the relay element.** In a document that names languages, Telnyx's relay element carries the start language's voice when the languages' voices differ (before, only when every language had the same one); each `<Language>` keeps its own. A start language with no voice of its own names none there. Twilio's document is unchanged (a test pins both). **A known limit:** a language whose `<Language>` names no voice may keep the start language's voice after a switch (the relay element's), where the guide had said a locale with no voice of its own never reads its language in another's voice; unproven either way until a live call (live-checks check 15). The guide's 13.3 says so; `pnpm check` warns of Telnyx voices named for some of an app's locales and not others (`telnyxVoiceWarnings`), and the server warns at start when, on Telnyx, some locales have a voice (the app's, or `TELNYX_VOICE` for the default) and others none (`telnyxUnvoicedLocales`).
3. **Ending after the last line has played.** On a call whose carrier reports its playback, the held `end` still goes on the report (`tokensPlayed` naming the last line, or `agentSpeaking` off that stays off); the ceiling for a report that never comes is now the lines' estimate times `END_PLAYBACK_FACTOR` plus `END_PLAYBACK_MARGIN_MS`, never past `END_PLAYBACK_MAX_MS`. New options: `END_PLAYBACK_FACTOR`, 1 to 10, default **2**; `END_PLAYBACK_MARGIN_MS`, 0 to 60000, default 2000 (the margin it always had). **A default that changes behaviour, the maintainer's decision (2026-10-13: the default is 2; `END_PLAYBACK_FACTOR=1` restores the old wait; CLAUDE.md and the guide's 14.12 name it beside `RESUMED_AFTER_MS`):** the factor was a fixed 1, which cut the live call's goodbye (estimate 6.1 s, cut at 8.1 s); 2 holds for a voice at half the estimated pace (2.5 words a second), and costs at most the estimate again in silence before the hang-up when no report comes. With the default 15 s most, a line estimated past 6.5 s reaches the most before twice its estimate. A carrier that reports nothing (Telnyx without `TELNYX_EVENTS`) is unchanged, the estimate and half a second: no measurement says by how much the estimate is short there, and a longer wait would delay every transfer; `TELNYX_EVENTS` is the fix for such a line. The startup line names the factor and margin where a listed carrier is asked to report its playback (Telnyx with `TELNYX_EVENTS`).
4. **Barge-in per carrier.** `BARGE_IN_TWILIO` and `BARGE_IN_TELNYX` (the same four values) override `BARGE_IN` for that carrier's calls: the relay element's `interruptible` in its start document (the legacy `/voice` included) and the lines' own flag (`bargeInOfCarrier`; a call that names no carrier is on the legacy one, Twilio). Unset, `BARGE_IN` applies, as before. Each is checked at startup like `BARGE_IN` (a bad value refused by name, which `pnpm diagnose` reports), against its own carrier only, and `BARGE_IN` against the carriers with none of their own; a carrier's variable whose carrier is not listed is checked for its value and applies to no call. The startup line names each listed carrier's own (`barge-in any (telnyx none)`).

**Review fixes.** Beyond the four: the frame log and the console mask Telnyx's `CallerId`, `FromSipUri` and `ToSipUri` on every call (`ADDRESS_KEYS`, `maskAddress`: each run of five or more digits to its last four, the rest kept, so `anonymous@anonymous.invalid` stays readable; the floor of a call data key that reads one too), where before an ordinary call's were written whole; and the `/cr-action` frame-log line masks any field holding the last seven digits of the caller's number, whatever its name (`maskCopiesOf`). A withheld webhook's copies are found from every field that may carry the number (`From`, `Caller`, the caller ID, the SIP From), not `From` alone, and a SIP From's display name that is a withheld word (`"Anonymous" <sip:...>`) is a mark.

The options are in the guide's 13.1 and 14.12 and in every `.env.example` (the clinic's, the utility's, the template's) and the home-server page.

## As built: C. Languages

8. **A language tag a carrier rejects.** Where it came from: the routed fixture's Spanish locale is `es`, and with no `voice.locales.es` the engine speaks and hears a locale as its own tag (`core/locale.ts speechLanguagesOf`), so the start document wrote `<Language code="es"/>` (and `ttsLanguage="es"` on a call that starts in it). The engine already writes `voice.locales.<tag>.tts` and `transcription` where an app names them, so a correct config gives a correct document; it does not guess a region for a bare tag (`es` may be `es-US`, `es-MX` or `es-ES`), and warns where the config cannot be right. `channel/speechLanguages.ts` reads an app's languages as the document will write them (`bareSpeechTags`: a tag with no region subtag, for a locale's `tts` or `transcription`, only for an app whose document names languages) and says the finding in one set of words (`bareTagFinding`). `pnpm check` warns of each such locale at its key in app.yaml; `pnpm diagnose` says it under a new `languages` check, a **fail** on a server whose `VOICE_PROVIDERS` lists Twilio and a warning on Telnyx alone; and the server warns at start. **Telnyx:** nothing in the repository (the adapter's comments, the conformance fixtures, the guide, live-checks) says whether Telnyx takes a tag with no region, so the words say "whether Telnyx takes one is not known", for both carriers; live-checks check 16 asks. The routed fixture now names `voice.locales.es: { tts: es-US, transcription: es-US }`, as a correct app does. The library fixture keeps its bare `es`: the engine's document tests rely on it (another locale gets the carrier's defaults), so `check` warns of it, and the check tests that are about other things leave its two speech warnings out by name (`LIBRARY_SPEECH`), with one test holding that those are its only warnings.
9. **A recognizer per language.** A locale already names its own recognizer per carrier (`voice.locales.<tag>.recognition.<carrier>: { provider, model }`, written on that language's `<Language>` as Twilio's `transcriptionProvider` and `speechModel` and Telnyx's documented equivalents; the tests pin both documents), so no new option: the live call's app named none. What was wrong is the guide's claim that a language with none gets the carrier's default: on Twilio it was heard with the start language's flux. The models documented as hearing English only are one list, `ENGLISH_ONLY_MODELS` in `channel/voiceProviders.ts` (Deepgram's flux, as Twilio names it, `flux`, and as Deepgram does, `flux-general-en`; the comment says where it came from), beside `DEFAULT_RECOGNITION` (Twilio's Deepgram flux, which `server/voice/twilio.ts` now reads from there). `englishOnlyHearings` finds every language other than English heard by one: its own (`own`), the deployment's for the default locale (`deployment`: in `check` the server's default flux, "unless TWILIO_SPEECH_MODEL names another"; in `diagnose` and at start the server's own `recognitionFor`), or, for a locale that names none, the one the document names for another language (`another`, the live call). `check`, `diagnose` (a warning) and the server's start say each, with the fix (`voice.locales.<tag>.recognition.twilio: { provider: Deepgram, model: nova-3-general }`, or the server's `TWILIO_SPEECH_MODEL` for the default locale). The routed fixture names that recognizer for `es`. No server option and no default changed; nothing new in 14.12 or the `.env.example` files.
10. **Intent labels per language.** The label entered a line through `core/turn.ts`'s `ack_intent`, `confirm_intent_explicit`, `disambiguate_intent`, `ack_intent_then`, `ack_queued` and `bridge_next` (`intentLabel`, `formLabel` in `core/app/intents.ts`; app.yaml's `console.formLabels` is the console's only). A locale gives its own in the shape of its default file: `locale/<tag>/intents.yaml` (`intents: { <id>: { label } }`) and, for an internal form, `locale/<tag>/forms.yaml` (`forms: { <id>: { label } }`), each a schema of its own (`locale-intents.schema.json`, `locale-forms.schema.json`, generated), read by the loader beside the locale's prompts (`LoadedConfig.localeIntents`, `localeForms`; in the configuration hashes by path) and built into `AppLocales.labels` (absent when no locale gives one, so every other App is as before). `intentLabel` and `formLabel` take the session's locale; every call site in `core/turn.ts` passes `s.locale`, and a label a locale leaves out is the default's. The decision model is still given the default's label (`core/state.ts`'s pending confirmation and active form), as it reads every question in the default language, so no recorded question changes; a disambiguation's options are the labels said, so a re-ask says them again in the same words. `check` refuses, at the key, a locale's label for an intent intents.yaml lacks (with the near name), and in a locale's forms.yaml a form that is an intent's or no internal form; `validateApp` holds an App built in code to the same. It warns, once per locale, when the locale's own prompts.yaml says one of the six lines and gives no label for a form intent, an internal form or `done`. Both fixtures carry Spanish labels (the library's `locale/es/intents.yaml`; the routed fixture's `intents.yaml` and `forms.yaml`), and the routed scenario `spanish-line` now expects "Claro, le puedo ayudar a reportar un problema." (its expectation, not its baseline).

**Baselines.** None changed. The routed regression: corpus 18/18, scenarios 12/12 pass and 12/12 match the baseline (the baseline records prompt ids and acks, not the words). Tests whose expectations pinned the English label in a Spanish line (`define/locale.test.ts`, `define/spanishCall.test.ts`) now expect the Spanish one, and the library's hashed files include `locale/es/intents.yaml` (`define/configHash.test.ts`).
