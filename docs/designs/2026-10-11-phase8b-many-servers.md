# Phase 8b, many servers, trimmed: the build

Date: 2026-10-11. Status: **build plan; being built.** Source: [design.md section 8](../design.md#designed-for-many-servers-phase-8b) and the maintainer's decisions of 2026-10-09 and 2026-10-11: Postgres first, tested with PGlite (Postgres in WebAssembly, from npm), so nothing is installed to develop it; Redis may follow later behind the same contract; traces on S3-compatible storage with local files the default; and a trimmed scope, the core promise that **a deploy or a failed server never drops a call**.

Built now: a Postgres store for calls, chats and tokens with one owner per call at a time; the audit in Postgres; traces on S3-compatible storage; the console's events across servers; a container image; and the two-server test. Left for later, as needs show: console roles with single sign-on (OpenID Connect, for the console only), OpenTelemetry, a Redis store, `--role voice|chat|console`, and hosting guides. One machine keeps working exactly as it does: every piece is an option whose default is today's.

## Decisions

1. **The Postgres store.** `SESSION_STORE=postgres://...` implements the call, chat and token stores of `server/stores/types.ts` and passes `runStoreContract` unchanged, run against PGlite in the test suite and against a real Postgres in the two-server test. The schema is created on first use (a version table; a newer schema refuses to start with a message, never migrates silently). The `pg` driver is the only new runtime dependency, loaded only when the option names Postgres.
2. **One owner per call.** A lease per call id: the server that runs a call's turns holds it, renews it while the call is live, and gives it up when the call ends or the server drains. Another server takes a call over when the carrier reconnects to it and the lease has lapsed (a crash) or was given up (a drain). A turn is never run by two servers at once: the lease is taken in the same transaction that reads the session. The reconnect counter is incremented atomically. Idempotent writes (`ctx.idempotencyKey`) mean a turn repeated after a takeover writes once.
3. **The audit in Postgres.** `AUDIT_STORE=postgres://...` (default: today's day files). A hash chain per session, and each session's last hash anchored into a daily chain, since two servers appending to one day file would fork it. `pnpm audit:verify` verifies either kind and exits 1 at the first break. The console access log goes to the same place.
4. **Traces on S3-compatible storage.** `TRACE_STORE=s3://<bucket>/<prefix>` with `S3_ENDPOINT`, `S3_REGION` and the keys from the environment (AWS S3, Cloudflare R2, MinIO and others); default: today's local files. A call's trace is one logical trace whichever servers ran it: each server writes its own segments under the call's id, and readers (the console, replay, `kb:gaps`) join them in order. Requests are signed with AWS Signature Version 4 by code of our own over `fetch`, so no SDK is added. Tested against an in-process fake S3.
5. **The console across servers.** The console's event bus (`server/dashboard/bus.ts`) gets a Postgres implementation (`LISTEN`/`NOTIFY`, chosen with the session store), so one console sees every server's calls, and a chat resumed on another server closes the old socket wherever it is. Payloads stay as redacted as they are today.
6. **The container image.** A `Dockerfile` for this repository's apps and one the standalone scaffold writes into a project: Node 22, the app and its built package, `dialogwright start --tunnel none`, a non-root user, `/ready` as the health check, SIGTERM drains.
7. **The two-server test.** Two levels:
   - **In process, in the normal suite:** two servers in one Node process on two ports, sharing one PGlite, behind a tiny proxy; a simulated carrier call (the existing Twilio and Telnyx simulators) on server A; A is stopped abruptly mid-call; the carrier's reconnect reaches B, which takes the lease and resumes. Asserts: no dropped turn, the question the caller was on asked again, a write done once, the audit chain verifies, the trace joins. Also a drain: A drains, its calls move to B.
   - **Compose, the real thing:** `docker compose` with Postgres, MinIO, two app containers, a load balancer and a test driver that places the simulated call and `docker kill`s the container holding it. Run by hand (`pnpm multi:test`, needs Docker) and by a GitHub Actions workflow weekly and on demand, never on every push.
8. **Laptop mode stays first.** No new option changes a deployment that does not set it; `pnpm diagnose` checks each new option (reachable, schema version, bucket writable) without printing a secret; the guide's section 14 gets a part on many servers, and the website's scaling guide is brought in line.

## Tasks

The usual loop per item: a worktree, an implementer, a reviewer, the full local suite (with `pnpm adopt:test`), a fast-forward onto local `main`. 8b1: the Postgres store, the lease, the in-process two-server test. 8b2: the audit in Postgres, traces on S3, the console bus. 8b3: the image, the compose test and its workflow, the docs.

## As built (8b1)

8b1 is the Postgres store, one owner per call, the in-process two-server test, the diagnose check and the docs ([guide 14.14](../guide/14-running-it.md#1414-many-servers-on-one-database)). One machine is unchanged: with `SESSION_STORE` unset, `memory` or `file:`, the server takes no lease, awaits nothing it did not, and every test, regression and `adopt:test` is as it was.

1. **The Postgres store** (`server/stores/postgres.ts`) as decided, with these choices:
   - Five tables: `dw_schema` (the version, one row), `dw_calls`, `dw_call_leases`, `dw_chats`, `dw_tokens`. Made on first use in one transaction under an advisory lock, so servers starting together make them once. A database at any other version, older or newer, is refused at startup with what to do: there is only version 1, and no migration runs unasked.
   - A record is kept as the JSON text it was given, not `jsonb`, which reorders keys: the contract asks for a call back exactly as saved. A call's reconnect count is a column of its own beside it, which a load reads, so a callback counts a reconnect in one `UPDATE`.
   - The code runs on a thin client (`stores/sql.ts`: `query` and `transaction`). The server opens it through `pg`; the tests through PGlite (`stores/pgliteSql.ts`), passed in by `ServerOverrides.sessionSql`, a test seam and not a setting. The contract also runs once through `pg` against PGlite's wire server (`@electric-sql/pglite-socket`, one connection, as PGlite is one session), so the driver's own types (a `bigint` as a string) are covered.
   - **`pg` is an optional dependency** (`optionalDependencies`), not a dependency or an optional peer. It is pure JavaScript and small, so a normal install has it and the container image (8b3) needs no extra step; it is imported only when `SESSION_STORE` names Postgres (a variable specifier, as the ONNX adapter's); an install made without optional packages gets an error naming `pnpm add pg`. `adopt:test` stays green.
   - The connection string is never said: the startup line, every error and `pnpm diagnose` mask its password (`maskConnectionString`, `maskSecrets` on a driver's message).

2. **One owner per call**, with these choices:
   - **The contract has the lease.** `CallLeases` (`claim`, `renew`, `release`, `holder`, `saveAs`, `countReconnect`, `removeUnleased`) sits beside the three stores, and `runStoreContract` holds a store's `leases` to eight checks named `lease: ...` (one owner at a time, a lapsed lease taken over and a released one at once, renewal, the claim reading the call, a save kept only from the holder and never lowering the reconnect count, reconnects counted once each under the limit, a removed call taking its lease, exactly one of eight racing claims winning). The memory and file stores keep leases in the process (`stores/leases.ts`), so they pass; a store that gives no `leases` passes those checks with nothing to hold, so an older store's run is unchanged. The server reads a lease only from a shared store.
   - **The lease is taken at the socket's setup, not at the callback.** With no sticky sessions the callback and the socket that follows may reach different servers. The callback's server loads the call only to answer (a borrowed entry, never saved from there and dropped once answered) and counts the reconnect in the database; the server the socket reaches takes the lease and reads the call in one transaction (`INSERT ... ON CONFLICT DO UPDATE ... WHERE` the holder is this server or its lease has lapsed), waiting up to one and a half holds for another server's to lapse or be released, and puts the caller through to a person (`end` with `busy`) if it never is.
   - **A server holds a call in memory only while it holds its lease.** When the call's socket closes it gives the call up once the turn running has saved, waiting at most half a hold and never for a service's answer (the request is saved with its key, and whoever takes the call sends it again); a drain closes the sockets, so the same happens, and `close()` gives up whatever is left. Every save is `saveAs`, refused unless this server holds the lease; a refused save, or a renewal that no longer names the call, lets the call go there, socket and all. One consequence: a reconnect on a shared store, a relay's blip included, is usually heard as resumed, since the server that takes it back cannot tell a blip from a move.
   - **Timings.** `CALL_LEASE_MS`, default 5000 (500 to 60000): the most silence a crash adds; renewed every third of it in one statement per server for all its calls, which leaves room for two missed renewals. A hold that lapses while its server lives costs nothing unless the carrier has reconnected elsewhere, and then the call is that server's. Times are the servers' clocks (as the token store's always were, and as the contract's clock drives them), not the database's, so the servers keep their clocks in step, which `pnpm diagnose` checks.
   - **A server's name.** The lease owner is `SERVER_ID` (default `server`) with a random suffix per process, never `SERVER_ID` alone: two processes given one name would otherwise share a hold, and run one call twice.
   - **Tokens.** The server's token calls were synchronous (`decideAction`'s mint and revoke). Rather than change `decideAction`'s signature and its many callers, a token store the server runs on answers `mint` and `revoke` at once (`ServerTokenStore`); the Postgres one writes behind them in order, and the callback awaits `settled(callId)` before it hands the carrier a token (one that could not be saved puts the caller through to a person). `verify` (at setup) and `has` (at the upgrade) are awaited only when a store answers with a promise, so the memory and file paths run as they did.
   - A lease taken for a socket that closed while it waited is given back (`giveBack`), and the minute's sweep of saved calls removes only one no server holds, recorded by the one server that removed it (`removeUnleased`).

3. **The two-server test** (`server/manyServers.e2e.test.ts`, about fifteen seconds): two servers in one process on two ports, one PGlite, a small balancer sending each webhook and socket to the first server up and not draining. A crash is the server's database client cut (`cut()`, so nothing more of it lands) and then its sockets and listener closed with no drain. On Twilio and on Telnyx, a call is crashed mid-form and taken over by the other server after the hold lapses; a call drained (`RESTART_PAUSE_S=0`, a 60-second hold, so only a release lets it move in time) is taken over at once; and a drain whose callback still reaches the stopping server (a balancer slow to see `/ready` say 503) gets the pause and its socket reaches the other. Each asserts the `resumed` line and the question again, the form's values, the turns one after another across the two servers' traces with none dropped or repeated, the reconnect counted once, and nothing left in the tables. A service request the dead server had sent is sent again once by the new server with the same key, so a store that keeps keys does it once. And what cannot be done goes to a person: a socket reaching a server while another holds the call on, and a new call whose token cannot be saved. `sessions.shared.test.ts` covers the same rules on one machine's leases, and `stores/postgres.test.ts` the races between two servers' stores on one database (one claim of two wins, a lapsed lease taken over with the old holder's save refused, a released one taken at once, renewal keeping it, reconnects counted once across both).
   - **Changed:** the plan's "the audit chain verifies, the trace joins" is per server in 8b1: each server's audit chain verifies and the call's turns run on from one server's trace to the other's. One chain per call and one joined trace are 8b2's (decisions 3 and 4).

4. **Diagnose**: check 10 with `SESSION_STORE=postgres://...` (not with `--offline`) says whether the database answers, its tables' version (or that the server will make them), and whether a test lease can be taken and given up, each failure with its fix, never the password.

**Left, or doubtful.** Real concurrency is tested only on PGlite, which runs one transaction at a time, and through `pg` on its one-connection wire server; the compose test (8b3) runs a real Postgres with servers in separate processes. Each server's minute sweep reads every saved call in the database (fine for hundreds, to move into SQL for more). Until 8b2: the audit and traces are per server, the console sees only its own server's calls, and a chat resumed on another server does not close its old socket on the first. A transfer held for its line to play (`END_AFTER_PLAYBACK`) whose socket closes first is owed by the server that held it: a callback that reaches another server hangs up.

### As built (8b1): review fixes

Where this part and the one above differ, this one is what is built.

The review's probes, each now a test (`server/manyServers.e2e.test.ts`, `server/sessions.shared.test.ts`, `server/stores/postgres.test.ts`, `server/relayPing.test.ts`, `server/restart.e2e.test.ts`), found eight things; all are fixed. The session tables stay at version 1 (never released): their columns changed in place.

1. **A held transfer whose callback reached another server hung up.** A transfer whose `end` waits for its line (`END_AFTER_PLAYBACK`) is now saved with the call (`StoredCall.heldHandoffData`, the `held_handoff` column) until the `end` is sent; a callback for a call no longer live here takes it from the store in one statement (`CallStateStore.takeHeld`: `DELETE ... RETURNING`), so exactly one server dials it, and a store that cannot say puts the caller through rather than hang up. The file store does the same, so a restart in the hold puts the caller through too. SESSION_SCHEMA is not bumped: the field is outside the session and optional, and a server that does not know it reads the record as an ended call and forgets it, as it did before; it never resumes one wrongly. The same holds for `StoredCall.droppedAtMs` (below).
2. **A database that stops answering held callers in silence.** Every query has a deadline on both sides of the wire: the pool's `query_timeout` and `statement_timeout` with TCP keepalive, and a deadline on this side (`boundedSql`), both `SESSION_STORE_TIMEOUT_MS` (new, default 2000, 100 to 30000). The claim waits to a deadline on the wall clock, with backoff and jitter; a setup whose token or lease cannot be had ends toward a person (`end` with `unavailable` or `busy`); a callback whose call cannot be read answers with the handoff number (`dial:store-unavailable`), and the token waits (`landed`) are bounded too. A claim that timed out here but committed there leaves a lease no one runs: the renewal gives up any lease this server holds for a call it does not have.
3. **Clock skew broke takeover.** Leases are timed by the database's clock (`clock_timestamp()`), in claim, renew, saveAs and removeUnleased; the injected clock is a test option (`leaseNow`). Diagnose reports the database's clock against this machine's, for information. The docs no longer promise clocks within a second.
4. **Removal was not fenced, and a dropped entry's turn still acted.** A shared store removes a call only as its holder (`removeAs`); a call loaded only to answer is removed only when no one holds it. The adapter ends a call and revokes its token only while it still holds the call (`holds`), so a turn that outlived its hold acts only on its own server's trace and audit. A socket's release waits for the turn running up to a quarter of a hold less than a claimer waits, and not for a service's answer.
5. **A half-open socket sent the caller to a person.** The reconnect counter fences the lease: a claim records the call's reconnect count, and a later claim takes the lease when a reconnect has been counted since (the carrier only reconnects a call whose socket it has given up). This also makes a crash a takeover at once rather than a wait for the lapse, so `CALL_LEASE_MS` is now the wait only when nothing announces the takeover. Plus `RELAY_PING_MS` (new, default 0, off): a relay socket that misses a ping is closed. Off by default because whether each carrier's relay answers pings (RFC 6455 says it must) is for a live check.
6. **Every start needed CREATE.** The tables' version is read first with no DDL; tables are made only when absent. Diagnose matches.
7. **The resumed line on a same-server blip.** A release no longer deletes the lease row: it marks it given up, by its socket (a clean hand-off) or by a stop, and the next holder is told which (`LeaseClaim.took`). A clean hand-off, to the same server or another, is resumed with the question alone, as on one machine.
8. **Minor:** runtime messages are masked (every log line with the store's password taken out); the masking reads a connection string by hand, so a password with `/`, `#`, `?` or a space is masked whole; a claim decides on the lease row locked and reads again if a racing claim made it, with a clear error after three tries; a test runs an idempotent tool on a server that dies before it saves, and the next server runs it again with the same key; the docs say what the tests show and what is still to be shown.

**The resumed line and silence** (the maintainer's decision): the line depends on how long the caller was left in silence, not why. `RESUMED_AFTER_MS` (new, default 1500, 0 to 60000; 0 says it wherever it was said before) is measured from the carrier's callback, which comes the moment the relay session is lost, to the setup of the socket that resumes the call: the silence the carrier's reconnect makes. One machine records the callback's time with the call (`StoredCall.droppedAtMs`); a shared store records it with the reconnect count, on the database's clock, and a claim says how long ago it was (`LeaseClaim.silentMs`). The line is only ever removed, never added: a reconnect to the server holding the call and a clean hand-off stay silent. A planned restart's pause (`RESTART_PAUSE_S`, default 5) is past the threshold, so one machine keeps today's line there; a pause set under it lets a quick restart pass unnoticed. **Changed from the maintainer's expectation:** "a crash takeover (the lease wait) gets the line" no longer holds by default, because the reconnect fence (item 5) takes a crash over at once: a crash whose carrier reconnects within 1.5 s passes unnoticed, and one slower than that gets the line (both tested). The restart tests that show the restart machinery pin `RESUMED_AFTER_MS=0`; the threshold has tests of its own on the memory, file and Postgres stores. No regression exercises a reconnect, so the regressions are unchanged.

### As built (8b1): review fixes, second round

Where this round and the parts above differ, this round is what is built (notably: a crash always hears the resumed line, item 3; and masking touches only connection strings, item 4).

1. **The reconnect fence defeated the turn-in-flight wait.** Every reconnect is counted before any socket arrives, so a claimer always found `reconnected` and took the call while the holder was still finishing a turn. Now a holder whose socket closes while work is queued for the call marks its lease `closing` (a column; still renewed and saved under), and a claim takes a reconnected lease only when it is not marked: the half-open case, where the holder never saw the close, is still taken at once. The claimer waits, up to its deadline, for the holder to finish, save and give the call up (`socket`); a turn that ends the call ends it, and the waiting server closes the socket (`ClaimResult` `ended`), so the carrier's callback hangs up. Tested: the slowed turn runs once, on the holder, and the caller hears where it got to; the ending turn; and the half-open case.
2. **`RESUMED_AFTER_MS` defaults to 1500 everywhere**, the maintainer's decision, recorded as the one exception to "every server option has a default that keeps the behaviour from before it" in CLAUDE.md and the 14.12 row: on one machine a planned restart under 1.5 s of silence gets no apology; 0 restores the old line.
3. **The threshold applies only to clean hand-offs.** Silence measured from the carrier's callback misses what the caller heard before it when the holder never let go. So a call taken as `stop` or `own` (and on one machine, one saved by a stopping server: `StoredCall.stopped`, set by `close()`) is apologized to only past the threshold; one taken as `lapsed` or `reconnected`, or found on the file store with no stop (a crash), always hears the line; `socket` never does. The docs say the callback's timing is documented for Twilio and an assumption for Telnyx (its adapter's assumption 1), for a live check.
4. **Masking no longer mangles lines.** `maskSecrets` replaces the password only inside connection strings in a line (the one given, and any `scheme://...` a driver quotes), never as a bare word: a short password such as `a` leaves `auth failed for user "u" at host a` as it is.
5. **The schema version stays 1** because version 1 never shipped: said by the constant, and any change after the first release bumps it.
6. **A held transfer whose caller hung up in the hold** is dropped by the hangup's callback, on whichever server it lands (logged), and the sweep removes one no callback took after `HELD_TRANSFER_MAX_MS` (two minutes), not the call's whole time.

### As built (8b1): review fixes, third round

1. **A transfer decided by a turn still running when the socket closed was lost** when the reconnect reached another server: the turn ended the call and forgot it, the other server's claim found nothing (`ended`) and the callback hung up. Now a turn that ends the call while the call has no socket, with a durable store, keeps its end: its lines and its `end` are saved with the call (`StoredCall.heldFrames`, with the `end`'s handoff as `heldHandoffData`, a goodbye's too), the lease is given up, and the relay token is left live for the next socket. The server that socket reaches takes the call from the store in one step (`takeHeld`, which now returns the saved call; claim result `replay`), says the lines and sends the `end` (held for its line where the carrier needs it), so the carrier's callback dials the app's chosen target, or hangs up after the goodbye; nothing is left for another server to send or dial. One machine with the file store does the same when the carrier connects again after the turn has ended; with the memory store nothing changes. Tested on both carriers, transfer and goodbye, on another server, on the same server, and on the file store.
2. **A stale `stopped` mark** could label a crash as a clean hand-off (a planned restart's call resumed, its new server crashed before its next save, and the next restart found the mark). A call restored with the mark is saved at once without it. Tested (and the test fails without the fix).

## As built (8b2)

8b2 is the audit in Postgres, traces on S3-compatible storage, the console across servers, the diagnose checks and the docs ([guide 14.14](../guide/14-running-it.md#1414-many-servers-on-one-database), 14.12's rows, the `.env.example` files, the scaling guide). One machine is unchanged: with `AUDIT_STORE` and `TRACE_STORE` unset, and `SESSION_STORE` not Postgres, the audit is day files, the traces are files, the bus is in the process, and every test, regression and `adopt:test` is as it was.

1. **The audit in Postgres** (`audit/postgres.ts`, `AUDIT_STORE=postgres://...`, the session database or another), as decided, with these choices:
   - Two tables under their own row in `dw_schema` (`audit`, version 1): `dw_audit_entries` (a chain, its seq, the UTC day, the entry as JSON) and `dw_audit_anchors` (a day, its seq, the anchor as JSON). Made on first use under the schema lock, read first with no DDL, refused at another version, as the session tables are; the schema code is shared (`ensureTables`, a `TablePart` per set of tables).
   - **An entry is a day file's line**: the same drafts, redaction and hash (`entryHash`); `seq` is its place in its call's chain (a test shows the same drafts at the same time give byte-identical JSON in both).
   - **Anchored every time a call's chain grows**, not only at its end: each append (a turn's entries, in one transaction) anchors the call's newest hash into the day's chain, so a call's newest entry is always anchored and a cut or forged tail is found. The plan's "each session's last hash" is read as that.
   - **A turn that outlived its server's hold is chained, not dropped**: a call's entries are chained under an advisory lock on the call, and the anchor under one on the day, so two servers appending to one call at once are put one after the other in one chain (tested with two sinks racing on one call). The audit records what a turn did; dropping it would lose a tool's run.
   - **The console's access log** goes to the same audit, under call id `console` as in a day file, chained per day (`console@<day>`) so no chain grows without end and retention can remove a day of it. An access the audit could not record is still not served: a sign-in, sign-out and link wait for the database, the live feed and a replay too (503 if it fails; as first built, a live feed whose record failed was served unrecorded on the browser's retry: fixed in the review, below).
   - **`AuditSink.append` may answer with a promise** (`Chained<AuditEntry>`), with `appendAll` for a turn's entries in one transaction; every caller waits for one where it got one (`chainDrafts`, `whenChained`), and a sink that answers at once is used exactly as before (no added await on one machine).
   - `pnpm audit:verify` takes a folder or a `postgres://` URL (or `AUDIT_STORE`), masks the password, walks every call's chain from GENESIS and every day's anchors, checks each anchor names an entry that is there as anchored and each chain's newest entry is anchored, and exits 1 at the first break of each chain or day. It reads every row at once (fine for now; to page for very large audits).
   - Retention (`AUDIT_RETENTION_DAYS`) removes a call's chain whole once its newest entry is past the days, and the days' anchors; what stays verifies. `SESSION_STORE_TIMEOUT_MS` bounds the audit's questions too (no new option). A turn whose audit cannot be written fails as a turn whose day file cannot be written does today.

2. **Traces on S3-compatible storage** (`trace/store.ts`, `TRACE_STORE=s3://<bucket>/<prefix>`), as decided, with these choices:
   - **SigV4 of our own** (`trace/s3/sigv4.ts`) over `fetch` (`trace/s3/client.ts`: put, get, delete, a paged ListObjectsV2, ten seconds a request), held to six of AWS's published vectors (the four S3 documentation examples and two of the SigV4 suite), and tested against an in-process fake store (`testing/fakeS3.ts`) that checks every signature and payload hash. Path-style with `S3_FORCE_PATH_STYLE=on`, else virtual-hosted; `S3_REGION` defaults to `us-east-1` (R2 takes `auto`). No session token (temporary credentials) yet.
   - **Segments named so that name order is turn order**: `<prefix><call>/<first>-<last>-<ms>-<server>-<n>.(trace|frames).jsonl`, the first and last turn index of the records (a frames segment, the call's turn when its first line was written), the time of its first line, the writing server (`SERVER_ID` and its suffix; `SERVER_ID` now names a server without Postgres too), and its count. The turn index travels with the call, so a takeover reads on in order whatever the servers' clocks say. Each line is the trace file's line byte for byte (`traceLine`, `frameLine`).
   - **Writes**: a record at once, frame lines within a second (or with the next record); a segment is never rewritten. A failure never stops a call: logged at once and then at most once a minute with a count (never a key), counted on `/health` as `traces` (`failures`, `dropped`), kept and tried again (2 s, doubling to 30 s, sooner with the next record), up to four megabytes waiting per call; a stopping server writes what is waiting for up to five seconds. A server that dies loses at most its last second of frame lines.
   - **Changed from the brief, a finding:** the brief said to match "a local disk failure today, logged and counted". Today's local writer does neither: `appendFileSync` throws inside `runTurn` after the audit is chained, so a full disk fails the turn (the caller hears "say that again" and the session does not advance). One machine is left exactly as it was (the overriding principle); the S3 writer never throws. Whether one machine should also log, count and go on is the maintainer's call.
   - **One reader** (`S3TraceReader`) for every reader: the console's list (from the object names alone: started at the first segment's time, turns its last index less its first plus one, as a call's turn indexes are consecutive) and replay, the text harness's `--replay s3://<bucket>/<prefix>/<call>`, and `kb:gaps --traces s3://...` and `kb:review`'s Gaps tab (both default to `TRACE_STORE` when set), exported from `dialogwright` for kb-author. Retention removes a call whole once its newest segment is past `TRACE_RETENTION_DAYS`, never a call live here.
   - Left: an app's own pages (`AppRouteDeps.traceDir`) still trace to files; the console's list reads the whole prefix's listing (paged, bounded by retention); a turn that outlived its hold writes its record to the store too, so the joined trace may then hold a turn index twice.

3. **The console across servers** (`server/stores/notices.ts`), as decided, with these choices:
   - **Notices on the session database**, opened whenever `SESSION_STORE=postgres` (a chat needs them with the console off): a row in `dw_notices` (its own `dw_schema` row, `notices`, version 1) and a `NOTIFY dw_notices` of its id, so a body of any size goes (a console `turn` event is often past `NOTIFY`'s 8000 bytes). Each server `LISTEN`s on a connection of its own (`SqlClient.listen`: the `pg` driver's reopened after a failure, with a read to catch up; PGlite's in the tests), reads the rows it has not seen (a lookback of 256 ids, as ids become visible in commit order), skips its own, and hands each to the topic's subscribers. Rows are swept after ten minutes; a server that starts hears nothing from before it.
   - **The bus** links to the notices (`DashboardBus.link`, `receive`): each event published on a server goes to the others as its console had it, redacted exactly as on one machine, and each server's bus numbers what it shows. One console follows every server's calls as one machine's follows its own (the most recent call).
   - **A chat resumed on another server**: the server that restores a chat from the store announces it, and the one that had it closes that socket (1000, `resumed elsewhere`, as on one server) and forgets the chat without an end or a store write. Doubtful: a turn the first server was still running then may save once more over the new server's save.

### As built (8b2): review fixes, and two decisions

Where this part and the one above differ, this one is what is built. Each finding is now a test.

**The maintainer's decisions.**

- **A. A trace write that fails never fails a turn, on one machine too.** The trace file and the frame log are written through a guard (`trace/guard.ts`) that logs at most once a minute (never more than the error) and counts on `/health` as `traces.failures` (shown only once a write has failed, so `/health` is as it was while the disk works), and the call goes on. With a disk that works every line is as before. An audit write that fails still fails the turn, as the audit is the record (tested: a chat whose audit folder is gone answers `server_error` on a turn the audit records). This is the second exception to "every option keeps the old behaviour" (after `RESUMED_AFTER_MS`), recorded in 14.10 and 14.12. It also settles the finding of the first 8b2 report: one machine now logs, counts and goes on, as the trace store does.
- **B. A retention policy by time and size**, each a setting whose default is what was there before (keep everything, no log file): `TRACE_MAX_GB` removes the calls written least recently, whole and never live, on one machine and on the trace store (beside `TRACE_RETENTION_DAYS`); the audit by time only (`AUDIT_RETENTION_DAYS`), never by size; `DISK_WARN_FREE_GB` (gigabytes rather than a percentage: a disk's size says nothing about how much a line needs) adds `freeBytes` and `low` to `/health`'s `disk` and warns in the log once an hour; `LOG_FILE` with `LOG_MAX_MB` (default 10) and `LOG_KEEP` (default 5) appends everything the process prints to a file the server rolls itself (`server/logFile.ts`), installed before the settings are read so a failed start is in it too. `pnpm service` sets `LOG_FILE` for launchd and sends launchd's stdout to `/dev/null` (its `err.log` keeps what goes wrong before the server reads its settings); systemd keeps the journal. `pnpm configure` writes the proposal into a new settings file: `TRACE_RETENTION_DAYS=30`, `TRACE_MAX_GB=5`, `DISK_WARN_FREE_GB=2`, `LOG_MAX_MB=10`, `LOG_KEEP=5`, and `AUDIT_RETENTION_DAYS` commented out with a word on keeping the record. `pnpm diagnose` says the policy in one line (a new check, `retention`, always ok). The numbers are the coordinator's proposal for the maintainer to adjust.

**Important.**

1. **The live feed counted as recorded before it was.** `noteLive` set its session as seen before the database had the record, so a browser's retry was served unrecorded. Now it is set once the record is written; a retry while the database is down is refused again (503, `the access could not be recorded`), and served, recorded once, when it is back (tested end to end).
2. **One lock per day serialised the fleet's audit.** Each server now anchors into its own chain for the day (`dw_audit_anchors` keyed by day, server and seq; the anchor names its server), so servers never wait on each other's anchors; a call's newest hash is still always anchored, and `audit:verify` walks every server's chain for every day (`<day> (<server>): N anchors, chain intact`). Every lock wait in an audit write is bounded (`SET LOCAL lock_timeout`, `SESSION_STORE_TIMEOUT_MS`). Pools are sized: 12 connections to the session database (one held for LISTEN, the rest for the stores and an audit sharing it), 5 to a separate audit database; the guide gives the database's `max_connections` to plan for.
3. **S3 listings, and the layout.** A listing past its page bound (1000 pages) throws instead of answering in part. A call's segments are now under the day it started (`<prefix><yyyy-mm-dd>/<call>/`, the session's `startedAtMs`, which moves with the call, so a call that crosses midnight or moves server stays in one folder; decided: its start day). The console lists the newest days only, until it has its fifty; retention lists and deletes only the day folders past the bound; a bucket's lifecycle rule is documented as the native way. The reader's join is unchanged from the outside (`read(id)` looks for the call's day from the newest back).
4. **Order and doubled turns** (the probe): segments are named `<first>-<last>-<gen>-<ms>-<server>-<n>`, `gen` being the call's reconnect count when written, so within a turn the server the call moved to reads after the one it left, by the reconnect the database counted, never a clock. **Changed from the review's wording:** the sequence is the reconnect count the call already carries (`CallEntry.reconnects`, saved with it and counted atomically before any takeover), not a new per-frame counter, which would have needed a change to the saved call for no better order: within one server, its own segment count orders. Records a server writes after it let the call go (the trace store sees that its entry is no longer the one the store holds) go to a `late` segment, marked `outlivedHold: true`; the console shows them as a marker ("a late turn") that changes nothing else on screen, `kb:gaps` passes over them (counted as skipped lines), and the turn counts leave them out. The guide's "whatever the servers' clocks say" and "no turn dropped or repeated" now name these exceptions.
5. **Privileges.** The guide lists every table with the rights a restricted user needs (`dw_notices` with `USAGE` on its sequence; the audit tables with `DELETE` only for retention). `ensureTables` takes a part whose tables are all there as made, with no DDL, even without its version row (written if the user may), so a restricted user opens notices an owner made. Diagnose tries a notice insert in a transaction rolled back and names the rights when it fails.

**Minor.** A sign-in link is made, and written to its file, only once `link_made` is recorded (`linkRecorded`, awaited at startup; `console:link` fails with 500 and writes nothing when it cannot be recorded). The audit's retention runs as one sweeper (a try-lock; the others skip), with a 60-second deadline of its own, removing old chains in set-based statements that re-check each chain's newest day with its lock held. A trace segment is named once and tried again under the same name, and lines written meanwhile go to a batch of their own (no duplicate after a lost answer: the probe). Notices are read every 30 seconds besides each NOTIFY, stamped and swept by the database's clock, and a chat's takeover carries its announcement's id (all servers' notices are ordered by it): a server lets a chat go only for an announcement later than its own restore of it (tested with a stale one). The S3 client reads every body within the request's deadline (a stall is an S3Error, the probe), up to a bound (64 MB an object, 16 MB a page or an error), says a store's error code only when it is letters and digits, and the trace store bounds what waits across all calls (64 MB). Diagnose check 12 lists its test object too. `AuditSink.append` may answer with a promise: `whenChained` and the `Chained` type are exported from `dialogwright` for an app's own pages (`AppRouteDeps.audit`), and the guide says so. A hangup's audit entry reaches the console before its end with the audit in Postgres, as on one machine (tested). The design doc's live-feed claim, the guide's note that the notices hold ten minutes of the console's redacted events (the callers' words among them) in the database, and the console test asserting the refusal's body are fixed.

**Left, or doubtful.** `audit:verify` still cannot tell a call's newest entries cut together with their anchors (the probe's last case, as a day file cannot). The size bound is swept hourly, so the traces may pass it by up to an hour's writes. The `pg` LISTEN path is still exercised only on PGlite.
