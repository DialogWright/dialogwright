# Texting: a sender and a webhook for any app, consent through the gate, and a photo sent back

Drafted and built on 2026-11-08 from the maintainer's decisions below. The engine gains texts (SMS and MMS) as a capability, neutral to any app; the wheelshop demo uses it to ask a caller for a photo of the damage once their request is confirmed, and to send that photo on to the shop.

## The maintainer's decisions (2026-11-08)

1. **The wheelshop texts from its own Twilio number.** A test text from that number was delivered, so the number is registered and can send.
2. **The caller gives consent at the request.** A required yes or no, asked after the callback number ("Is it OK if we text you at that number?"), read back with the request.
3. **After the request is confirmed, the caller gets a text:** reply with a photo of the damage.
4. **Their reply's photo is forwarded to the shop's phone** with the request's summary.
5. **Reply with a photo, not an upload link.** No page to host, nothing for the caller to open: they answer the text the way they answer any text.

## The shape

### The engine: a capability for any app

**Sending.** The server gives app code a sender: `ctx.texts?.send({ to, body, media? })` on the tool context (and on the app context of a hook), absent where no sender is configured. The provider is Twilio's Messages API by fetch (no SDK), with `TWILIO_ACCOUNT_SID` and `TWILIO_AUTH_TOKEN`; the number texts are sent from is `TEXT_FROM`, which under a host an app's own settings file may give its own (a business's own number). `TEXT_FROM` unset is no sender, the default: no text is sent, as before. A send never throws: a failure is a receipt with `status: failed` and the provider's code and message (numbers masked). A text sent with a key (`key: ctx.idempotencyKey`) is not sent twice on the server; the first receipt comes back, marked `repeat`.

Each text is recorded in the audit (`text_sent`: the number by its last four, the body by its length, the media by their count, the provider's message id and status) and, on a call or chat, in the turn's trace (`texts`). The words are never recorded: they are the app's fixed lines, and the caller's own number is the one thing a text carries that the records mask.

The provider is one adapter, `TextProvider` (`texts/types.ts`): `{ id, send({ to, from, body, media }) }`. A Telnyx sender is a second adapter of the same shape, chosen by a setting when it is added; nothing an app writes changes.

**Receiving.** `POST /messages/twilio`, Twilio's signature checked exactly as the voice webhook's is (the same HMAC over the public URL and the form), refused (403) when invalid. Its fields (`From`, `To`, `Body`, `MessageSid`, `NumMedia`, `MediaUrlN`, `MediaContentTypeN`) become an `IncomingText`; the number texted (`To`) picks the app, as a call's number picks it under a host. Twilio is answered at once with an empty `<Response/>` (no auto-reply from the engine), the message is recorded (`text_received`, under its message id on the `sms` channel: the sender by their last four, the media by their count), and it is handed to the app's new optional hook, `AppCode.onText(message, ctx)`, whose context has the sender (`ctx.texts`), the app's settings (`ctx.env`) and its systems (`ctx.sys`). The engine downloads no media: the URLs are Twilio's, and forwarding passes them as `MediaUrl` on the outgoing message, which Twilio fetches.

**Consent through the gate.** A form's `then` entry in business.yaml may carry a condition: `{ tool: send_photo_link, when: { field: textOk, is: "yes", reason: no-consent } }`. The business compiler writes it as a `oneOf` rule on the tool's param, after the read-back's `confirmed`, so with a no the gate refuses the text, the refusal is audited under its reason, and the form goes on without it (the write made, the done line said). `pnpm check` holds the condition to a choice field of the same form and one of its options, and refuses it on the form's write (its first tool, which a yes always makes). The policy card lists each such action under "Done only on the caller's answer", with the field, the option and the reason.

**A choice said one way in each line.** A choice field's `says` may give an option `{ readBack, done }`, so the consent reads back as "and we'll text you at {callbackNumber}" and the done line says "Reply to our text with a photo ...", or, for a no, "and we'll call you at" and "We'll call you ...".

**The business's text lines.** business.yaml gains `texts:`, the texts the app's own code sends, by name, in fixed words with the placeholders its code fills: never a generated line, never said on a call. And `owner.number` is optional, since a real number belongs in the app's settings.

### The wheelshop

- The request gains a required `textOk` (yes or no), asked after the callback number, read back by its `says`; the price line and the done lines say "reply to our text with a photo", still promising nothing before the read-back's yes (the agent-mode design's decision 25).
- `send_photo_link` is a real text from business.yaml's `texts.photoRequest`, held to the consent by the gate, idempotent on `ctx.idempotencyKey`, and printed where there is no sender.
- `notify_owner_request` and `notify_owner_booking` text the summary to `SHOP_PHONE`, the app's own setting, printed where it is unset or there is no sender. A text to the business is not a text to the caller, so no caller's consent applies.
- `onText`: a text from a number with a recent request (the app's systems keep each request by its callback number, in memory: the demo's, said so in DESIGN.md) is forwarded to `SHOP_PHONE` with the photos ("Photo from {name}, ...{last4}, for their {vehicle} request."), and the caller gets the fixed thank-you ("Got it, thanks. We'll text you a price soon."); a text from an unknown number is forwarded as "Text from ...{last4} (no request on file)"; a text with no photo is forwarded too.

## Settings

| Setting | Default | What it does |
|---|---|---|
| `TEXT_FROM` | unset: no sender | The number texts are sent from (E.164); on a host, an app's own settings file may give its own. |
| `TWILIO_ACCOUNT_SID` | unset | The Twilio account texts are sent through; needed with `TEXT_FROM`. |
| `TWILIO_AUTH_TOKEN` | (the voice webhook's) | Sends the texts, and checks the incoming webhook's signature. |
| `SHOP_PHONE` (the wheelshop's own) | unset: the shop's summaries and forwards are printed | The shop's phone the summaries and photos go to. |

The Twilio console's number takes `https://<PUBLIC_HOST>/messages/twilio` as its "A message comes in" webhook (HTTP POST).

## Calls made for the maintainer to check

1. **The incoming hook runs after Twilio is answered,** so a slow forward never holds Twilio's webhook (its timeout is 15 s); a hook that throws is logged, and what it sent before it threw is still recorded.
2. **Twilio's media URLs are passed as they come.** Where the account enforces HTTP basic auth on media URLs, Twilio cannot fetch them for the forward; the default does not, and the engine never fetches them itself.
3. **The keys of texts sent are kept in memory** (the latest 2000 per app): a server restarted between a send and its repeat sends again. The wheelshop's stand-in systems keep theirs in memory too.
4. **The recent request a text is matched to** is the wheelshop's, kept in its systems in memory for seven days; a restart forgets it, and the photo is then forwarded as from an unknown number, which still reaches the shop.
5. **The thank-you goes only with a photo** from a number with a recent request: a text with no photo is forwarded, and the caller gets no reply, so a word like STOP is never answered with "We'll text you a price soon" (Twilio answers STOP and HELP itself).
