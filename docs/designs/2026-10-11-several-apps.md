# Several apps on one deployment (design, for review)

Date: 2026-10-11. Status: **decided (the maintainer, 2026-10-11); to be built after Phase 8b and before the console.** Source: the maintainer, 2026-10-11: clients where each phone number (the number called, often called the DNIS) launches a different app; a self-hosted deployment with one owner; calls from Telnyx and Twilio at once, many numbers on each; no transfers between apps yet.

## At a glance

Today a server runs one app: the engine keeps a registry of apps and every session records its app's id, but the server registers one app and sends every call to it. This design lets one deployment (one server, or many under Phase 8b) run several apps and choose the app for each call by the number called, with a default for a call that names no number. Each app stays a folder of its own, with its own policy, prompts, tests, traces and audit. Nothing changes for a deployment that runs one app.

## The hosting file

```text
# host.yaml, beside the apps (or named by HOST_FILE)
apps:                                            # each app is known by the id its own app.yaml gives it
  - apps/utility
  - apps/clinic
  - { package: "@acme/repairs-line" }            # an app installed as a package
numbers:                                          # the number called -> the app's id; several numbers may name one app
  - { number: env.POWER_LINE,  app: utility }
  - { number: env.CLINIC_LINE, app: clinic }
  - { number: env.CLINIC_LINE_ES, app: clinic }
default: utility                                  # a call with no number, or a number listed nowhere
# web chat chooses its app by path: /chat/<app id>
```

## Decisions proposed

1. **One owner, one set of carrier accounts.** `VOICE_PROVIDERS=twilio,telnyx` already takes calls from both at once, each with its own secret; every number on either carrier points its webhook at the same server. Separate accounts per app (a hosted, many-customer product) are out of scope.
2. **The number chooses the app.** The number called, as each carrier delivers it (the same normalising as the `called` route condition), is looked up in `numbers`; an exact match picks the app, anything else goes to `default`. Numbers stay in the environment, never in YAML. A number listed for two apps is refused at start. An app's `voice.numbers` (number to language) keeps working inside the app.
3. **Settings in two layers.** The server's settings file holds what is shared (carrier secrets, the model and its key, `PUBLIC_HOST`, the stores). Each app may keep a settings file of its own for its own variables (its transfer targets, `startParameters`, `called` numbers), read only for that app, so `env.BILLING_NUMBER` in two apps can mean two numbers. `pnpm diagnose` checks every app's variables.
4. **Records per app.** Traces and audit go to a folder (or key prefix, or Postgres schema column) per app; the audit's chain stays per session, so nothing forks. The console shows every app's calls with an app filter and the app's name on each row; Insights can be read per app or together.
5. **Chat by path.** The engine's web chat serves each app at its own path; the widget names it (`data-app`), defaulting to the default app.
6. **No transfers between apps.** A call starts and finishes in its app. A transfer to a person works as today, with each app's own targets.
7. **Commands.** `pnpm start` takes `--host <file>` (or finds `host.yaml`), and `--app` keeps its meaning for one app. `pnpm configure` can add an app to a host file. `pnpm check` checks the host file (every app exists and passes its own check, no number twice, the default is an app).
8. **One app stays the simple case.** With no host file, a server runs its one app exactly as today.

## Decisions (the maintainer, 2026-10-11)

1. **Numbers live in host.yaml**, each pointing at an app by the id its own app.yaml gives it, so several numbers pointing at one app (likely common) is one line each and the app folder names no number. host.yaml lists the apps by folder or package; app.yaml defines the app.
2. **Settings in two layers:** each app's settings are its existing `.env` (so `pnpm configure` keeps working per app); what every app shares (carrier secrets, the model and its key, `PUBLIC_HOST`, the stores) is in a server-level settings file.

## As built (2026-10-12)

Built as decided, on the branch `several-apps`. Where the design left a choice open, or a point needed one, the choice and why:

1. **The file.** `host.yaml` (schema `packages/dialogwright/schemas/host.schema.json`, from `define/schema/host.ts`): `apps` (each a folder path from host.yaml's folder, `{ folder, env }`, or `{ package, env }`, a package found in `node_modules` from host.yaml's folder upward), `numbers` (`{ number: env.<NAME>, app: <id> }`, a number never written in YAML) and `default` (optional: the first app listed). It is read with no app code loaded (`define/host.ts` `resolveHostFile`), and every problem is a line at its place in host.yaml with its fix: an app folder missing, a folder with no app.yaml, an app listed twice, a number's app or the default not among the apps, one variable listed twice, an app's named settings file missing.
2. **Finding it.** `--host <file>`, else `HOST_FILE`, else `host.yaml` at the project's root (beside the apps); `--app` always runs one app; with none of these, a server runs its one app exactly as before (every existing test, regression and the adoption test unchanged). This repository has no host.yaml at its root, so its commands are as they were; the fixture is `packages/dialogwright/src/testing/host/` (the callback and routed fixture apps, each with its own settings file, both naming `MAIN_LINE`).
3. **The number picks the app.** The answer webhook matches the number called (Twilio's `To`, Telnyx's) as a `called` condition does (`sameNumber`: a ten-digit national number matches its `+1` form) and answers in that app (its languages, start parameters, hints, callData echoes). The setup must agree on whichever server it lands, so the start document names the app as the custom parameter `dialogwright_app` (`HOST_APP_PARAMETER`, reserved in an app's `startParameters`, sent only under a host); the setup takes it, else its own number called (Twilio's `to`, Telnyx's `telnyx_call_to`), else the default. A reconnect, a callback, a restore and a takeover use the app the session was saved in (sessions always carried `appId`). The server refuses to start when a number is unset or not E.164, or two variables hold one number. That Telnyx hands `dialogwright_app` back in the setup's custom parameters rests on what callData's `dw_<key>` echoes already rely on; a live call should confirm it ([live-checks.md](../live-checks.md)), and the setup's own number is the fallback meanwhile.
4. **Settings in two layers.** The server's settings file (`ENV_FILE`, or the `.env` beside host.yaml) holds what every app shares, the numbers among it. Each app's own file (its `.env`, or the one its entry's `env` names) is read only for the variables its YAML names (`appYamlEnvReferences`: transfer targets, `startParameters`, `called` numbers), over the server's settings; a variable an app names and its own file does not set is the server's; another app's file is never read for it. The rest of an app's `.env` is not read under a host, and `pnpm diagnose --host` names what is there. An app's code reading `process.env` sees the server's settings only. `pnpm configure` still writes one app's `.env` as before; adding an app to a host file is a line in host.yaml written by hand, which `pnpm check` checks: a command to edit YAML would be less clear than the line itself.
5. **Records per app.** Traces in `TRACE_DIR/<app id>/`, the audit in `AUDIT_DIR/<app id>/` (a chain per app per day), recorded clips in `AUDIO_DIR/<app id>/` (served at `/audio/<app id>/`); the server's own audit, the console's sign-ins and replays (no app's), in `AUDIT_DIR/_server/` (an app id starts with a letter, so none is `_server`). Every audit entry under a host names its app in `app`, hashed with the entry. In Postgres (`AUDIT_STORE`) the audit stays a chain per call, each entry naming its app in its body: no new column and no migration, and the app is as tamper-evident as the rest of the entry. On the trace store each app's traces are under `<prefix><app id>/`. Retention is the server's, the same for every app: the days for each folder, and `TRACE_MAX_GB` bounding each app's traces (so one busy app never removes another's). `pnpm audit:verify` walks each app's folder and the server's; `pnpm kb:gaps --traces TRACE_DIR/<app id>` reads one app's.
6. **Chat by path.** Each app's chat at `/chat/<app id>`, the default's at `/chat` too; the widget's `app` (`data-app`) connects to `<endpoint>/<app>`. `CHAT_ALLOWED_ORIGINS` and the sign-in stay the server's, one list for every app (a list per app can come when a deployment needs one); `CHAT_MAX_SESSIONS` is counted per app; a chat is resumed only at its own app's path.
7. **The console, minimally.** One console for every app: each replay row starts with its app's name, the header's app filter (`/dashboard?app=<id>`) shows one app's calls alone, live and in Replay, a replay is read from its own app's records, and the page carries each app's console words so each call is shown in its own; the live feed's `call_started` names the call's app. Insights per app waits for the console's redesign.
8. **Commands.** `dialogwright serve [--host <file>]` (`pnpm serve` here) is the server of a host file, every app in one process; `pnpm start --host` and `pnpm service ... --host` run it as `node <the engine's bin> serve --host <file>` (`bin/dialogwright.mjs`, which registers tsx's loader, so the apps' TypeScript is imported in any folder), in the host file's folder, so a relative `TRACE_DIR` is beside it. `pnpm check host.yaml` (and a bare `pnpm check`, for the host.yaml beside the apps) checks the file, then each app it lists with its own check. `pnpm diagnose --host` runs the server's checks with its settings, then the numbers, then each app's own variables as the server will read them.
9. **What a host does not run.** Each app's code is imported from its folder (`app.ts` or `src/app.ts`, as `pnpm check` reads it, else `index.ts`), not its own launcher: what a launcher starts beside the server (downstream services, its own pages, such as the utility's chat demo) does not run under a host, and an app's service requests are answered with no result. A deployment that needs them writes its own launcher with `loadHost` and `serverMain` (both exported by `dialogwright`; `ServerOverrides.apps`).
10. **Many servers.** Each server runs the same host.yaml; a call taken over keeps its app (shown on two servers sharing PGlite, the audit and an S3 store, on both carriers).

### Review fixes (2026-10-12)

A review found the first build ran every app's tools against the default app's systems and its gate's lookups (one set of tools for the process), and that several other things were the default app's or the server's alone. As fixed:

11. **Each app's tools.** Made once per app for the process (`{ ...app.systems(), codes: mockCodeVerifier }`, so a record one call makes is there for the next, as for one app) and given to its calls (new, restored and taken over), its chat and, for the default app, a launcher's pages. The test that would have caught it runs, in an app that is not the default, a write, a read behind identity under its own scope rule, a handoff to its own transfer target, its chat (on both carriers and through a takeover on two servers), and, in the testkit as a second app, identity with a one-time code and a downstream service request (`server/host.apps.e2e.test.ts`, `server/host.many.e2e.test.ts`).
12. **Each app's client.** With `JEV_CLIENT=heuristic` or `stub` each app has its own client (the stub from its own fixtures' corpus, found from its package's folder, parsed against the app; its heuristics alone where it has none); a model client (jev, the cassettes) is shared, since a model knows no app.
13. **Masking by the call's own app.** The trace writer (files and the trace store), the console's live records and replays, and the frame log's end frame masked by the default app's slots; they now take the call's app (a routed call's account and birth date were in its trace in the clear when the default app had no such slots).
14. **HANDOFF_NUMBER per app.** An app's own settings file may give its own `HANDOFF_NUMBER`, `CHAT_AUDIENCE` and `CHAT_ISSUER` (`APP_OWN_SETTINGS`), else the server's. With several apps, one with neither transfer targets nor its own `HANDOFF_NUMBER` is warned of at start and by `pnpm diagnose --host`; a stopping server's new calls go to each app's own.
15. **Services per app.** host.yaml's app entry names its services' URLs by variable, `services: { <name>: env.<NAME> }`, read from the app's own settings; a launcher's `serviceUrls` are the default app's alone under a host, so two apps' services of one name never share a URL. A service with no URL is a WARNING at start (no refusal: one in the process needs none); diagnose checks each URL host.yaml names.
16. **Chat sign-in per app.** `CHAT_AUDIENCE`, `CHAT_ISSUER` and `CHAT_JWKS_URL` per app (above), so an app's portal may sign in with an identity provider of its own: each app's chat verifies tokens against its own provider's keys, each JWKS URL's keys fetched and cached once for the server (`ChatDeps.keysFor`). There is no shared-secret variant of the sign-in to carry. With `CHAT_SIGNIN=jwt` and several apps, two apps sharing an audience is a WARNING at start and in diagnose; diagnose checks each app's own JWKS URL and warns of one without its own issuer. A test signs in with two providers' keys, each app's token accepted only at its own `/chat/<id>`; it fails when every app's chat reads the server's JWKS URL.
17. **The smaller ones.** What an app's own file sets and does not name is logged by name at start. `pnpm serve` reads the `.env` beside host.yaml when no settings file is named. A SIP `To` (`sip:+1...@host:port`) is read by its user part, for host routing and `called` conditions alike; a digit-for-digit match wins over a ten-digit one, and two numbers ending in the same ten digits are a WARNING. The console's header links follow the call's app, a replay is addressed by its app (`?app=`), and its access entry names the app. `dialogwright_app` is reserved for an app built in code too (validateApp). `pnpm check <file>` reads a file as a host file only by its name or its shape. The guide says the settings' precedence, how to move one app's records into a host, and that `TRACE_MAX_GB` and `CHAT_MAX_SESSIONS` count per app.

**The sweep.** Every use of the default app, and every process-wide singleton, in `server/`, `core/`, `run/`, `jev/`, `trace/`, `handoff/`, `kb/` and `prompts/`, and why each is right under a host:

- Fixed above: `core/tools.ts demoTools` (one app's systems), `run/client.ts buildClient` and `jev/heuristicStub.ts`/`jev/fixtureStub.ts`/`jev/corpus.ts loadCorpus` (one app's heuristics and corpus), `trace/writer.ts traceLine` and `trace/store.ts` segments, `server/dashboard/events.ts redactRecord`/`redactFrameLine`, `server/dashboard/observer.ts` (its `redactTurnState`), `server/adapter.ts loggedFrame` (the end frame's handoff data), each now given the call's app.
- Right as they are: `core/session.ts newSession`/`emptySlots` (the server names the app under a host; the default only on a server of one); `core/app/registry.ts appOf` (the session's own app); `server/index.ts` (the default app only on a server of one); `server/dashboard/routes.ts spokenOf`/`pageMeta` (the default only when the console has no apps list, a server of one); `trace/redact.ts`'s default parameters (every server caller now passes the call's app; the harness, which runs one app, relies on the default); `jev/defaults.ts quietAnswer` (given the stub's app); `run/fixtures.ts`, `run/client.ts buildThresholds`, `jev/corpus.ts corpusApp`, `prompts/sheet.ts` and `prompts/generate.ts` (the harness and the clip tools, run per app in its own package, never by a host's server); `core/thresholds.ts` (an app's own thresholds are merged per session in the core).
- Process-wide singletons that are per call: the adapter's maps and sets (`noInputTimers`, `continuations`, `heldEnds`, `reportsPlayback` and the rest, keyed by the call's id), the token store, the session store (each entry holding its own app's resources); shared on purpose: the dashboard bus (one console; each `call_started` names its app), the injection screen and the model client (no app in them), the clock, and `BOOT_ID`. The knowledge base's retriever is the app's own (`App.knowledge`); a handoff summary reads the call's app (`appOf(session).handoff`).

What the tests show: `define/host.test.ts` (the file and its problems), `server/host.test.ts` (routing, the two layers of settings, loading the fixture), `server/host.e2e.test.ts` (on Twilio and Telnyx, a call to each number reaches its app, the second number of an app too, any other number or none the default; each app's handoff and a drained call go to its own `MAIN_LINE`; records in each app's folder with `app` on every entry; chat at each path and a 404 for no app; the console's rows, filter and replay), `server/host.many.e2e.test.ts` (a call taken over after its server dies stays in its app, its trace under the app's prefix, its audit verified with every entry naming the app), and the commands' own tests (`hostServe`, `start`, `doctor`, `serviceFile`, `hostCheck`, `verifyCli`). `server/host.apps.e2e.test.ts` (the review's: a non-default app's write, scoped read, identity, handoff, transfer target, service request, own client, own masking and chat; and the utility, not the default, answering from its own approved passage word for word with keyword retrieval where the embedder's model is not cached, its `kb_answer` naming the app, while the default app, with no knowledge base, does not: the test fails when the turn's retrieval reads the default app's knowledge). Not built: transfers between apps, separate carrier accounts per app, Insights per app, and a command that edits host.yaml.
